### 1.1 풀 전략을 바꾸면 옛 풀의 비활성 인스턴스가 씬에 쌓인다

**문제**: 풀 전략(A 자체 풀, B 생성·파괴, C Unity 내장 풀)은 개발자 모드에서 토글한 뒤 다음 판 시작에 바뀐다. 판 경계 흐름은 활성 객체 전부 반납(`DespawnAll`), 전략 교체(`ReplaceStrategies`), 새 풀 예열(`Prewarm`) 순서다. 이때 옛 A·C 풀이 쥐고 있던 비활성 인스턴스를 아무도 치우지 않았다. 반납된 객체는 옛 풀 안에 비활성으로 남고, C# 전략 객체를 버려도 그것이 만든 GameObject는 씬 계층에 그대로 있다. 예열 수량이 카테고리 합계 약 1,500개(Monster 450, PlayerProjectile 300, EnemyProjectile 100, PlayerOrb 16, PlayerZone 16, EnemyZone 8, Gem 600, Chest 16)라 토글 한 번마다 그만큼 쌓일 수 있었다. 비활성 객체는 CPU를 거의 쓰지 않아 프레임 시간에는 바로 드러나지 않으므로, 측정을 토글하며 반복하면 조건이 조금씩 달라지는 조용한 오염이 된다.

**원인**: `IPoolStrategy`가 활성 객체 반납(`ReleaseAll`)만 정의하고 풀이 만든 객체의 수명 종료를 빠뜨렸다. Unity에서는 C# 객체 수명(전략 인스턴스가 GC 대상이 되는 것)과 씬 객체 수명(GameObject는 `Destroy`해야 사라짐)이 다르다. 교체 가능한 전략을 설계할 때 "생성"만 인터페이스에 올리고 "정리"를 빠뜨린 것이다. 웨이브 2a 구현자 보고의 미확정 항목을 코드 리뷰하다 발견했고, 단일 전략 안의 동작만 검사하는 테스트로는 잡히지 않았다.

**해결**: `IPoolStrategy`에 `void Clear();`를 추가했다. 의미는 "이 전략이 보유한 비활성 인스턴스를 전부 파괴한다"이다. A는 템플릿별 스택을 비우며 파괴하고, C는 `ObjectPool.Clear()`(파괴 콜백)를 부르며, B는 할 일이 없다. 활성 인스턴스가 남아 있으면 `InvalidOperationException`을 던져 호출 순서(`DespawnAll` 먼저)를 강제한다. `EntityLifecycle.ReplaceStrategies`는 풀 객체가 바뀔 때 `DespawnAll`, 옛 풀 `Clear()`, 새 풀 `Prewarm` 순서로 부른다. 앱이 씬을 검색해 비활성 `PooledObject`를 파괴하는 안(풀 내부 상태와 씬 상태가 어긋나고 씬 전체 검색 비용이 든다)과, 누적을 허용하고 측정 때 토글 뒤 재시작하는 운영 규칙(사람이 지켜야 하고 알려진 한계로만 남는다)은 채택하지 않았다.

**배운 점**
- 교체 가능한 전략은 생성과 정리를 한 쌍으로 인터페이스에 둔다. `IDisposable`을 붙이는 것과 같은 이유다.
- Unity에서 "객체를 버린다"는 두 가지다. C# 참조를 놓는 것과 `Destroy`하는 것. 풀처럼 GameObject를 만들어 쥐는 객체는 두 번째를 책임져야 한다.
- 단일 전략의 단위 테스트는 전략 교체 경계의 결함을 못 잡는다. 교체 시나리오(A에서 C, 다시 A) 테스트가 필요하다.

### 1.2 엔진 충돌판과 자체 충돌판이 36조합 중 18조합에서 다른 상태 해시를 냈다

**문제**: 웨이브 7 구현 중, 풀 3 x 타깃 3 x 틱 2 x 충돌 2 = 36조합의 상태 해시 일치 검사에서 엔진 충돌판 18조합이 자체 충돌판과 다른 해시를 냈다. 전략을 바꿔도 결과가 같아야 한다는 프로젝트의 결정론 주장이 깨진 것이다.

**원인**: 두 전략이 접촉 경계를 다르게 판정했다. 접촉 거리에 정확히 닿는 순간(제곱거리 0.490000129 대 제곱반지름 합 0.48999998), Box2D는 허용오차로 한 스텝 먼저 Enter를 내고 자체판은 정확 비교라 다음 스텝에 낸다. 이 경계 접점은 몬스터가 플레이어에서 정확히 접촉 거리에 멈추는 규칙과, 플레이어 중심에서 스텝당 0.15로 2틱 날아간 탄(거리 0.7 = 0.2 + 0.5)이 겹쳐 체계적으로 생겼다(판당 약 120건). 옛 규칙에서는 탄이 첫 Enter에서 소모돼 1스텝 차이가 흡수됐다. 하지만 "이미 죽은 대상은 통과한다"는 새 규칙(1.3)에서는 살아남은 둘째 탄의 궤적이 1스텝 밀린 채 이어져 판 끝까지 갈라졌다. 바로 전날 넣은 규칙이 잠복해 있던 경계 차이를 드러낸 것이다.

**해결**: `EngineCollisionStrategy`가 `Physics2D.Simulate` 뒤 Box2D가 접촉 중이라고 아는 쌍과 이번 스텝 콜백이 온 쌍을 후보로만 두고, 각 후보에 대해 자체판과 같은 `CircleMath.Overlaps`(R5)로 현재 위치와 반지름을 다시 계산해 참/거짓의 순변화만 Enter/Exit로 보고한다. 보고되는 겹침 상태의 단일 소유자는 두 전략 모두 R5이고, Box2D는 후보 탐색(넓은 판정)만 맡는다. 이벤트 정렬·채널·형식은 바뀌지 않는다. 36조합 기준을 "같은 충돌 전략 안에서만 일치"로 완화하는 안, 탄 통과 규칙을 철회하는 안, Box2D 접촉 오프셋·데이터(W4 속도)를 조정하는 안은 각각 결정론 주장 약화, 전날 결정의 번복, 이 사례만 피하고 경계 클래스는 남는다는 이유로 채택하지 않았다. 측정에는 "엔진판 = Box2D 후보 + R5 정확 좁은 판정"이라는 의미가 더해지며, 스텝당 추가 비용은 후보 쌍 수만큼의 제곱거리 비교다.

**배운 점**
- 같은 판정을 두 구현이 따로 하면 경계 조건에서 반드시 갈라진다. 판정의 정의는 한 곳(R5)에 두고 구현마다 "후보를 찾는 일"만 다르게 해야 한다.
- 부동소수·엔진 허용오차는 평소에는 안 보이다가, 새 규칙이 차이를 증폭하는 순간 드러난다. 규칙을 하나 넣을 때마다 36조합 해시 검사를 돌려야 하는 이유다.
- 결정론 주장을 지키려고 비교 기준을 완화하면 주장 자체가 약해진다. 완화하기 전에 차이의 원인을 먼저 닫는다.

### 1.3 같은 스텝에 이미 죽은 몬스터에 닿은 탄이 소모됐다

**문제**: 2026-11-11 스모크 라운드에서 한 몬스터에 탄 여러 개가 동시에 닿고 탄 공격력이 몬스터 체력보다 크면, 탄이 전부 사라진다는 체감이 있었다.

**원인**: 코드로 확인하니 `PlayerHitHandler.HandleProjectile`이 대상의 생존 여부를 보지 않고 `ApplyDamage`(죽은 뒤에는 무시)를 한 뒤 소모 처리와 디스폰을 했다. 명세에 "이미 죽은 대상"에 대한 규정이 없던 공백이지 코드 결함이 아니었다.

**해결**: 아군 투사체가 Enter한 대상이 그 시점에 이미 죽어 있으면 피해도 소모도 없이 통과하도록 했다. 그 대상은 "맞힌 목록"에 기록해 같은 탄이 같은 대상을 다시 맞히지 않는다. 탄은 계속 날아가 다음 적에 정상 명중한다. 처리 순서는 충돌 이벤트 정렬 순서로 고정이라 전략과 무관하게 같다. 탄 낭비를 밸런스 요소로 남기는 안은 체감이 나쁘고 의도된 규칙이라 할 근거가 없어, 초과 피해를 다음 적에게 이월하는 안은 관통 규칙·피해 분배와 얽혀 복잡해지고 결정론 검증 범위가 늘어나 채택하지 않았다.

**배운 점**
- "대상이 이미 죽었다"처럼 같은 스텝 안에서 순서에 따라 갈리는 경우는 명세에 명시하지 않으면 구현이 임의로 정한다. 같은 스텝 다중 이벤트 규칙은 정렬 순서와 함께 적는다.
- 사용자의 체감 제보가 곧바로 코드 확인으로 이어지는 절차(제보 → 코드로 사실 확인 → 규칙으로 승격)가 효과적이었다.
- 이 규칙은 1.2의 해시 불일치를 드러내는 계기가 되었다. 규칙 하나가 다른 영역의 숨은 차이를 증폭할 수 있다.

### 1.4 디스폰된 몬스터가 겹침 집합에 남아 계속 피해를 줄 수 있었다

**문제**: 등록 해제된(디스폰된) 몬스터가 겹침 집합에 남아, 이미 사라진 몬스터가 플레이어에게 계속 피해를 주는 경로가 있었다.

**원인**: 설계 1회차의 버그였다. 등록 해제 시에는 Exit 이벤트가 나오지 않아, 겹침 기록을 지우는 곳이 없었다. 기능 구현 전 명세 정합 점검(TECH 2회차)에서 발견했다.

**해결**: `Despawned` 이벤트에서 겹침 기록을 삭제하도록 했다.

**배운 점**
- 상태를 이벤트(Enter/Exit)로 쌓는 구조에서는 "객체가 이벤트 없이 사라지는 경로"가 상태 누수의 전형적 원인이다. 생명주기 종료도 상태 정리의 트리거로 본다.
- 구현 전에 계약 문서끼리 대조하는 점검이 코드 전에 버그를 잡을 수 있다.

### 1.5 몬스터끼리 분리 패스를 `MonsterTick`에 두면 틱 전략에 따라 결과가 갈린다

**문제**: 플레이 중 몬스터끼리 겹친다는 피드백으로, 매 스텝 겹치는 몬스터 쌍을 반지름 합까지 밀어내는 분리 패스를 넣어야 했다. 처음 떠올리는 위치는 몬스터 이동을 하는 `MonsterTick` 단계였다.

**원인**: `MonsterTick` 핸들러는 `SimulationDriverEarly` 안에서 돌고, 객체별 틱(`PerObjectFixedUpdate`) 전략의 몬스터 이동(`MonsterSelfTicker`, 실행 순서 -500)은 그보다 뒤에 돈다. 즉 `MonsterTick`에 두면 분리가 이동보다 먼저 실행되어 두 틱 전략의 입력 위치가 달라지고, 전략 무관 동일 결과라는 요구가 깨진다.

**해결**: `MonsterSeparation`을 `BuildIndex` 단계 순서값 -10에 두었다. 이동은 어느 틱 전략이든 `BuildIndex` 앞에서 끝나 있다. 이웃 후보 탐색은 전수 O(n^2)이고(400기에서 스텝당 79,800쌍), 쌍은 패스 시작 위치 기준으로 ID 오름차순 처리하며 보스는 밀리지 않는다. 비용이 문제가 되면 공간 해시로 바꾸되 쌍 집합과 처리 순서는 같아야 한다.

**배운 점**
- 같은 이름의 단계라도 어느 드라이버에서 도는지에 따라 다른 전략의 코드와 상대 순서가 달라진다. 새 규칙을 단계에 넣기 전에 객체별 틱처럼 "끼어드는" 코드와의 순서를 확인한다.
- 비용이 걱정되는 O(n^2)는 먼저 올바른 위치에 두고 측정으로 판단한다(F10 측정에 400기 비용이 들어간다).

출처: DECISIONS 5절 "첫 Play 피드백: 몬스터 규칙 3건 (2026-11-10 사용자 요청)" 3항. 단계 위치의 근거는 TECH 5.12.1 "몬스터끼리 분리 패스"(웨이브 7).

### 1.6 같은 스텝에 상자를 둘 이상 먹는 경우의 규정이 없었다

**문제**: 상자 효과는 진화 조건을 충족한 무기가 있으면 진화가 우선이고, 없으면 강화 70%·회복 30%다. 같은 스텝에 상자를 2개 획득하면 어느 상자가 먼저 처리되는지, 앞 상자의 진화 결과가 뒤 상자의 판정에 보이는지 규정이 없었다.

**원인**: 기획 단계에서 상자를 한 번에 하나씩 먹는 것으로만 상정했다. 2차 독립 검토가 이 규정 공백을 찾았다(규정 공백 8건 중 하나).

**해결**: 같은 스텝에 상자를 2개 이상 획득하면 충돌 이벤트 정렬 순서대로 하나씩 처리하고, 앞 상자의 진화 결과를 뒤 상자의 판정에 반영하도록 명세에 적었다. 진화 자격 무기가 1개뿐일 때 채널 8 정렬 순서에서 앞 상자가 진화하고 뒤 상자는 그 결과를 본 상태로 판정(자격 무기 없음, 70:30 추첨)하는 것을 EditMode 테스트("상자 2개 순차")로 고정했다.

**배운 점**
- 다중 이벤트가 같은 상태를 읽고 쓰는 곳은 "동시에" 처리하지 않고 정렬 순서에 따른 순차 처리로 정의한다. 결정론 정렬 키가 이미 있으면 그대로 재사용한다.
- 독립 검토가 코드가 아니라 명세의 빈칸을 찾아 주었다. 규정 공백은 구현 전에 닫는 것이 싸다.

### 1.7 객체별 `FixedUpdate`는 호출 순서가 보장되지 않아 결정론이 깨질 수 있었다

**문제**: F17의 객체별 틱(A) 모드는 몬스터마다 `FixedUpdate`를 호출한다. Unity는 같은 클래스 인스턴스끼리의 호출 순서를 보장하지 않는다. 그런데 중앙 틱(B)과 같은 스텝 결과가 나와야 비교가 공정하다.

**원인**: 인스턴스 사이의 호출 순서가 비결정이다. 한 몬스터의 `Tick`이 다른 객체(투사체 생성, 소환, 사망)에 직접 영향을 주면, 호출 순서에 따라 결과가 갈린다. 엔티티 클래스에 `FixedUpdate`가 있으면 Unity가 중앙 틱 모드에서도 그것을 호출해 측정이 불공정해지는 문제도 있었다.

**해결**: `Tick`은 자기 상태만 쓰고, 다른 객체에 영향을 주는 일은 지연 명령 큐에 넣어 Lifecycle 단계에서 (Source, Sequence) 순으로 적용한다. 엔티티 클래스에는 `FixedUpdate`를 두지 않고, 객체별 모드에서만 켜지는 별도 컴포넌트(`MonsterSelfTicker`, `ProjectileSelfTicker`)가 `FixedUpdate`를 가진다. 두 컴포넌트의 실행 순서(-500, 500)는 드라이버 사이에 끼어들게 정했다. 같은 시나리오를 30/60/144 FPS와 두 틱 전략으로 600스텝 돌려 상태 해시(FNV-1a, float은 비트 패턴)가 일치함을 PlayMode 테스트로 확인했다.

**배운 점**
- 엔진이 순서를 보장하지 않는 곳에서는 "순서에 의존하지 않는 구조"(부작용을 모아 한 곳에서 정렬해 적용)로 바꾼다.
- 측정하려는 두 모드가 서로의 비용에 섞이지 않게 하려면 모드 전용 코드는 모드 전용 컴포넌트에 둔다.

## 2. 검토했으나 채택하지 않은 대안

"트레이드오프를 알고 선택했다"를 보이기 위한 절이다. 각 항목은 대안 이름, 검토한 이유, 채택하지 않은 근거다.

### 2.1 sweep and prune

- **검토한 이유**: Box2D·Bullet의 broadphase로 실제로 쓰이는 기법이라, 몬스터 수백~수천 기의 충돌 후보 추림에 맞을 수 있다고 보았다.
- **채택하지 않은 근거**: 이 프로젝트의 질의는 국소 이웃 열거이지 전역 구간 집계가 아니다(도구와 문제의 모양이 다르다). 공간 해시는 O(1) 삽입·질의인데 sweep and prune은 로그 인자가 추가 비용이다. N이 400~2,000인 구간에서는 캐시 지역성이 복잡도보다 지배적이다. 적이 플레이어로 몰려드는 상황의 비용 증가는 본질적(실제로 가까운 쌍이 많음)이라 자료구조로 줄일 수 없어 게임 규칙(관통 0이면 조기 종료, 피해 판정 쿨다운)으로 다룬다. 세그먼트 트리/펜윅이 맞는 자리는 가중치 랜덤 뽑기(누적 합 + 이분 탐색)다.
- 출처: DECISIONS 2절 "공간 분할에 sweep and prune을 쓰지 않음".

### 2.2 터널링 방지를 위한 쌍별 검사

- **검토한 이유**: 고정 스텝에서 빠른 투사체가 작은 적을 통과(터널링)하지 않도록 JSON 로드 때 데이터를 검증하려 했다. 처음에는 모든 (객체, 상대) 쌍에 `(v_a + v_b)/60 <= r_a + r_b`를 검사하는 안, 그다음에는 단일 부등식(투사체 최대 속도 + 적 최대 속도 <= 투사체 반지름 + 최소 적 반지름)을 검토했다.
- **채택하지 않은 근거**: 쌍별 검사는 O(N x M)이라 데이터가 늘수록 커지고, 무기 하나를 추가할 때 기존 모든 몬스터와의 쌍을 신경 써야 해서 "코드 수정 없이 JSON만으로 추가"(F11)와 구조가 어긋난다. 경고도 쏟아진다. 단일 부등식은 최대 속도 몬스터와 최소 반지름 몬스터가 다른 개체일 수 있어 실재하지 않는 조합으로 멀쩡한 데이터를 거부한다. 그래서 객체별 불변식 `v/60 <= r`(어떤 객체도 한 스텝에 자기 반지름보다 멀리 이동하지 않는다)로 교체했다. 모든 객체가 각자 불변식을 만족하면 모든 쌍이 안전하다는 점이 근거이고, 새 데이터를 추가할 때 그것만 검사하면 된다. 충분조건이지만 필요조건은 아니라서, 1단(객체별 O(N))을 통과하지 못한 객체만 2단에서 실제 상대와 쌍별 검사한다. 런타임 보정도 채택하지 않았다(검증에서 막지 않고 경고만 한다).
- 출처: DECISIONS 4절 "Q35. 터널링 처리".

### 2.3 ScriptableObject (JSON 대신)

- **검토한 이유**: 에디터에서 프리팹·스프라이트를 직접 참조로 물릴 수 있어 "코드 수정 없이 추가"를 가장 깔끔하게 만족한다.
- **채택하지 않은 근거**: 빌드 후 편집이 불가능해 "빌드된 게임에서 데이터 파일만 편집해 추가"라는 시연을 할 수 없다. 그래서 `StreamingAssets`의 JSON을 택했다. 대가로 파서 연동, 에셋 키 레지스트리, 스키마 검증을 직접 만든다.
- 출처: DECISIONS 8절 "PRD#21. 데이터 형식".

### 2.4 Development Build 전용 개발자 모드

- **검토한 이유**: 스크립팅 심볼로 컴파일을 분리하면 코드 자체가 없어 "꺼져 있으면 동일 동작"을 가장 강하게 충족한다.
- **채택하지 않은 근거**: 배포 빌드 하나로 플레이·측정·JSON 핫 리로드 시연을 모두 할 수 없다. 그래서 릴리스 빌드에도 포함하고 `--dev` 인자로 활성화하는 쪽을 택했다(비활성 상태에서는 시작 시 인자 확인 1회 외에 분기도 키 감시도 없다). 대가로 동일 동작은 코드 부재가 아니라 측정(인자 없는 릴리스 빌드 대 `SURVIVOR_NO_DEV` 빌드의 3분 플레이 3회 Profiler 비교)으로 보인다. 숨은 키 조합을 비활성 상태에서 매 프레임 감시하는 안은 그 감시 비용이 릴리스 경로에 남아 채택하지 않았다.
- 출처: DECISIONS 9절 "Q40. 개발자 모드 활성화와 릴리스 포함", "코드 제거 빌드 비교 (`SURVIVOR_NO_DEV`)".

### 2.5 프레임 드랍 시 이동 거리 클램프

- **검토한 이유**: 프레임이 떨어졌을 때 한 번에 너무 멀리 움직여 투사체가 적을 통과하는 것을 막으려는 초기 안(PM 원안)이다.
- **채택하지 않은 근거**: 저프레임에서 투사체가 실제로 느려져 요구를 만족하지 못하고 증상만 가린다. 로직을 `FixedUpdate` 고정 스텝(1/60초)에서 돌리고 catch-up 상한을 3스텝으로 두면, 각 스텝의 dt가 항상 같아 동작이 프레임레이트와 무관해진다. 대신 저성능 구간에서 게임 시간이 느려지는 슬로모션을 의도적으로 허용한다. 재려는 것이 "한 스텝에 몇 ms"라 슬로모션은 측정에 영향이 없고 오히려 재현성에 도움이 된다.
- 출처: DECISIONS 1절 "고정 타임스텝 채택 (클램프 폐기)", "Q25. 스텝 간격·catch-up 상한·렌더 보간".

### 2.6 전략 조합 16가지 전수 측정

- **검토한 이유**: 4개 축의 끔/켬 조합을 모두 재면 상호작용을 빠짐없이 볼 수 있다.
- **채택하지 않은 근거**: 비용이 폭발하고 해석이 어렵다. 6회(전부 끔 1회, 전략별 단독 4회, 전부 켬 1회)로 단독 기여의 합과 "전부 켬"의 실제 값을 비교해 상호작용을 본다. 공간 분할(F16)과 자체 충돌 판정(F18)이 구조를 공유하므로 상호작용은 실제로 존재한다. 이 6회를 400기 고정이 아니라 기준선이 버거워지는 지점 N*에서 돌리는 것도 같은 논리다(400기는 게임플레이 상한일 뿐이라 모든 전략이 여유롭게 돌면 차이가 노이즈에 묻힌다).
- 출처: DECISIONS 2절 "Q15. 전략 비교 6회", "Q32. 끔/켬 정의와 측정 구성".

### 2.7 궤도·장판만 `Collider2D`로 두고 세 판정만 자체 구현

- **검토한 이유**: 처음에는 투사체-몬스터, 플레이어-몬스터, 젬-플레이어 세 판정만 자체 구현하고, 개수가 몇 개뿐인 궤도·장판은 `Collider2D`를 유지하는 안이었다.
- **채택하지 않은 근거**: 궤도·장판은 몬스터와 충돌하므로 판정을 `Collider2D`에 맡기면 몬스터 400마리가 전부 Collider를 유지·갱신해야 한다. 궤도가 몇 개인지는 무관하다. 그러면 객체당 유지 비용과 `Physics2D` 시뮬레이션이 남아 자체 판정의 이득 큰 부분이 사라진다. "개수가 몇 개뿐이라 이득이 작다"는 근거는 판정 쌍의 상대편(몬스터 400기)을 보지 않은 오류였다. 그래서 다섯 판정을 전부 자체 구현하고(원-원 판정 함수 하나로 끝낸다), 몬스터 Collider는 엔진 충돌 전략과 `Physics2D` 쿼리 전략일 때만 켜는 토글 구조로 두었다.
- 출처: DECISIONS 4절 "Q23. 자체 충돌 판정 범위".

### 2.8 고정 크기 맵과 경계 차단

- **검토한 이유**: 공간 해시 격자를 맵 크기에 맞춰 고정 배열로 둘 수 있어 단순해 보였고, 경계로 이탈을 막는 것이 일반적이다.
- **채택하지 않은 근거**: 플레이어는 10분간 총 3,000유닛을 이동하므로 어떤 유한 맵이든 경계에 닿는다. 공간 해시는 애초에 무한 좌표를 다루고, 경계가 필요한 고정 배열 격자가 더 단순하지도 않다. 그래서 경계 없는 무한 평면으로 하고, 디스폰 거리 D가 경계 역할을 대신한다.
- 출처: DECISIONS 5절 "맵 구조: 경계 없는 무한 평면".

### 2.9 자동 진화

- **검토한 이유**: 조건(무기 5단계 + 패시브 보유)을 채우는 순간 진화시키면 구현이 단순하다.
- **채택하지 않은 근거**: 적 수백 마리와 투사체가 깔린 화면에서 진화가 조용히 일어나 플레이어가 눈치채지 못할 가능성이 크다. 상자 경유 진화는 "획득 순간"을 만들어 1~2분 시연 영상에서 조합 시스템을 보여줄 장면이 된다. 상자 수도 충분하다(보수적으로 1,500~2,500 처치로 봐도 상자가 30~50개).
- 출처: DECISIONS 6절 "Q10. 진화 발동 방식".

### 2.10 UI Toolkit

- **검토한 이유**: 신규 UI의 권장 기술이라 처음 TECH 1회차에서 선택했다.

### 3.1 F9 오브젝트 풀 전략 A/B/C

**가설**
- B(생성·파괴)는 요청과 반환마다 객체를 할당·해제한다. 그래서 GC로 인한 간헐적 프레임 스파이크가 생기고, 평균보다 1% low(최악 프레임 시간)가 더 나빠질 것이다.
- A(자체 풀)와 C(Unity 내장 풀)는 둘 다 재사용 구조여서 정상 상태에서 할당이 거의 없다. 따라서 1% low는 B보다 좋고, A와 C끼리는 차이가 작을 것이다.
- C는 `collectionCheck: true`라서 반환할 때마다 검사 비용이 든다. 이 비용이 반환이 많은 구간에서 A와 C의 차이로 드러나는지 본다. 검사 비용의 크기는 아직 재지 않았다.

**측정 방법**: 프리셋 A1(풀 B, 생성·파괴, 기준선), A2(풀 A, 자체 풀), C1(풀 C, Unity 내장 풀)을 N*에서 비교한다. 주요 열은 `avgFps`, `onePercentLowFps`, `worstFrameMs`, `gcAllocPerFrameBytes`, `pool_msPerStep`, `memTotalUsedMB_avg`/`max`다. 풀링은 GC 할당을 줄이는 대신 메모리를 미리 점유하므로 메모리 열을 함께 본다.

**사전 실측(구현 단계, Unity 6000.3.28f1, batchmode PlayMode 테스트)**: 측정이 아니라 동작 확인이다.
- B에서 `Destroy`는 1프레임 뒤에 적용됐다. 같은 프레임 안에서는 객체가 남아 있지만 먼저 비활성화했기 때문에 활성 객체 검색에 잡히지 않아, 같은 프레임의 다음 스텝에 간섭하지 않는다.
- `collectionCheck: true`에서 중복 반환하면 `InvalidOperationException`이 난다. `false`에서는 예외 없이 같은 객체가 두 번 쌓인다. 풀에서 나오지 않은 객체의 반환은 `true`여도 받아들여진다. `maxSize: int.MaxValue`에서는 반환한 1000개가 모두 보관되고 파괴는 0회다.
- 재사용 순서(같은 획득·반환 시퀀스): A는 `0,1,2,0,1,3,3,1`(LIFO), C는 `0,1,2,1,0,3,2,3`이었고 두 전략 모두 반복 실행에서 결과가 같았다.

| 프리셋 | avgFps | onePercentLowFps | worstFrameMs | gcAllocPerFrameBytes | pool_msPerStep | pool_msPerFrame | memTotalUsedMB_avg | memTotalUsedMB_max |
|---|---|---|---|---|---|---|---|---|
| A1 (B 생성·파괴) @ N 1200 | 60.3 | 25.4 | 48.0 | 63,418 | 0.26 | 0.26 | 1,708 | 1,773 |
| A2 (A 자체 풀) @ N 1200 | 81.4 | 32.3 | 38.9 | 52,655 | 0.11 | 0.08 | 1,617 | 1,700 |
| C1 (C Unity 내장 풀) @ N 1200 | 77.2 | 31.1 | 38.2 | 53,266 | 0.11 | 0.09 | 1,696 | 1,768 |

**결과**: N 1200, 3600스텝, 라벨별 마지막 유효 행(`docs/measurements/final-rows.csv`).
- 풀 마커는 생성·파괴 0.26ms/스텝, 자체 풀 0.11, Unity 내장 풀 0.11이다. 자체 풀과 내장 풀의 마커 값은 같다.
- 평균 FPS는 60.3(A1) → 81.4(A2) → 77.2(C1), 1% low는 25.4 → 32.3 → 31.1이다.
- 프레임당 GC 할당은 63,418B(A1), 52,655B(A2), 53,266B(C1)다. 풀링으로 약 1만 바이트(약 17%)가 줄었을 뿐 5만 바이트대가 남는다.

**해석**: 가설 중 "B(생성·파괴)가 1% low에서 더 나쁘다"와 "A와 C는 서로 차이가 작다"는 맞았다. 1% low가 B 25.4에서 A 32.3, C 31.1로 좋아졌고, A와 C의 풀 마커는 0.11ms로 같다(FPS는 A가 4.2 높지만 3.5절의 측정 편차 안이다). "A와 C가 정상 상태에서 할당이 거의 없다"는 틀렸다. 풀링 뒤에도 프레임당 5만 바이트대 할당이 남았고, 이는 풀 밖의 요인이다. 원인은 미확인이며 3.5절에서 다룬다. 풀링이 메모리를 더 점유한다는 우려는 이 측정에서 보이지 않았다(A2·C1의 평균이 오히려 낮거나 비슷하다). `collectionCheck: true`의 검사 비용은 풀 마커에 A와 C의 차이로 드러나지 않았다. 별도로 재지 않았으므로 크기는 모른다.

### 3.2 F16 타깃 탐색: 전수 순회 vs 공간 해시 vs Physics2D 쿼리

**가설**(측정 전, 검증되지 않음)
- 교차점: 전수 순회(A)는 질의 1회에 모든 몬스터를 본다(O(N)). 공간 해시(B)는 질의점 주변 몇 개 셀만 보지만, 스텝마다 해시를 다시 짓는 고정 비용(O(N) 삽입 + 사전 조작)이 있다. 그래서 N이 작을 때는 A가, N이 커지면 B가 유리하고 그 사이 어딘가에 교차점이 있다고 예상한다.
- 교차점을 정하는 요인은 스텝당 무기 질의 수(질의가 많을수록 재구축 비용이 나뉘어 교차점이 작아진다)와 셀당 평균 몬스터 수(디스폰 D=45 덕분에 일반 몬스터가 플레이어 중심 반경 45 안에 있어 분포가 일정하다)다.
- 셀 크기 2.0: 해시에 들어가는 일반 몬스터의 반지름 상한은 1.0이다(그보다 크면 해시에서 빠진다). 지름 2.0인 셀이면 최근접 후보가 대개 고리 0~1 안에서 확정된다. 셀이 더 작으면 빈 셀 순회가, 더 크면 셀당 후보 수가 늘 것으로 본다.
- 보스를 해시에서 뺀 이유: 셀 크기를 보스에 맞추면 일반 몬스터 조회가 비효율적이 되고, 보스는 1마리라 전수 검사 비용이 거의 없다.
- C(`Physics2D` 쿼리)는 묶음 C(프리셋 C2)에서 N*에 대해 측정한다.

**측정 방법**: 스케일링 곡선 B1~B8(적 50/100/200/400 x {전수 순회, 공간 해시})로 두 곡선과 교차점을 찾고, A3(공간 해시만 켬) 대 A1(기준선)로 N*에서의 단독 효과를 본다. C2는 `Physics2D` 쿼리 대 내 구현을 비교한다. 셀 크기는 헤더 `cellSize`에 남는다(기본 2.0, 개발자 모드에서 다음 판부터 변경).

**해석**: "N이 커지면 공간 해시가 유리하고 그 사이에 교차점이 있다"는 가설은 **이 범위에서는 틀렸다**. N 400까지는 전수 순회도 질의 비용이 마이크로초 단위라 병목이 아니고, 공간 해시는 재구축 비용만큼 같거나 조금 더 든다. N 1200에서도 해시의 이득은 targeting 0.003 → 0.001ms로 미미하고 인덱스 0.14ms가 더 든다. 공간 해시의 가치는 타깃 탐색이 아니라 **충돌 후보 추림**(3.4절: 같은 0.14ms 인덱스로 충돌 비용이 2.3ms 줄었다)에 있다. 가설의 교차점 요인(질의 수, 셀당 평균 몬스터 수)과 "셀 크기 2.0이 적당하다"는 판단은 이 측정으로 확인하지 못했다. 셀 크기를 바꿔 돌려 보지 않았다. 반면 `Physics2D` 쿼리(C2)는 전수 순회의 약 160배(0.485 대 0.003ms)이고 평균 FPS가 54.9로 55 아래다. 엔진 질의는 이 용도에서 내 구현보다 확실히 비쌌다.

### 3.3 F17 고정 스텝과 호출 오버헤드: 객체별 FixedUpdate vs 중앙 틱

**가설**(측정 전)
- 객체별(A)은 엔티티마다 Unity 네이티브에서 관리 코드로 `FixedUpdate` 호출이 1회씩 든다. 중앙(B)은 그룹당 1회 호출 안에서 인터페이스 호출 N회로 끝난다. 따라서 N이 클수록 중앙이 유리하고, 차이는 N에 대략 비례할 것으로 예상한다.
- 객체별은 스텝 밖 프레임에서도 활성 티커마다 호출이 일어난다. 게이트가 닫혀 있어 첫 줄에서 반환하지만 호출 비용은 남는다. 그래서 일시정지 중에도 객체별의 프레임 비용이 중앙보다 높을 것으로 예상한다.
- catch-up 프레임(스텝 3회)에서는 객체별의 호출 횟수가 3N이 되어 차이가 커질 것이다.
- 소수(N이 수십 이하)에서는 차이가 측정 잡음 안에 묻힐 것이다.
- 중앙의 등록·해제는 슬롯을 null로 비우고 다음 `RunGroup`에서 압축하므로 O(1) + O(N)이다. 객체별의 등록·해제는 `enabled` 토글이라 Unity 내부 목록 갱신 비용이다. 대량 디스폰 스텝의 Lifecycle 비용은 어느 쪽이 클지 판단하지 못했다.

**측정 방법**: A4(Update만 켬, 중앙 틱) 대 A1(기준선, 객체별 `FixedUpdate`)을 N*에서 비교한다. 측정 지점은 프로파일러 마커 `Survivor.Tick.Monsters`(Early에서 열고 Mid에서 닫음)와 `Survivor.Tick.Projectiles`(Mid에서 열고 Late에서 닫음)이며, 객체별과 중앙을 같은 마커로 비교할 수 있다. 주요 열은 `tickMonsters_msPerStep`, `tickProjectiles_msPerStep`, `slowmoFrames`(스텝 3회 프레임 수)다.

**구현 검증(실측, 측정이 아님)**: 몬스터·투사체 약 84개, 600스텝 시나리오에서 두 틱 전략의 상태 해시가 모두 같았다. 성능 수치는 없다.

### 3.4 F18 충돌 판정: 자체 제곱거리 vs 엔진 `Collider2D`, 이벤트 동등성 E1·E2

**가설**(측정 전, 작성자가 결정 문서에서 정리한 것이며 검증되지 않음)
- 엔진판은 몬스터 Collider 유지·갱신과 `Physics2D` 시뮬레이션 비용이 든다. 자체판은 공간 해시로 후보를 추려 원-원 판정(제곱거리 비교)만 한다. 그래서 몬스터 수 N이 클수록 자체판이 유리할 것이다.
- 자체 충돌 판정은 F16 공간 해시를 후보 추림에 재사용하므로 두 전략은 독립이 아니다. "전부 켬"(A6)이 단독 기여의 합보다 작거나 크면 그 차이가 상호작용이다.
- 엔진판은 "Box2D 후보 + R5 정확 좁은 판정"이므로(1.2), 스텝당 추가 비용은 후보 쌍 수(보통 수십~수백)만큼의 제곱거리 비교이고 넓은 판정·바디 동기화 비용은 그대로다. 전략 비교의 취지(엔진 물리 대 자체 격자)는 유지된다.

**측정 방법**: A5(충돌만 켬, 자체 제곱거리) 대 A1(기준선, 엔진 `Collider2D`)을 N*에서 비교하고, A6(전부 켬)로 상호작용을 본다. 엔진판 CCD는 끈 상태로 비교한다(비교 실험은 CCD Discrete). 주요 열은 `collision_msPerStep`, `collision_msPerFrame`, `avgFps`, `ccdMode`다.

**동등성 검증**: 같은 시나리오(타깃은 공간 해시, 3,600스텝)를 두 전략으로 돌려 충돌 이벤트 로그를 (스텝, 채널, A, B, 종류) 집합으로 비교한다. 로그는 개발자 모드의 `Collision log (next run)`로 만든다.
- **E1**: 자체(`Self`)와 `Engine/Discrete`를 비교한다. 다르면 첫 불일치 스텝과 두 바디의 거리·반지름 합을 출력한다. 골격 실행(웨이브 3)에서는 3배치 이벤트 집합이 일치(1688/1553/1387건)했다. 엔진판은 "순변화 필터" 뒤의 결과였다. 필터 없이는 이번 스텝에 등록된 바디가 상대의 직전 위치와 겹칠 때 가짜 Enter/Exit가 남아 불일치했다. 이후 R5 게이트(1.2)를 넣은 뒤에도 3배치가 같아야 한다.
- **E2**: `Engine/Discrete`와 `Engine/Continuous`를 같은 방식으로 비교한다. 트리거에는 CCD가 적용되지 않아 자명하게 같다는 것이 실측(U6)으로 확인되었고, E2 골격 2배치에서 이벤트 집합이 일치했다. 본 실행에서 같은 결과를 한 번 더 받아 기록한다.

"공유 구조라 전부 켬이 단독 합과 같지 않다"는 3.5절에서 다룬다. 공유 `MonsterSpatialIndex` 비용은 A3·A5·A6에서 모두 0.14ms이고 A6에서 두 번 들지 않았다. 설계대로 유지 비용은 한 번만 든다. E1은 자체판과 엔진판(R5 정확 판정 뒤)의 이벤트 집합이 본 실행에서도 같음을 확인했다. - **전략 효과(N 1200, 스텝당 ms)**: 충돌 엔진 2.63~2.78 대 자체 0.46, 풀 생성·파괴 0.25~0.26 대 자체 풀 0.11(= Unity 내장 풀 0.11), 틱 객체별 0.51~0.53 대 중앙 0.23~0.24, 타깃 전수 0.003 ≈ 공간 해시 0.001 + 인덱스 0.14 대 `Physics2D` 쿼리 0.485.
- **상호작용**: 전부 켬 A6는 스텝 6.17ms로 기준 A1의 9.00ms보다 2.83ms 짧다. 마커 기준 단독 변화의 합은 풀 -0.15, 타깃 +0.14(인덱스 비용 추가), 틱 -0.28, 충돌 -2.32로 -2.61ms이고, A6의 마커 합 변화 -2.62ms와 거의 같다(가산적). 스텝 기준으로는 단독 변화의 합이 A2 -0.46, A3 -0.19, A4 -0.53, A5 -2.34로 -3.52ms인데 A6 실측은 -2.83ms라 0.69ms 차이가 난다. 마커 밖 비용(5.44ms, 분리 패스 추정)이 조합마다 다르게 움직인 것으로 보이지만 원인은 미확인이다. 평균 FPS는 A1 60.3에서 A6 89.5로 올랐다.
- **55 FPS 경계(추정, 조합별 N 스윕 + 보간)**: 기준 A1 약 1,250, 전부 켬 A6 약 1,450(N 1400에서 59.3), `Physics2D` 쿼리 C2 약 1,200(N 1200에서 54.9). 조합별 N 스윕 전체는 `docs/measurements/README.md` 표 3에 있다.
- **마커 밖 비용**: A1 @ N 1200에서 스텝 9.00ms 중 프로파일러 마커 6개의 합이 3.57ms라 **스텝당 5.44ms가 마커 밖**이다.
- **GC와 젬**: 프레임당 GC 할당은 A0 스윕에서 N 200 약 10KB, 800 약 13KB, 1200 약 62KB, 1800 약 90KB다. 활성 젬 평균은 136 → 1,128 → 1,415 → 2,374로 늘었다.
- **측정 편차**: 같은 조합(전부 끔, N 1200)이 A0에서는 66.7 FPS, A1에서는 60.3 FPS로 나왔다.

**해석**
- 종합 가설 1("N\*가 존재하고 그 지점에서 전략 효과가 가장 선명하다")은 N\*(1400)가 존재했다는 부분만 맞았다. 효과를 보는 N은 N\*가 아니라 그 직전의 1200으로 옮겼다(1400에서는 기준이 이미 한계 아래). N\*에서 효과가 가장 선명한지는 N 1400의 A·C 비교를 하지 않아 확인하지 못했다.
- 종합 가설 2("A6 ≠ 단독 합")는 **약하게만 성립**한다. 마커 기준으로는 단독 합 -2.61ms 대 A6 -2.62ms로 가산적이고, 스텝 기준으로는 -3.52ms 대 -2.83ms로 0.69ms(스텝 9.00ms의 약 8%)가 어긋난다. 마커 안의 효과는 단독 효과의 합으로 설명되고, 어긋남은 마커 밖 비용에 있다. 각 조합이 1회 측정이라 정량 판정은 미확정이다. 가장 큰 항은 충돌(-2.32ms)이다. 공간 해시는 타깃 탐색에서는 순손해(+0.14ms)였지만 자체 충돌과 인덱스를 공유해 그 투자가 충돌에서 회수된다(3.2절).
- **측정 편차**: 같은 조합이 N 1200에서 66.7 FPS(A0)와 60.3 FPS(A1)로 약 10% 갈렸다. 그래서 FPS의 작은 차이(예: A3 66.8, A4 70.8)는 전략 효과로 읽기 어렵고 스텝당 ms 합계도 마커 합과 잘 안 맞는다(A3는 인덱스 비용이 늘었는데 스텝 합계는 0.19ms 줄었다). 전략 효과는 마커별 ms를 우선하고, FPS는 큰 차이(A5·A6, A2, C2)만 근거로 쓴다. 편차의 원인(에디터 상태, 젬 수 등)은 확인하지 못했다.
- **내 구현 대 엔진 제공(C)**: 풀은 내 구현(0.11ms)과 Unity 내장 풀(0.11ms)이 같았다. 타깃 탐색은 내 구현이 `Physics2D` 쿼리보다 낫다(0.003 대 0.485ms).
- **마커 밖 5.44ms(추정, 미확인)**: 원인을 몬스터 분리 패스(`MonsterSeparation`, `BuildIndex` 순서 -10, 전수 O(n^2): 1200기면 스텝당 719,400쌍)로 **추정**한다. Profiler로 확인하지 않았다. 다음 최적화 후보: 분리 패스를 전용 마커로 재서 비용을 확인한다.
- **GC 증가와 젬(원인 미확인)**: GC 할당이 N 200의 약 10KB에서 N 1200의 약 62KB로 늘 때 활성 젬도 136개에서 1,415개로 늘었다. 젬 부하가 전략 비교를 가렸을 가능성이 있지만 원인은 확인하지 못했다. 다음 최적화 후보: 젬 디스폰 규칙을 둘지 판단한다(SPEC F10 83행의 판단 지점).
- 개발자 모드 오버헤드 비교(F19)와 빌드 3종 측정은 아직 하지 않았다.
