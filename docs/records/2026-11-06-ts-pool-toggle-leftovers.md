## 문제

풀 전략(A 자체 풀 / B 생성·파괴 / C Unity 내장 풀)은 개발자 모드 토글 뒤 다음 판 시작에서 바뀐다(TAC-F9-7). 판 경계 흐름은 "활성 객체 전부 반납(`DespawnAll`) → 전략 교체(`ReplaceStrategies`) → 새 풀 예열(`Prewarm`)"이다. 이때 옛 A·C 풀이 쥐고 있던 **비활성 인스턴스**는 아무도 치우지 않는다. 반납된 객체는 옛 풀 안에 비활성으로 남고, C# 전략 객체를 버려도 그것이 만든 GameObject들은 씬 계층에 그대로 있다. 예열 수량이 카테고리 합계 약 1,500개(Q13: Monster 450, PlayerProjectile 300, EnemyProjectile 100, PlayerOrb 16, PlayerZone 16, EnemyZone 8, Gem 600, Chest 16)라서 토글 한 번마다 그만큼 쌓인다.

관찰 가능한 증상(예상): 계층 창의 비활성 객체 수가 토글마다 약 1,500씩 증가, 프로파일러 메모리 증가. 비활성 객체는 CPU를 거의 쓰지 않으므로 프레임 시간에는 바로 드러나지 않는다 — 그래서 측정(F10)을 토글하며 반복할 때 조건이 조금씩 달라지는 조용한 오염이 된다.

## 원인

`IPoolStrategy`(Core, TECH 5.6)가 "활성 객체 반납(`ReleaseAll`)"만 정의하고 **풀이 만든 객체의 수명 종료**를 빠뜨렸다. Unity에서는 C# 객체 수명(전략 인스턴스가 GC 대상이 되는 것)과 씬 객체 수명(GameObject는 `Destroy`해야 사라짐)이 다르다. 교체 가능한 전략 패턴을 설계할 때 "생성"만 인터페이스에 올리고 "정리"를 빠뜨린 것이다. 코드 리뷰(웨이브 2a 구현자 보고의 미확정 항목)에서 발견됐고, 테스트는 단일 전략 안의 동작만 검사해 잡지 못했다.

## 해결

`IPoolStrategy`에 `void Clear();`를 추가했다. 의미는 "이 전략이 보유한 비활성 인스턴스를 전부 파괴한다". A는 템플릿별 스택을 비우며 파괴, C는 `ObjectPool.Clear()`(파괴 콜백), B는 할 일 없음. 활성 인스턴스가 남아 있으면 `InvalidOperationException`을 던져 호출 순서(`DespawnAll` 먼저)를 강제한다. LOOP의 `EntityLifecycle.ReplaceStrategies`는 풀 객체가 바뀔 때 `DespawnAll` → 옛 풀 `Clear()` → 새 풀 `Prewarm` 순서로 부른다.

검토했으나 채택하지 않은 대안:
- **App이 씬을 검색해 정리**: 전략 교체 때 비활성 `PooledObject`를 전부 찾아 파괴. 인터페이스는 그대로지만 풀 내부 상태와 씬 상태가 어긋난다(Unity 내장 풀은 파괴된 객체 참조를 계속 보관) + 씬 전체 검색 비용.
- **누적 허용 + 운영 규칙**: 측정 때 토글 뒤 게임을 재시작. 코드 변경은 없지만 사람이 지켜야 하고 "알려진 한계"로만 남는다.

## 배운 점

- 교체 가능한 전략(Strategy 패턴)은 **생성과 정리를 한 쌍으로** 인터페이스에 둔다. `IDisposable`을 붙이는 것과 같은 이유다.
- Unity에서 "객체를 버린다"는 두 가지다: C# 참조를 놓는 것과 `Destroy`하는 것. 풀처럼 GameObject를 만들어 쥐는 객체는 두 번째를 책임져야 한다.
- 단일 전략의 단위 테스트는 **전략 교체 경계**의 결함을 못 잡는다. 교체 시나리오(A→C→A) 테스트를 LOOP 조립 테스트에 넣는다.

## 보강할 실측 (LOOP·App 뒤)

- 토글 A→C→A→C 4회 뒤 씬의 비활성 `PooledObject` 수와 `Profiler.GetTotalAllocatedMemoryLong()` — `Clear()` 전(이론상 약 6,000개 누적)과 후(약 1,500개 유지) 비교. 수치가 들어가면 이 항목이 "겪은 문제"가 된다.
- `Clear()` + `Prewarm` 비용(판 경계 1회, ms) — 측정 세션 밖이라 F10에는 들어가지 않음을 확인.
