## README 쪽 요약

```markdown
### F16 타깃 탐색 전략
- 무기의 "가장 가까운 적" 질의를 `ITargetProvider` 뒤로 분리했다. 몬스터는 이 질의를 쓰지 않고 플레이어 위치를 직접 읽는다.
- 구현 A `BruteForceTargetProvider`: 전수 순회. 측정 대조군이고 출하용이 아니다.
- 구현 B `SpatialHashTargetProvider`: `MonsterSpatialIndex`(공간 해시, 셀 키 R14) 위에서 고리 탐색을 하고, 큰 몬스터(보스 포함, R25)는 해시 밖 목록으로 전수 검사한다.
- 구현 C `Physics2DTargetProvider`: 웨이브 3으로 이월했다(충돌 구현의 `PhysicsBodySynchronizer`에 의존한다).
- 결정론: A와 B 모두 BuildIndex 스냅샷 위치와 `TargetOrdering.IsBetter`(제곱거리 → ID)로 고른다. EditMode 동등성 테스트에서 반환이 비트 단위로 같았다. 무작위 10,000배치, 격자 동거리 8배치, 큰 몬스터 포함 1,000배치에 셀 크기 4종을 썼다.
- 셀 크기 기본값은 2.0이다(`StrategySelection.DefaultSpatialHashCellSize`). 개발자 모드에서 다음 판부터 바꿀 수 있고 측정 헤더 `cellSize`에 남는다.
- Spatial EditMode 테스트 68건은 전체 스위트 연속 3회에서 모두 통과했다.
```

## devlog 쪽 초안

```markdown
## [측정] F16 타깃 탐색: 전수 순회(A) vs 공간 해시(B)
**가설** (측정 전, 검증되지 않음)
- [가설] 교차점: A는 질의 1회에 모든 몬스터를 본다(O(N)). B는 질의점 주변 몇 개 셀만 보지만, 스텝마다 해시를 다시 짓는 고정 비용(O(N) 삽입 + 사전 조작)이 있다. 그래서 N이 작을 때는 A가, N이 커지면 B가 유리하고, 그 사이 어딘가에 교차점이 있다고 예상한다.
- [가설] 교차점을 정하는 요인: 스텝당 무기 질의 수(질의가 많을수록 재구축 비용이 나뉘어 교차점이 작아진다), 셀당 평균 몬스터 수(디스폰 D=45 덕분에 일반 몬스터가 플레이어 중심 반경 45 안에 있어 분포가 일정하다).
- [가설] 셀 크기 2.0: 해시에 들어가는 일반 몬스터의 반지름 상한은 1.0이다(그보다 크면 R25로 해시에서 빠진다). 지름 2.0인 셀이면 최근접 후보가 대개 고리 0~1 안에서 확정된다. 셀이 더 작으면 빈 셀 순회가, 더 크면 셀당 후보 수가 늘 것으로 본다.
- 보스를 해시에서 뺀 이유: 셀 크기를 보스에 맞추면 일반 몬스터 조회가 비효율적이 되고, 보스는 1마리라 전수 검사 비용이 거의 없다(SPEC F16).

**구현 검증** (실측)
- A와 B의 반환(bool, Id, Position, DistanceSquared)이 비트 단위로 같다. 허용 오차는 쓰지 않았다.
  - 무작위 10,000배치: 질의 59,787건, 셀 크기 4종 비교 239,148건, 약 10.1~10.6초.
  - 격자 동거리 8배치: 질의 5,832건, 약 70ms.
  - 큰 몬스터 포함 1,000배치: 질의 9,000건, 0.39~0.79초.
- 무작위 배치가 오래 걸린 것은 셀이 작고(0.5) 몬스터가 성기며 질의점이 무리 밖인 경우에 B가 빈 셀을 많이 돌기 때문으로 보인다. 측정 시나리오(무리 안의 플레이어 위치에서 질의)와는 다른 조건이다.
- 고리 탐색 종료 조건에는 TAC-F16-2에 부동소수 반올림 여유를 더했다. 셀 배정 반올림 때문에 같은 거리이면서 ID가 더 작은 후보를 놓치지 않기 위해서다.

**결과** (사용자 측정 후 기입): N = 50/100/200/400에서 A·B 측정 CSV 경로, 두 곡선의 교차점 N*, 측정한 cellSize.
**해석** (사용자 측정 후 기입): 가설과 맞았는지, 셀 크기 변경 효과.
**C(Physics2D)**: 웨이브 3 이월. 묶음 C에서 N*에 대해 측정한다.
```
