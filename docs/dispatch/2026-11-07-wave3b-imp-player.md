- 로직에서 `Time.*`·`UnityEngine.Random`·`System.Random`·`DateTime` 금지(TAC-0-2). 시간은 `context.Step`·`long` 스텝, 속도는 스텝당 값(R1·R3 — 초 단위 상수가 코드에 나타나면 안 된다). 난수는 `RngStreams.Get(RngStream.Chest)`(상자 효과)만 — 레벨업 추첨(LevelUp 스트림)은 FLOW 몫이다.

- 쿨다운·무적·관통 기록은 `long` 스텝 번호 + `EntityHandle`(세대 포함) 키다(TAC-0-10). `EntityLifecycle.Despawned`를 구독해 대상 기록을 지운다(5c.3 #12) — 등록 해제는 Exit을 내지 않는다.

- **플레이어 등록 경로(16회차 A5', 5.12 `PlayerEntity` 계약 블록)**: `public sealed class PlayerEntity { Vector2 Position { get; } CollisionBody Body { get; } CollisionBody MagnetBody { get; } void RegisterForRun(ICollisionStrategy collisions, Vector2 position); void UnregisterFromRun(); }` — `RegisterForRun`은 `RunSession.Reset` ④에서 `EntityHandleAllocator.Reset()` 직후 호출되며 몸 → 자석 순으로 ID를 받아(1:1·2:1) `position`에 두고 `collisions`와 물리 레지스트리에 등록하고 `collisions`를 기억한다(이미 등록돼 있으면 `InvalidOperationException`, null은 `ArgumentNullException`). `UnregisterFromRun`은 ① 앞에서 두 바디를 해제하며 ID는 해제하지 않고(④에서 할당기 리셋), 등록돼 있지 않으면 아무것도 하지 않는다(첫 판). 할당기·물리 레지스트리·스탯 출처·`Host`는 생성자로 주입받는다(인자 구성은 당신이 정하고 ★로 보고). 플레이어는 풀 엔티티가 아니다(`EntityCategory`에 없음) — `EntityLifecycle.Spawn`을 타지 않고 몸 바디(`PlayerBody`, 반지름 `PlayerStatsDefinition.Radius`)·자석 바디(`PlayerMagnet`, 반지름 `PickupRadius`에 P3 적용)를 직접 만들어 `EntityHandleAllocator`에서 ID(1:1 → 2:1)를 받고 `ICollisionStrategy.Register`·`IPhysicsBodyRegistry.Register`에 등록한다(5c.3 #1의 명시적 예외). `Body.Host`에 `Rigidbody2D`·콜라이더를 **붙이지 않는다**(`PhysicsBodySynchronizer.Register`가 멱등으로 붙인다 — COLLISION 계약).
- **TAC(EM)**: F1-1~F1-4·F1-7(`KeyboardInputSource`는 LOOP가 만들었다 — 당신은 `IInputSource`만 호출), F2-1~F2-6(첫 보유 규약: `_nextFireStep = 보유가 적용된 스텝`, 네 경로), F3-12(최대 피해 1회, 동률은 작은 ID, 무적 중 M3 투사체는 피해 없이 `Despawn(Consumed)`), F4-4~F4-6(상자 효과 ①진화 → ②70/30, 강화 대상 목록 비면 회복, 상자 2개 순차), F6-1~F6-9, F7-1~F7-3, 0-1·0-2·0-6·0-10. 5a: R10·R13·R22·R23. 5c.3 #1~#12.
- **명령 규약(5.4)**: 무기 발사 결과물은 WeaponTick에서 **명령으로**(Source = 플레이어 ID 1:1, 슬롯 순서라 Sequence 결정적): `SpawnPlayerProjectile(position, direction, definitionId = 무기 ID, levelIndex, slotIndex)`, `SpawnPlayerOrb(…, orbIndex)`, `SpawnPlayerZone(position, …)`. 소모·교체 회수는 `Despawn(target, reason: Consumed|Replaced)`(Source = 소모된 엔티티 ID 또는 플레이어 ID). `PlayerSpawnCommandHandler`는 Lifecycle에서 `EntityLifecycle.Spawn<PlayerProjectile|OrbitOrb|DamageZone>(category, position, lifetimeSteps, init)` — 투사체 `LifetimeSteps`, 장판 `DurationSteps`, 궤도 원 **0**(수명 없음, TAC-F6-4 5회차).
- **5.9 채널 의미**: 채널 0 Enter 1회 = 피해 + `MarkConsumed` + `Despawn(Consumed)`(관통은 TAC-F6-9); 1·2 Enter/Exit = 소유 무기 인스턴스의 트래커 `OnEnter/OnExit`(궤도 원·장판은 자기 `SlotIndex`로 무기를 찾는다); 3·5 = 겹침 집합, 4 Enter = 일회성 후보 + 투사체 소모. `IsConsumed`인 엔티티의 뒤 이벤트는 무시(5.10).
- **로그(5c.3 #8)**: 진화·`SetLoadout`은 성공해도 `LoopLog.Info` 한 줄(Area `[Loop]` 재사용 — 영역별 internal 유지가 PM 확정). 스텝마다 로그 금지. 계약 위반은 `InvalidOperationException`, 인자 null은 `ArgumentNullException`, 예상 가능한 실패는 `bool Try…`(5c.3 #7).

### 5-B. PM 기본값 (문서에 없거나 모호한 곳 — 이렇게 하고, 더 나은 근거가 있으면 반박으로 올린다)

- **P1. `PlayerEntity`의 형태**: `MonoBehaviour`가 아닌 평범한 클래스(5.12 계약 블록은 `sealed class`)이며 `Position`·`Body`(1:1)·`MagnetBody`(2:1)·`Host`(두 바디가 공유하는 GameObject 1개, 생성자로 주입 — 부팅 때 1회 만들고 판마다 재사용)를 가진다. 시각 표현(SpriteRenderer)·transform 동기화는 **App(웨이브 4) 몫**이다 — 당신은 `Position`만 정확히 유지한다. 판 시작 위치는 `RegisterForRun`의 `position` 인자(App이 원점을 준다). 몸·자석 바디의 `Position`은 PlayerMove 단계에서 함께 갱신한다. P3 레벨업으로 자석 반지름이 바뀌면 `MagnetBody.Radius` 갱신 + 기억한 전략의 `NotifyRadiusChanged(MagnetBody)` — 엔진 전략은 이를 동기화기에 위임해 콜라이더 반지름을 맞춘다(COLLISION 계약), 자체 전략은 매 스텝 `Radius`를 읽는다. 다른 통지는 없다.
- **P2. `PlayerMovement`**: Begin order 10에서 `input.ReadMove(context.Step, player.Position)`을 **1회** 읽어 캐시하고, PlayerMove order 0에서 적용한다(같은 스텝에서 두 번 읽지 않는다 — U17 래치 전제). 스텝당 이동 = `MoveMath.ToUnitDirection` 방향(또는 `MoveCommand.Direction`이 이미 단위 벡터면 그대로) × 속도. 속도 = `StatMath.ApplyMultiplier(PlayerStats.MoveSpeedPerStep, P2 보너스)`; `SpeedOverride ≥ 0`이면 `StepMath`로 **스텝당 값으로 환산**해 쓴다(초당 값으로 들어온다). 위치 제한·보정 코드 없음(F1-4).
- **P3. `PlayerHealth`**: `Hp`·`MaxHp`(float, `PlayerStatsDefinition.MaxHealth`; 최대 체력은 판 시작에 1회 읽고 핫 리로드에 따라가지 않는다 — 5c.3 #10 "체력·최대 체력 제외")·`IsDead`(`Hp <= 0`)·`TakeDamage(amount)`(0 미만으로 내려가지 않게 클램프)·`Heal()`(R23 `ProgressionRules.ApplyHeal`)·`SetHp(hp)`(dev, `[0, MaxHp]` 클램프). 사망 판정의 소비자는 FLOW의 `StepOutcomeGate`(Lifecycle 90, `IsDead` 읽기) — 당신은 이벤트를 쏘지 않는다.
- **P4. `WeaponInventory`**(WeaponTick 0): 슬롯 4개(`GameRules.MaxWeaponSlots`) 고정 배열, 슬롯 순서로 `WeaponInstance.Tick`(발사·궤도 원 위치·자식 보정). 공개 조회: `Slots`(읽기 전용, null 허용)·`Owns(weaponId)`·`ConsumedByEvolution`(ID 집합, D5)·`TryGetSlot(index, out instance)`. FLOW의 `LevelUpCandidateBuilder`가 이 조회로 제외 규칙(TAC-F5-3)을 적용한다 — 후보 계산 자체는 FLOW다. `PassiveInventory`도 같은 꼴: 슬롯 3개, `Owns(id)`·`Level(id)`·`BonusOf(PassiveStat)`(보유 패시브의 현재 레벨 `Bonus` 합).
- **P5. `WeaponInstance`**: 생성 때의 `WeaponDefinition` 참조와 현재 `Level`(1부터)·`_nextFireStep`·행동 객체(`ProjectileWeapon`/`OrbitWeapon`/`ZoneWeapon`, `WeaponFactory`가 `Behavior`로 고른다)·트래커(궤도·장판만)를 가진다. 강화는 `Level + 1`과 트래커 `SetInterval`(W2·E2는 P1 적용 간격, W3는 정의값 그대로 — TAC-F2-3). 핫 리로드 뒤에도 생성 때의 정의를 유지한다(5.14 8회차).
- **P6. 궤도 원 위치의 원본**: `OrbitWeapon`이 WeaponTick에서 `θ_i = θ0 + ω·step + 2π·i/orbCount`로 계산해 **자기 `OrbitOrb`들의 `Position`을 직접 쓴다**(같은 어셈블리, `OrbitOrb`에 internal setter). `OrbitOrb`·`DamageZone`은 `IUpdatable`이 아니다(틱 전략에 등록되지 않음). `PlayerProjectile`만 `IUpdatable`(`TickGroup.Projectiles`): 직진(W1·E1) 또는 매 스텝 `Targets.TryFindNearest(자기 위치)` 재조준(W4, 대상 없으면 마지막 방향). 궤도 원이 가리키는 무기 슬롯은 `SlotIndex`·`OrbIndex`로 기억한다.
- **P7. `PlayerSpawnCommandHandler`가 정의를 얻는 곳**: 명령의 `SlotIndex`로 `WeaponInventory` 슬롯의 **현재 인스턴스 정의**를 쓴다(레지스트리 재조회 없음, 5c.3 #10). 슬롯 무기 ID가 명령의 `DefinitionId`와 다르면(같은 스텝에 교체됨) 그 명령은 **조용히 버리고** ★ `DroppedCommandCount`를 센다. `LevelIndex`로 `Levels[levelIndex]`를 읽는다.
- **P8. 채널 0 명중 처리(`PlayerHitHandler`)**: 이벤트 A = 투사체(`lifecycle.TryGet` → `PlayerProjectile`, 자기 타입), B = 몬스터(`damageables(e.B)`, null이면 무시). 투사체가 `IsConsumed`면 무시. 관통: 투사체가 "맞힌 ID 목록"(세대 포함)을 가지고 재피해를 막으며 `PierceCount + 1`회째 명중에서 `MarkConsumed` + `Despawn(Consumed, Source = 투사체 ID)`. 피해량 = 생성 때 받은 레벨 정의의 `Damage`(투사체가 보관). 이미 처치된(생존 아님) 몬스터에 대한 같은 스텝 추가 피해는 인터페이스 구현(MONSTER)이 무시하므로 당신은 그냥 부른다.
- **P9. 지속 피해(`WeaponDamageResolver`, Resolve 10)**: `Rules.WeaponsEnabled`가 거짓이면 `CollectHits`를 부르지 않는다(Enter/Exit 기록은 계속). 참이면 슬롯 순서로 각 트래커의 `CollectHits(step, list)`(ID 오름차순)를 모아 순서대로 피해를 적용한다. 피해량은 그 무기의 **현재 레벨** 정의 `Damage`(장판·궤도 원은 소유 무기 인스턴스의 현재 값을 읽는다 — 강화 즉시 반영) [기본값].
- **P10. `PlayerDamageReceiver`**(Resolve 20): 채널 3·5의 Enter/Exit으로 겹침 집합(정렬 목록)을 유지하고, 채널 4 Enter는 그 스텝의 일회성 후보 목록에 넣으며 **피해 적용 여부와 무관하게** `MarkConsumed` + `Despawn(Consumed, Source = 투사체 ID)` 명령을 넣는다(무적 중에도 소모, TAC-F3-12). Resolve에서 `Rules.PlayerTakesDamage && step >= InvulnerableUntilStep`이고 후보가 있으면 후보들의 피해량(`contactSources(id)?.ContactDamage`)을 읽어 최대값, 동률은 작은 ID 1회 적용 → `InvulnerableUntilStep = step + InvulnerabilitySteps`. 조회에 실패한(이미 사라진) 후보는 건너뛴다. `Despawned` 구독으로 겹침 집합에서 제거.
- **P11. 상자 효과(`ChestEffectResolver`)**: ① `EvolutionService.TryFindFirstEligible`이 참이면 `applier.ApplyEvolution(slot, rule, ctx)`, RNG 소비 없음 → `Evolved`. ② 아니면 `chestRng.Chance(GameRules.ChestUpgradeChance)`; 참이면 `IsWeaponUpgradable`인 보유 무기를 슬롯 순으로 나열해 `NextInt(count)`로 고른 뒤 `ApplyChestUpgrade(slot)` → `WeaponUpgraded`, 목록이 비면 `Heal()` → `Healed`; 거짓이면 `Heal()` → `Healed`. 호출자는 MONSTER의 `PickupSystem`이 생성자 델리게이트 `Action<DeterministicRng, StepContext> openChest`로 부른다(App이 `(rng, ctx) => resolver.Resolve(rng, ctx)`를 꽂고 반환값은 버린다) — 당신은 `Resolve` 메서드만 제공한다.
- **P12. 개발자 명령 핸들러**: `PlayerProgressionApplier`에 공개 메서드 `HandleSetLoadout(in PendingCommand, in StepContext)`·`HandleSetHealth(…)`(이름은 자유, ★ 보고)를 두고 조립 루트가 `PendingCommandQueue.RegisterHandler`로 꽂는다. `SetLoadout`의 `Payload`는 `IReadOnlyList<WeaponLoadoutEntry>`로 캐스트한다(다른 타입이면 `ArgumentException`). 적용 규칙은 5.14 A11: 빠진 무기의 자식은 `Despawn(Replaced)`, 새 무기는 첫 보유 규약(`_nextFireStep = context.Step`), 슬롯 순서 = 목록 순서, 4개 초과는 `ArgumentException`.
- **P13. 진화·레벨업 적용의 자식 정리**: `ApplyEvolution`은 원본 인스턴스의 활성 자식(궤도 원·장판) 전부에 `Despawn(Replaced)` 명령(Source = 플레이어 ID), 결과 무기 인스턴스는 `Level 1`·`_nextFireStep = context.Step`(교체 스텝). 원본 ID는 `ConsumedByEvolution`에 추가. `ApplyLevelUpOption`은 게이트 닫힘 중 호출되므로 `StepContext`가 없다 — "보유가 적용된 스텝"은 `clock.Step`(다음에 실행될 스텝)이고 자식 정리 명령은 **다음 스텝 WeaponTick에서 보정**(TAC-F6-8의 부족/과잉 보정 경로)으로 처리한다 [기본값]. 즉 게이트 중에는 명령을 넣지 않는다.
- **P14. 테스트 구성**: `SimEntity` 파생 실물(`PlayerProjectile`·`OrbitOrb`·`DamageZone`)은 Simulation(런타임 어셈블리) 타입이라 EditMode 테스트에서도 `PrefabCatalog`(세 카테고리만) + 실물 `EntityLifecycle`로 생성할 수 있다 — 2b의 제약은 **테스트 어셈블리 안에 정의한** `SimEntity` 파생 더블에만 해당한다. 풀·틱·충돌·물리 레지스트리는 `LoopEmDoubles`를 재사용하거나 당신 폴더의 최소 더블을 쓴다. 정의 객체는 `GameDataLoader.LoadFromTexts`로 만든다(JSON 문자열을 테스트에 둔다). `StepContext`는 생성자로 직접 만든다. EditMode에서 만든 GameObject는 `[TearDown]`에서 `Object.DestroyImmediate`.

### 5-C. 기준선 — 정상 동작인데 결함으로 오판하기 쉬운 것

1. `StepContext.PlayerPosition`은 Begin·PlayerMove 단계에서 **이전 스텝의 위치**다(드라이버가 PlayerMove 뒤에 다시 읽는다). 무기·충돌은 새 위치를 본다.
2. `TryFindNearest`는 몬스터가 없으면 false이고 던지지 않는다 — W1·W4·E1·`nearestEnemy` 장판은 그때 발사하지 않고 `_nextFireStep`을 그대로 둔다(TAC-F2-2). `placement: player` 장판은 타깃과 무관하게 생성한다(TAC-F6-5 9회차).
3. 생성 스텝에는 `Tick`이 오지 않는다(5.4) — 투사체의 첫 이동은 s+1이다. `Debug.Assert(ctx.Step > SpawnStep)`만 둔다.
4. 궤도 원은 `lifetimeSteps = 0`으로 생성하며 `LifetimeSystem`이 건너뛴다. 진화·강화 직후 궤도 원 개수 보정은 **다음 WeaponTick**이고 W2 → E2 공백은 정확히 1스텝이다(TAC-F7-2).
5. 등록 해제(디스폰)는 Exit을 내지 않는다 — 트래커·겹침 집합은 `Despawned` 구독으로 지운다. `Forget`을 빠뜨리면 죽은 대상이 겹침 집합에 남는다(2026-10-16 검토의 설계 버그 재발 금지).
6. `PlayerStatsDefinition.InvulnerabilitySteps`는 0일 수 있다(매 스텝 피해 가능). `MoveSpeedPerStep` 등 `…PerStep` 필드를 읽는다 — 초 단위 필드(`MoveSpeed`)를 읽으면 R3 위반이다.
7. `WeaponsEnabled == false`는 측정용 예외다: 발사·생성 명령과 지속 피해가 멈추고 궤도 원 위치 갱신·Enter/Exit 기록은 계속된다(TAC-F2-5).
8. 첫 배치 실행은 2~5분이다. 기존 테스트는 당신 변경 전에도 전부 통과한다.
9. `SimEntity.MarkConsumed`·`OrbitOrb` 위치 setter 같은 internal은 같은 어셈블리라 보인다 — 테스트 어셈블리에서는 보이지 않는다(`InternalsVisibleTo`는 Loop 테스트용 일부뿐, `SimulationAssemblyInfo.cs` 참조). 테스트에서 필요한 상태는 public 읽기 속성으로 노출한다.
10. test-framework 1.6: `LogAssert.ignoreFailingMessages`는 `[SetUp]`에서 켜도 본문에 이어지지 않는다 — 본문에서 켠다.
11. `IPhysicsBodyRegistry`에는 `Clear`가 없다 — 판 리셋 ②의 `ICollisionStrategy.Clear()`는 물리 레지스트리 등록을 지우지 않으므로 `UnregisterFromRun`이 ① 앞에 필요하다(16회차 [기본값]). 피해량·체력은 전부 `float`이다(정의가 float; 반올림 규칙 없음).
