## §2 IMP-PLAYER (1단계)

### 2.2 이미 확인된 사실 (origin/main a501bd8)
- `ChestEffectResolver.Resolve(DeterministicRng, in StepContext)`(`ChestEffectResolver.cs:27~66`) 반환 경로 4개: 진화 / 회복(확률) / 회복(후보 없음) / 강화. `enum ChestEffect { Evolved, WeaponUpgraded, Healed }`는 **그대로**(패시브는 웨이브 7). `PlayerProgressionApplier.Heal()`은 현재 `void`(137행), 호출부는 레벨업 `case UpgradeKind.Heal: Heal();`(87행)과 리졸버 둘, 둘 다 문장 호출. 테스트에 `Heal`을 `Action`으로 넘기는 곳이 있는지는 **미확인** — 있으면 당신이 고친다.
- `PlayerProjectile.Tick` 45행 `if (IsHoming && context.Targets.TryFindNearest(Position, out TargetHit hit))` — 성공 분기에 `LastTargetId = hit.Id;` 1줄, `Initialize`(57~70행)에 `LastTargetId = default;` 1줄. 분기 추가 없음. W1·E1은 `projectile`(유도 아님)이라 쓰지 않는다. W4만 `homing`.
- `SetLoadout`(`PlayerProgressionApplier.cs:146~206`)은 **슬롯 = 목록 위치 전체 교체**. 같은 슬롯·같은 ID면 인스턴스 유지 + `SetLevel`, 아니면 자식 `Despawn(Replaced)` 뒤 새 인스턴스. `WeaponId`가 null인 항목은 현재 `TryGetWeapon` 실패로 `ArgumentException`. 변경 = null 항목은 "그 슬롯 비움"(정의·레벨·중복 검사 건너뜀, 중복 검사는 null 아닌 ID끼리), 나머지 규약(4개 상한, 예외 규약) 불변. 기존 호출부(측정 프리셋·테스트)는 null을 보내지 않으므로 결과 불변. `WeaponLoadoutEntry.Level` 주석 갱신. 기존 `SetLoadout` 테스트 중 **null ID가 예외라고 단언하는 것이 있는지 미확인** — 있으면 새 규약으로 고치고 보고.
- 상자 결과 보관소는 applier가 갖고 `ResetForRun()`에서 `Clear()`(새 판에 비움, `LastSequence`는 유지). 생성자 인자·`RunSession`·조립 루트(`GameBootstrap`)는 **바꾸지 않는다**. Dev 노출(`IDevModeHost.ChestResults`)은 웨이브 6b IMP-DEV 몫 — 당신은 하지 않는다.
- 목록 기록은 효과·난수 소비를 바꾸지 않아야 한다(SPEC F4 12회차 23행). `PickupSystem`의 `openChest` 델리게이트(MONSTER 소유)는 그대로.
- 해시 밖: `ChestResultLog`·`Sequence`·`LastTargetId`는 `SimulationStateHash` 입력이 아니다(Loop 소유 파일, 만지지 않는다).

### 3.3 이미 확인된 사실 (시작 커밋 = DATA 머지 뒤 main, PM이 알려 줌)

- `StepMove`(`StepMove.cs:7`)는 `Toward`·`UnitDirection`뿐. 젬 끌림(`PickupSystem`)은 `Toward` 그대로.
- `CircleMath.Overlaps(a, ra, b, rb)` = `(b − a).sqrMagnitude <= (ra + rb)²`(경계 포함, Core 소유 — 호출만).
- 플레이어 반지름: `StepContext`에 없다. `MonsterSpawner.Bind`가 `_data.Current?.PlayerStats?.Radius ?? 0f`를 ★ internal `PlayerRadius`에 담고, `SpawnOnCircle`과 `MonsterCommandHandler.SpawnMonsters`(`_spawner.PlayerRadius`)가 `Initialize` 4번째 인자로 넘긴다. 판 중 불변(`PlayerEntity.cs:72~75`만 씀).
- `MonsterSpawner.OnPhase`(`MonsterSpawner.cs:50~87`): `_policy.CollectSpawns`(65) → 상한 검사 → 생성 → `!BossSpawnedThisRun && _policy.BossSpawnDue`(83). 끔이면 `CollectSpawns` 호출과 그 루프만 건너뛴다(Spawn 스트림 미소비). 보스 등장·소환·`SpawnMonstersNow`·`SpawnBossNow`는 끔과 무관. `Bind`에서 `SpawnsEnabled = true`.
- `MonsterCommandHandler`는 `ISimulationCommandHandler`(스텝 안 명령)다 — 대기 명령 핸들러를 여기에 두지 않는다. 대기 명령은 `PendingCommandQueue` 소유자 종류(현재 4종, `GameBootstrap.cs:315~318` 등록)로만 적용된다 → 다섯 번째 소유자 종류.
