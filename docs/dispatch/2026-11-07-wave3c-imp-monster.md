### 5-C. 기준선 — 정상 동작인데 결함으로 오판하기 쉬운 것

1. `MonsterRegistry.Monsters`는 ID 오름차순이고 `Spawned`/`Despawning`에서 갱신된다 — Lifecycle 안에서 `Despawn`을 부르면 **즉시** 목록에서 빠진다(그래서 M8은 ID를 먼저 모은다).
2. 생성 스텝에는 `Tick`이 오지 않는다. 생성 스텝 s의 Collision에도 없다. 스냅샷(`MonsterRegistry`)은 BuildIndex에서 만들어지므로 s의 Lifecycle에서 생긴 몬스터는 s+1 BuildIndex부터 스냅샷에 든다.
3. `SpawnGeometry.PointOnCircle`의 `u01`은 `[0,1]` 밖이면 예외다 — `NextFloat01`을 그대로 넘긴다. `IsBeyondDespawn`은 **엄격 초과**(`>`)다.
4. `DeterministicRng.Chance(p)`는 `p ≤ 0`에서도 **난수를 소비**하는지 `Scripts/Core/DeterministicRng.cs`를 보고 확인한다 — TAC-F4-2는 "확률 0이어도 뽑는다"이므로 소비하지 않는 구현이면 `NextFloat01() < p` 형태로 **당신 코드에서** 소비를 보장한다.
5. `MonsterDefinition.IsLarge`(데이터 필드)와 `MonsterSizeRules.IsLarge(radius, isBoss)`(R25 규칙)는 다르다 — `Body.IsLarge`에는 **규칙** 결과를 쓴다(데이터 필드는 로더가 R25로 채운 값이라 보통 같지만 보스 판정은 `isBoss` 인자가 원본).
6. `SimulationRules.MonsterCap` 400은 보스 제외 수의 상한이다 — 보스 포함 401기는 정상(R20).
7. 적 투사체의 소모·회수는 PLAYER 몫이다 — 당신 테스트에서 투사체가 플레이어에 닿아도 사라지지 않는 것은 정상(수명 만료로만 사라진다).
8. `LifetimeSystem`은 `ExpireStep = long.MaxValue`(수명 0)를 건너뛴다 — 젬·상자·몬스터는 수명이 없다.
9. `PendingCommandQueue`의 `SpawnBossNow`는 `BossSpawnedThisRun()`이 참이면 큐에서 거부된다(LOOP) — 당신 핸들러에는 오지 않는다. 하지만 `SpawnMonstersNow`로 보스 ID를 N기 넣는 것은 막히지 않는다 — 그때도 M4의 플래그 규칙을 적용한다(첫 1기만 플래그; 나머지도 생성은 된다 — 개발자 책임, 막지 않는다) [기본값].
10. 첫 배치 실행은 2~5분이다. 기존 테스트는 당신 변경 전에도 전부 통과한다. test-framework 1.6: `LogAssert.ignoreFailingMessages`는 본문에서 켠다.
11. `SimEntity.MarkConsumed`·`LoopLog`·`IsAttracted` setter 같은 internal은 같은 어셈블리라 보인다 — 테스트 어셈블리에서는 보이지 않는다. 테스트가 읽을 상태는 public 읽기 속성으로.
