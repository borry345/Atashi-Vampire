# 수동 스모크 라운드

`ORCHESTRATION.md` "PM 종료 체크리스트" 3번의 실행판이다. 자산은 체크리스트 **파일**이 아니라 **절차**다 —
기준은 SPEC이, 결과는 `RUN_LOG.md`가, 한계는 `DECISIONS.md`가 이미 소유하므로 프로젝트 루트에 체크리스트 md를
남기지 않는다(공식 문서: 반복 절차·체크리스트는 스킬에 둔다). 근거: PJT06 `JETSON_SMOKE.md`(2026-11-02)에
배포 순서·기준·결과·알려진 한계 넷이 섞여 역할과 소유 경계가 흐려졌다.

## 0. 시점과 전제

- tester 라운드 종료, SW로 확인 가능한 기준 전부 PASS, 실기기·실제 브라우저·외부 서비스 기준만 남음.
- 사용자가 기기를 조작한다. PM은 항목·방법·기대 현상을 주고 보고를 받는다. 실기기 조작을 에이전트에 맡기지 않는다.

## 1. 체크리스트 작성 — 작업 파일 `.scratch/smoke-<날짜>.md`

- 먼저 `.scratch/`가 그 프로젝트 `.gitignore`에 있는지 확인한다(`git check-ignore -v .scratch/`). 설치 스크립트는 `.gitignore`를 복사하지 않는다 — 없으면 한 줄 추가한다(PJT06은 직접 넣었다).
- 항목 출처는 SPEC의 `[HW]`(또는 "수동 확인") 표시 기준 **만**. 기준 ID를 그대로 쓰고 새 기준을 만들지 않는다.
- 항목 한 줄의 형식: 기준 ID — 조작 방법 — 기대 현상 — 어긋나면 받을 증거(화면 문구·콘솔 출력 원문).
- 순서는 의존 관계로(예: 한계 측정 → 그 한계를 쓰는 App → 입력 장치 → 로그 → 표시 장치).
- **배포 순서와 실행 명령은 여기에 쓰지 않는다** — 소유자는 readme(사용자 소유면 문안만 제공)와 TECH_SPEC의 배포 절이다.
  체크리스트에는 "배포 절 순서로 올린 뒤"와 **"코드를 다시 올렸으면 커널·프로세스를 재시작한다"** 두 줄만 둔다
  (옛 코드가 그대로 돌아 "수정이 반영되지 않았다"로 보인 일이 PJT06에서 2회).
- 보고 양식은 표 하나: `| 기준 | PASS/FAIL/미확인 | 증상·메모 |`.

## 2. 라운드 진행

- 사용자에게는 **한 절씩** 넘긴다. 전체를 한 번에 주면 어디까지 했는지 흐려진다.
- 보고마다 바로 돌려놓는다:
  - PASS → SPEC §2 상태 갱신(team-lead 재개 또는 PM 직접).
  - FAIL → `RUN_LOG.md`에 "스모크 발견 #N: 증상 원문 → 원인 → 조치" 한 항목, 재작업은 "소규모 수정 경로" 또는 team-lead(3회 상한).
  - 기구·환경의 한계로 판명(예: USB 수신기는 패드를 꺼도 장치가 남는다) → `DECISIONS.md` 해당 항목에 "알려진 한계"로, 기준 재정의가 필요하면 사용자 결정.
- 결정이 필요한 것(기준 재정의, 기본값 변경)은 한 번에 하나씩 추천안과 함께 묻는다.

## 3. 종료

- 전 항목이 PASS 또는 수용된 미확인이면 `RUN_LOG.md`에 라운드 종료 항목(항목 수, FAIL 건수와 해소, 미확인과 이유).
- 남겨야 할 내용이 전부 SPEC §2·`RUN_LOG.md`·`DECISIONS.md`·readme로 갔는지 확인한 뒤 **`.scratch/smoke-<날짜>.md`를 지운다.**
  이 확인이 삭제 조건이다. 미확인 항목(예: 멀티미터 대조 미실시)은 SPEC §2 상태에 "미확인(이유)"로 남긴다.
