### 5.16 상태 해시 (Simulation, IMP-LOOP)

```csharp
namespace Survivor.Simulation
{
    /// FNV-1a 64 over: step, player pos/hp/xp/level, monsters (ascending Id: id, pos, hp),
    /// projectiles (ascending Id: id, pos), gems (ascending Id: id, pos), kill count (R24). Floats hashed by bit pattern.
    /// (rev 11) also: player zones and player orbs (ascending Id: id, pos), and each weapon's _nextFireStep in slot order.
    public static class SimulationStateHash { public static ulong Compute(RunSession session); }
}
```
결정론 테스트(프레임레이트 3종, 전략 조합)와 개발자 모드 N스텝 결과 출력에 이 해시를 쓴다. (17회차) 무기별 `_nextFireStep`은 ★ `WeaponInstance.NextFireStep`(`WeaponInventory.Slots` 슬롯 순서, 빈 슬롯 처리는 LOOP가 정함)으로 읽는다(5.12). (11회차) 장판(PlayerZone)·궤도 원(PlayerOrb)의 (id, pos)와 무기별 `_nextFireStep`(슬롯 순서)을 입력에 더했다. 적이 0기일 때의 `placement: player` 장판 생성 분기(TAC-F6-5)처럼 몬스터·투사체에 흔적을 남기지 않는 무기 상태 차이도 해시가 직접 잡게 하기 위해서다.

(15회차) **웨이브 4로 이월.** `SimulationStateHash.Compute(RunSession)`은 `RunSession`(IMP-FLOW, 웨이브 4)에 의존하므로 웨이브 2b에서 만들지 않았다. 소유자는 그대로 IMP-LOOP이고 웨이브 4에서 작성한다(IMP-FLOW와 함께 또는 LOOP 재개, 5c.2·5c.4). 2b의 결정론 테스트는 테스트 전용 FNV-1a 64 도우미 `LoopPmStateHash`(`Tests/PlayMode/Loop/LoopPmRig.cs` 안의 internal 클래스)로 했다 — 입력은 스텝, 플레이어 위치, 활성 엔티티(Id 오름차순: index·generation·category·위치)이고 float은 비트 패턴으로 넣는다(이 절과 같은 규칙, 입력은 이 절의 부분집합). 결과: CentralTick·PerObject × `captureDeltaTime` 1/30·1/60·1/144, 600스텝, 마지막 시점 활성 엔티티 84 → 7회 모두 `0x5928B7C20FEF59D6`(PM 배치 기록, 6.2 U3). 웨이브 4에서 이 도우미를 실물 `SimulationStateHash`로 교체한다(5c.4 웨이브 4).

(21회차) **기준선 변경 예정 — 웨이브 6a 머지 때 1회.** 해시 함수와 입력 목록은 바꾸지 않는다(`SimulationStateHash.cs` 무변경). 현재 기록값(36조합 `0x7AE2FE65ACEFF8F4`, 게이트 결정론 `0xF8CB841EBAE36519`, Dev 결정론 `0x4147E68D6207C9B4`)은 테스트에 상수로 박혀 있지 않고(Tests grep에 없음) 실행 로그·문서 기록값이다 — 테스트는 프레임레이트·전략·실행 간 **일치**를 단언한다. 그래서 "갱신"은 6a 머지 뒤 PM이 새 기록값을 5c.5·RUN_LOG에 남기는 일이고 테스트 코드 수정이 아니다. 값이 바뀌는 원인(예상된 변경):
- 몬스터–플레이어 접촉 멈춤(R32, 5.12.1) — 몬스터 위치가 바뀐다. 실제 데이터로 몬스터가 플레이어에 닿는 모든 시나리오(36조합 1,800스텝·게이트·Dev 결정론 포함)가 해당한다.
- 구간 체력 배율 데이터(`spawnTable.json` 1.5/2.2/3.0, TECH 20 5.12.1) — 7,200스텝을 넘겨 일반 몬스터를 스폰하는 시나리오만(`Hp` 입력).
- 보스 장판 데이터 제거 — 보스가 나오는 시나리오만(장판 엔티티·플레이어 체력).
- 스폰 켬/끔 명령·`SetLoadout` 빈 슬롯 항목 — 그 명령을 쓰는 새 시나리오에서만. 기존 호출 경로의 값은 바뀌지 않는다.
- (22회차) **6a 머지 뒤 갱신된 기록값**(덮어쓰지 않고 이력 추가 — 5c.5 (22회차)): 36조합 `0xB999B737C31BD755`, 게이트 결정론 `0xF8CB841EBAE36519`(불변), Dev 결정론 `0x08FD01D7A732F22E`, 프레임레이트 비교 `0x5928B7C20FEF59D6`(origin/main 240f564, PM 확인 2026-11-11). 6b는 이 값을 바꾸지 않았다. **웨이브 7에서 다시 바뀐다**(아래).

(22회차) **기준선 변경 예정 — 웨이브 7 머지 때 1회.** 해시 함수·입력 목록은 그대로다(`SimulationStateHash.cs` 무변경 — 입력은 스텝, 플레이어 위치·체력·경험치·레벨, ID 오름차순 엔티티의 ID·세대·카테고리·위치·몬스터 `Hp`, 처치 수, 무기 슬롯·`NextFireStep`; 무기·패시브 **레벨은 직접 입력이 아니다**, `SimulationStateHash.cs:16~64`). 테스트는 일치만 단언하므로 갱신은 머지 뒤 PM이 새 기록값을 5c.5·RUN_LOG에 남기는 일이다. 바뀌는 원인(예상된 변경):
- 죽은 대상 통과(5.12 "IMP-PLAYER 웨이브 7") — 같은 스텝에 여러 발이 한 적에 몰리는 시나리오에서 투사체 생존·다른 몬스터의 `Hp`·처치·젬이 바뀐다. 실제 데이터의 36조합·Dev 결정론이 해당할 가능성이 높다.
- 상자 ② 후보에 패시브(5.14 22회차) — 패시브를 보유한 판에서 상자를 열 때만. 패시브 레벨은 직접 입력이 아니지만 P1(`NextFireStep`)·P2(플레이어 위치)·P3(젬 획득 시점)로 드러난다. 레벨업이 꺼진 시나리오(패시브 0개)는 후보 목록이 같아 영향 없음.
- 몬스터끼리 분리(5.12.1 22회차) — 겹친 몬스터가 있는 모든 시나리오의 몬스터 위치. `GameBootstrap`으로 조립하는 PlayMode 시나리오 전부가 해당한다(EM 리그는 분리를 등록하지 않으면 불변, 5.12.1).
- 패시브 로드아웃 명령(5.14 22회차) — 그 명령을 쓰는 새 시나리오에서만.
- (23회차) 엔진판 R5 게이트(5.9 23회차 수정, IMP-COLLISION 웨이브 7) — 엔진 충돌 조합의 값만 바뀌어 자체 충돌 조합과 같아진다(경계 접점에서 Box2D가 1스텝 먼저 내던 Enter가 자체판 스텝으로). 자체 조합의 값은 바뀌지 않는다. 중간 기록값(MONSTER 머지 예정본)은 5c.5 (23회차).

**해시 밖(22회차 추가)**: Dev 콘솔 창 열림·위치(`DevOverlay`), 다음 판 체크박스 레이블, Dev 패시브 구성 UI·`DevPassiveLoadoutPlanner`(명령이 적용된 결과만 해시에 드러남), `ChestResult`의 `PassiveUpgraded` 기록(목록은 21회차부터 해시 밖). 이것들이 해시를 바꾸면 결함이다.

**해시 밖(입력에 넣지 않음, 21회차)**: `ChestResultLog`·`ChestResult.Sequence`(5.12), `PlayerProjectile.LastTargetId`·`WeaponInstance.LastTargetId`, `MonsterSpawner.SpawnsEnabled` 값 자체([기본값] — 효과는 엔티티 집합·Spawn 스트림 위치로 드러남), 표시 배율 `GameRules.BodyVisualScale`·궤도 원 표시(5.17.2), 카메라 줌·Dev 커맨드 로그·Dev가 기억하는 스폰 상태(5.15.5). 이것들을 읽고 쓰는 것이 해시를 바꾸면 결함이다(SPEC F4·F6·F19·00-common 3.0 C 12회차 "결정론 기준 항목을 바꾸지 않는다"). 웨이브 6b는 해시를 바꾸지 않는다(6a 갱신값 그대로가 완료 기준, 5c.4). 웨이브 7(상자 패시브 후보·몬스터 분리)은 다시 바꾼다 — TECH 22회차.
