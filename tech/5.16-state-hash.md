### 5.16 상태 해시 (Simulation, IMP-LOOP)

```csharp
namespace Survivor.Simulation
{
    /// FNV-1a 64 over: step, player pos/hp/xp/level, monsters (ascending Id: id, pos, hp),
    /// projectiles (ascending Id: id, pos), gems (ascending Id: id, pos), kill count (R24). Floats hashed by bit pattern.
    /// (rev 11) also: player zones and player orbs (ascending Id: id, pos), and each weapon's _nextFireStep in slot order.
    public static class SimulationStateHash { public static ulong Compute(RunSession session); }
}
```
결정론 테스트(프레임레이트 3종, 전략 조합)와 개발자 모드 N스텝 결과 출력에 이 해시를 쓴다. (11회차) 장판(PlayerZone)·궤도 원(PlayerOrb)의 (id, pos)와 무기별 `_nextFireStep`(슬롯 순서)을 입력에 더했다. 적이 0기일 때의 `placement: player` 장판 생성 분기(TAC-F6-5)처럼 몬스터·투사체에 흔적을 남기지 않는 무기 상태 차이도 해시가 직접 잡게 하기 위해서다.

(15회차) **웨이브 4로 이월.** `SimulationStateHash.Compute(RunSession)`은 `RunSession`(IMP-FLOW, 웨이브 4)에 의존하므로 웨이브 2b에서 만들지 않았다. 소유자는 그대로 IMP-LOOP이고 웨이브 4에서 작성한다(IMP-FLOW와 함께 또는 LOOP 재개, 5c.2·5c.4). 2b의 결정론 테스트는 테스트 전용 FNV-1a 64 도우미 `LoopPmStateHash`(`Tests/PlayMode/Loop/LoopPmRig.cs` 안의 internal 클래스)로 했다 — 입력은 스텝, 플레이어 위치, 활성 엔티티(Id 오름차순: index·generation·category·위치)이고 float은 비트 패턴으로 넣는다(이 절과 같은 규칙, 입력은 이 절의 부분집합). 결과: CentralTick·PerObject × `captureDeltaTime` 1/30·1/60·1/144, 600스텝, 마지막 시점 활성 엔티티 84 → 7회 모두 `0x5928B7C20FEF59D6`(PM 배치 기록, 6.2 U3). 웨이브 4에서 이 도우미를 실물 `SimulationStateHash`로 교체한다(5c.4 웨이브 4).
