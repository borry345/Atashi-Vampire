## 4. 기능별 요구사항 및 수용 기준 (Functional Requirements & Acceptance Criteria)

spec/ 3절의 수용 기준(~~(11회차) SPEC 10회차, 정규식 295개(보정 포함 306개), 2026-11-05 기계 집계~~ ~~(20회차) SPEC 11회차, 정규식 312개(보정 포함 323개, PM 브리핑 수치)~~ (21회차) SPEC 12회차, 정규식 329개(보정 포함 340개, PM 브리핑 수치), spec/README.md 방법 기준)은 그대로 유효하며 여기서 반복하지 않는다. 아래는 그 기준을 이 설계로 구현할 때 추가로 지켜야 하는 **기술 수용 기준(TAC)** 이다. 각 항목은 5절의 계약과 5a의 공유 규칙을 근거로 하며, 테스트 위치를 함께 적었다(EM = EditMode, PM = PlayMode).

### 3.0 F·H·I (공통) 고정 스텝·결정론·ID·피해

- TAC-0-1 (2회차 수정): 게임 상태를 바꾸는 코드는 `SimulationPhase` 핸들러나 `IUpdatable.Tick` 안에서만 실행된다. 예외는 둘뿐이다. ① `RunSession.Reset(in RunStrategies)`(판 경계) ② 레벨업 게이트가 닫힌 동안(`clock.CloseReason == LevelUp && !StepActive`) `PlayerProgressionApplier.ApplyLevelUpOption`(5.14). 개발자 조작·핫 리로드 교체·타깃 공급자 전환은 `PendingCommandQueue`에 넣어 다음 스텝의 `Begin`에서 적용한다. (코드 리뷰 + PM)
- TAC-0-2: 로직 코드는 `Time.deltaTime`, `Time.time`, `Time.fixedDeltaTime`, `UnityEngine.Random`, `System.Random`, `DateTime`을 읽지 않는다. 시간은 `StepContext.Step`, 난수는 `RngStreams`만 쓴다. 예외는 일반 플레이의 시드 생성 1회(App)와 개발자 모드의 프레임 시간 수집(Dev)뿐이다. (정적 검사: grep 테스트를 EM에 둔다)
- TAC-0-3: `Time.fixedDeltaTime == 1f/60f`, `Time.maximumDeltaTime == 0.05f`를 부트스트랩에서 코드로 설정하고 PM 테스트로 확인한다((11회차) 테스트 비교는 정확 비교가 아니라 허용 오차 1e-6). 한 프레임의 스텝 수가 3을 넘지 않는다 [실측 U2]. (10회차) 1x에서 상한 3은 실측으로 확인됐다(U2). 배속 중에는 `maximumDeltaTime = 0.05 / timeScale` 규칙을 따른다(TAC-F19-6, D9). catch-up 상한 3 검증은 `captureDeltaTime`이 아니라 **실제 긴 프레임**(예: 테스트에서 `Thread.Sleep(100)` 뒤 다음 프레임의 스텝 수)으로 한다 — `captureDeltaTime`으로 흉내 낸 긴 프레임은 `maximumDeltaTime` 클램프를 우회한다(실측 U2).
- TAC-0-4: 같은 시드와 같은 입력 시퀀스로 `Time.captureDeltaTime`을 1/30, 1/60, 1/144로 바꿔 같은 스텝 수만큼 돌리면 `SimulationStateHash`가 같다 (PM, U3). (10회차) `captureDeltaTime`은 이 프레임레이트 결정론 테스트에만 쓰고 catch-up 상한 검증(TAC-0-3)에는 쓰지 않는다(실측 U2·U3). (11회차) 해시 입력에 장판·궤도 원(id, pos)과 무기별 `_nextFireStep`이 들어간다(5.16). 시나리오에 적 0기 구간 + `placement: player` 장판 무기를 포함해 그 생성 분기를 해시로 직접 비교한다.
- TAC-0-5 (2회차 수정): 일시정지·레벨업·결과 중에는 `SimulationClock.IsRunning == false`라 어떤 단계도 실행되지 않고, F17 A의 셀프 티커도 `Tick`을 호출하지 않는다(`StepActive == false`) (PM).
- TAC-0-6: `IUpdatable.Tick`은 자기 상태와 `StepContext`가 주는 읽기 전용 값만 읽고 쓴다. 다른 엔티티의 생성·소멸·피해는 `ISimulationCommands`로 미룬다 (코드 리뷰 + F17 A/B 동등성 PM).
- TAC-0-7 (2회차 신규): 레벨업이 스텝 s에서 발생하는 시나리오를 30/60/144 FPS로 돌리면, 세 경우 모두 게이트가 닫힌 시점의 `clock.Step == s + 1`이고 상태 해시가 같다. 같은 프레임의 catch-up `FixedUpdate`에서 스텝이 더 돌지 않는다. `Update` 경로에 `CloseAfterCurrentStep` 호출이 없고, `Update` 경로의 `Close` 호출 이유는 `Paused`·`RunReset`뿐이다(grep) (PM).
- TAC-0-8 (2회차 신규): `EntityLifecycle.Spawn`·`Despawn`은 현재 단계가 `Lifecycle`이거나 판 리셋 중일 때만 성공하고, 그 밖에서는 `InvalidOperationException`을 던진다. 스텝 s의 Lifecycle에서 생성된 엔티티는 스텝 s의 `CollectEvents`에 나타나지 않고 s+1부터 나타나며, 첫 `Tick`은 s+1이다 (EM + PM: 두 충돌 전략·두 틱 전략에서 같은 첫 피해 스텝; (15회차) 생명주기 부분은 PM — EditMode 테스트 어셈블리 안의 `SimEntity` 파생 더블은 `AddComponent`할 수 없어서, 5c.5).
- TAC-0-9 (2회차 신규, 3.0 H): 디스폰 뒤 같은 인덱스를 받은 엔티티의 `Generation`이 이전보다 1 크다. 풀 A/B/C 세 전략에서 같은 시나리오의 ID 발급 순서(로그)가 같다 (EM + PM; (15회차) 생명주기 부분은 PM, 5c.5).
- TAC-0-10 (2회차 신규, 3.0 I): 쿨다운·무적 기록은 전부 `long` 스텝 번호이고 `EntityHandle`(세대 포함)로 키를 잡는다. 디스폰된 대상의 기록은 `EntityLifecycle.Despawned`에서 지운다(등록 해제는 Exit을 내지 않으므로, 이 처리가 없으면 겹침 집합에 죽은 대상이 남는다) (EM; (15회차) 생명주기 부분은 PM, 5c.5). (15회차) 레지스트리(`MonsterRegistry` 등)는 `Despawned`가 아니라 Despawn 첫 단계의 `Despawning`으로 제거한다 — 겹침·쿨다운 기록 소비자는 그대로 `Despawned`(5.10). (17회차, PM 판정 — 구현 보정) 겹침 정리는 **양쪽**에서 한다: 피격자가 디스폰되면 위 `Forget`(기존), **가해자(장판·궤도 원)가 디스폰되면** 그 엔티티가 지금 겹친 대상 목록(`OrbitOrb.Overlaps`·`DamageZone.Overlaps`, internal)을 `WeaponInventory`의 `Despawned` 처리기가 소유 무기 트래커에 `OnExit`으로 다시 흘린다. 두 충돌 전략 모두 `Unregister`에 Exit을 내지 않으므로(TAC-F18-5) 이것이 없으면 장판이 사라진 뒤에도 겹침 수가 남아 그 적이 계속 맞는다(5.12, 5c.3 #12).

### F1. 플레이어 이동

- TAC-F1-1: `PlayerMovement`는 `IInputSource.ReadMove(step, position)`만 호출한다. `Keyboard.current`를 참조하는 코드는 `KeyboardInputSource` 한 곳에만 있다.
- TAC-F1-2: 대각 방향은 `MoveMath.ToUnitDirection(x, y)`의 8방향 상수 표를 쓴다. 단일 축과 대각의 스텝당 이동 크기 차이가 1e-6 이하다 (EM).
- TAC-F1-3: 속도 = `StatMath.ApplyMultiplier(PlayerStats.moveSpeedPerStep, P2 보너스)`(R13)((14회차) 코드 이름 `PlayerStatsDefinition.MoveSpeedPerStep`). `MoveCommand.SpeedOverride ≥ 0`이면 그 값을 쓴다(자동 경로 전용) (EM).
- TAC-F1-4 (2회차 수정): 위치를 제한하거나 보정하는 코드가 없다. (반복 배경은 TAC-F8-11로 옮겼다.)
- TAC-F1-5: 게임패드 입력이 아무 효과도 내지 않는다. `KeyboardInputSource`는 `Keyboard.current`만 읽는다 (PM).
- TAC-F1-6 (2회차 신규): `CameraFollow.LateUpdate`(실행 순서 0, IMP-FLOW)가 매 프레임 카메라 위치를 `PlayerEntity.Position`(시뮬레이션 값)으로 **그대로** 설정한다(보간·지연·감쇠 없음). 카메라 orthographic size는 `GameRules.CameraOrthographicSize`(9)로 부트스트랩에서 1회 설정한다. 플레이 중 아무 프레임에서나 `(camera.xy − player.Position)`의 크기가 0이다 (PM).
- TAC-F1-7 (2회차 신규, 3.0 F): `KeyboardInputSource`는 `Update`마다 키의 눌림 상태를 래치하되, 한 프레임 안에 눌렸다 떼어진 키(`wasPressedThisFrame`)도 그 프레임 래치에 포함한다. `ReadMove`는 래치를 읽기만 하고 지우지 않는다. 래치는 다음 `Update`에서 다시 계산된다(프레임 안의 스텝 1~3회가 같은 입력을 본다) [실측 U17]. (15회차) 래치 로직(방향 계산·반환 규칙) EM 확인, 실입력 미확인(6.2 U17).

### F2. 자동 공격

- TAC-F2-1: 시작 시 `PlayerStats.startingWeaponId`(기본 "W1") 무기를 1단계로 보유한다.
- TAC-F2-2: 무기 쿨다운은 "다음 발사 허용 스텝"(`_nextFireStep`)으로 관리한다. 발사 조건은 `step ≥ _nextFireStep && Rules.WeaponsEnabled && 타깃 있음`이고, 발사하면 `_nextFireStep = step + 유효 쿨다운 스텝`이다. 타깃이 없으면 발사하지 않고 `_nextFireStep`도 그대로 두어 다음 스텝에 다시 시도한다 (EM). (9회차, 사용자 결정 2026-11-05, SPEC F6 9회차) "타깃 있음"은 **대상이 필요한 무기(W1·W4·E1, `placement: nearestEnemy` 장판)에만** 붙는 조건이다. `placement: player` 장판은 `step ≥ _nextFireStep && Rules.WeaponsEnabled`만으로 생성하고 쿨다운을 소비한다(TAC-F6-5). 궤도형(W2·E2)은 발사 개념이 없고 궤도 원이 보유 중 상시 존재한다(TAC-F6-4). (7회차 보강, SPEC F2 7회차) **첫 보유 규약**: 무기를 처음 보유하게 된 모든 경로 — 판 시작의 W1(TAC-F2-1), 레벨업 `WeaponNew`, 진화 결과 무기(TAC-F7-2), 개발자 `SetLoadout`(5.14) — 에서 인스턴스는 `_nextFireStep = 보유가 적용된 스텝`으로 시작한다. 그래서 보유 뒤 첫 WeaponTick에서 발사 조건(타깃 있음 등)을 만족하면 쿨다운을 기다리지 않고 바로 발사하고, 이후 쿨다운은 그 발사부터 센다. 레벨업 획득은 게이트가 닫힌 동안 적용되므로 "보유가 적용된 스텝"은 그때의 `clock.Step`(다음에 실행될 스텝, TAC-0-7의 s+1)이다 (EM: 네 경로 각각 첫 발사 스텝).
- TAC-F2-3: 유효 쿨다운 = `StatMath.ApplyAttackSpeed(baseCooldownSteps, P1 보너스)` (5a R13) (EM). (7회차, D14 확정 2026-11-05, SPEC F2 7회차) P1은 **모든 무기의 쿨다운(발사·생성 간격)**에 적용한다: W1·W3·W4·E1의 `cooldownSteps`, W2·E2 궤도 원의 피해 틱 간격(`hitIntervalSteps`, W2의 유일한 간격). **W3 장판 내부의 피해 틱 간격(`hitIntervalSteps`)에는 적용하지 않는다**(장판을 까는 주기만 짧아진다). 그래서 W2·E2의 `ContactDamageTracker`에는 `ApplyAttackSpeed`를 거친 틱 간격을, W3의 트래커에는 정의값 그대로를 넘긴다(5.12 `SetInterval`) (EM: P1 단계별 W3 장판 틱 간격 불변). (8회차, SPEC F2 8회차) P1 획득·강화는 **다음 산정부터** 적용한다: 이미 잡힌 `_nextFireStep`과 트래커의 대상별 `nextAllowed`는 다시 계산하지 않고, 다음 발사·다음 허용 스텝을 정할 때부터 새 유효 간격을 쓴다 (EM: P1 강화 직후 첫 발사 스텝 불변, 그다음 간격만 짧아짐).
- TAC-F2-4: 무기 코드는 `ITargetProvider`(`StepContext.Targets`)만 호출한다. Simulation asmdef에 Strategies 참조가 없으므로 구현 클래스를 직접 참조하면 컴파일되지 않는다.
- TAC-F2-5: 공격 on/off는 `SimulationRules.WeaponsEnabled` 값으로만 제어한다. ### F5. 레벨업과 선택지

- TAC-F5-1: 후보 생성 `LevelUpCandidateBuilder.Build(...)`는 후보를 **정규 순서**(5a R12)로 반환한다. 비복원 추출은 `WeightedSampler.SampleWithoutReplacement`(5a R9)이고 RNG는 `LevelUp` 스트림이다 (EM).
- TAC-F5-2: 회복 후보 가중치 = `HealWeight.Compute(wBase, hp, maxHp)`(5a R8). 0이면 후보에서 뺀다. 추출 뒤 3칸에 못 미치면 남은 칸을 `Heal` 채움 항목으로 채운다(만체력이어도) (EM).
- TAC-F5-3: 제외 규칙은 다음과 같다. 새 무기는 무기 슬롯 4개가 차면 제외, 새 패시브는 패시브 3개가 차면 제외, `ProgressionRules.IsWeaponUpgradable`/`IsPassiveUpgradable`(R22)이 거짓인 항목의 강화는 제외, `evolvedOnly` 무기는 항상 제외, 진화로 소모된 원본 무기의 "새 획득"도 제외한다 [기본값, D5 — (8회차) SPEC F7 8회차로 확정, D5 해소] (EM). (7회차 보강, SPEC F5·F6 7회차) **이미 보유한 무기·패시브의 "새 획득"(`WeaponNew`/`PassiveNew`) 후보도 제외한다** — 보유 항목은 강화(`WeaponUpgrade`/`PassiveUpgrade`)로만 나타나고, 같은 무기를 두 번째 슬롯에 얻는 경로가 없다. 판정은 `LevelUpCandidateBuilder.Build`가 인자로 받는 `WeaponInventory`·`PassiveInventory`의 보유 ID로 하며 별도 함수를 두지 않는다 (EM: 보유 무기·패시브의 New 후보 0개).
- TAC-F5-4 (2회차 재작성, A4): 레벨업 처리 순서는 다음과 같다.
  1. 스텝 s의 `StepOutcomeGate`(Lifecycle order 90)가 사망·클리어가 아니고 `Rules.LevelUpEnabled`이면 `ExperienceSystem.TryBeginLevelUp(curve)`를 1회 호출한다. 참이면(경험치에서 임계값을 빼고 레벨 +1) `CloseAfterCurrentStep(LevelUp)`.
  2. FLOW가 다음 `Update`에서 닫힘을 보고 `LevelUpSession.Open`으로 회차를 연다. 후보는 **그 시점의 상태**로 뽑는다(게이트가 닫혀 상태가 고정되어 있고 LevelUp 스트림은 이 경로만 쓰므로 프레임 타이밍과 무관하게 결정적이다).
  3. 선택이 수락되면(TAC-F5-5) **스텝을 돌리지 않고 즉시** `PlayerProgressionApplier.ApplyLevelUpOption`을 호출한다.
  4. 이어서 `TryBeginLevelUp`을 다시 호출한다. 참이면 **같은 `Update` 안에서 두 번째 회차를 연다**(스텝 없음, 후보는 첫 선택 적용 **후** 상태로 뽑는다). 거짓이면 `clock.Open()`으로 재개한다.
  젬 대량 획득으로 여러 레벨분 경험치가 쌓여도 회차는 하나씩 순서대로 열린다(SPEC F5) (EM: `ExperienceSystem` / PM: 연속 3레벨 시나리오에서 회차 ID 1·2·3, 스텝 수 불변).
- TAC-F5-5 (2회차 재작성, A5): 선택 입력(키 1/2/3, 버튼 클릭, 포커스 버튼의 Enter)은 모두 `LevelUpSession.TrySubmit(roundId, index, frame)`(R29)을 부른다. 회차당 **처음 수락된 한 번만** 유효하고, 같은 회차의 두 번째 입력과 지난 회차 ID를 가진 입력은 거짓을 받는다. 같은 프레임에 키와 클릭이 함께 오면 먼저 처리된 하나만 유효하다(처리 순서는 보장되지 않음, U42). 새 회차는 **열린 프레임에는 입력을 받지 않는다**(`frame > OpenedFrame`) — 한 번의 키 입력이 연속 회차 두 개를 고르지 않게 하기 위해서다 (EM + PM).
- TAC-F5-6: `Rules.LevelUpEnabled == false`이면 경험치만 쌓이고 레벨·선택지는 생기지 않는다 [기본값, D19].
- TAC-F5-7 (2회차 신규, SPEC F5·F8 4회차): 레벨업 화면에서 ESC → `FlowState.Paused`(복귀 상태 = LevelUp). 일시정지 중 선택 입력은 무시한다(`TrySubmit`을 부르지 않는다). 재개하면 같은 `RoundId`와 같은 3개 선택지로 레벨업 화면이 돌아오고 추첨은 다시 하지 않는다. 일시정지에서 "타이틀로 나가기"는 판을 리셋하고 기록을 남기지 않는다 (PM).
- TAC-F5-8 (2회차 신규, 사망 > 클리어 > 레벨업): 같은 스텝에 사망 또는 보스 처치가 있으면 `TryBeginLevelUp`을 호출하지 않는다(쌓인 경험치는 판과 함께 버린다) (EM).

### F6. 무기 시스템

- TAC-F6-1 (2회차 수정): 무기 인스턴스는 `behavior` 값으로 `WeaponFactory`가 만든다. `projectile`(W1, E1)·`homing`(W4) → `ProjectileWeapon`(homing이면 투사체가 재조준 모드), `orbit`(W2, E2) → `OrbitWeapon`, `zone`(W3) → `ZoneWeapon`. W4를 나타내는 방법은 `behavior: "homing"` 하나뿐이다(불리언 플래그 없음).
- TAC-F6-2: W1 방향 = `MoveMath.DirectionOrDefault(target − playerPos)`(영벡터면 `Vector2.right`). 발사 후 방향은 바뀌지 않는다. `projectileCount > 1`이면 `spreadDegrees`를 균등 분할해 같은 스텝에 명령을 여러 개 넣는다 (EM).
- TAC-F6-3: W4 투사체는 `ProjectileTick`에서 매 스텝 `Targets.TryFindNearest(자기 위치)`로 방향을 다시 잡는다. 대상이 없으면 마지막 방향으로 직진하고 수명이 끝나면 소멸한다 [Q9]. W1·W4 모두 사거리 없이 `lifetimeSteps`로 소멸한다 [Q9]. (7회차 보강, SPEC F6 7회차) W4의 **첫 발사 방향**은 TAC-F6-2의 W1 규칙과 같다: 발사 스텝에 `MoveMath.DirectionOrDefault(target − playerPos)`(가장 가까운 적 방향, 영벡터면 +x). 재조준은 그 다음 스텝의 `ProjectileTick`부터다(생성 스텝에는 Tick이 오지 않는다, TAC-0-8·5c.3 #2) (EM).
- TAC-F6-4: W2 궤도 원 위치 = `playerPos + R·(cos θ_i, sin θ_i)`, `θ_i = θ0 + ω·step + 2π·i/orbCount`. `OrbitWeapon`이 WeaponTick에서 자기 궤도 원들의 위치를 스텝 번호로 바로 계산해 쓴다(누적 오차 없음) (EM). (5회차) 궤도 원은 무기를 보유하는 동안 상시 존재하며 수명·지속시간·재생성 쿨다운이 없다: `SpawnPlayerOrb` 명령을 처리하는 `PlayerSpawnCommandHandler`는 `EntityLifecycle.Spawn<T>`에 `lifetimeSteps = 0`(수명 없음)을 넘겨 `ExpireStep = long.MaxValue`가 되고(5.10), `LifetimeSystem`은 이를 회수하지 않는다. 회수 경로는 `orbCount` 감소 초과분(TAC-F6-8), 진화 교체(TAC-F7-2), 런 종료·재시작(`DespawnAll(RunReset)`) 셋뿐이다. 핫 리로드는 보유 인스턴스에 적용되지 않아(5.11.1) 해당하지 않는다 (SPEC F6 6회차 신규) (EM).
- TAC-F6-5 (2회차 수정, Q46②): W3는 쿨다운이 됐을 때 `Targets.TryFindNearest(playerPos)`가 있으면 그 위치로 `SpawnPlayerZone` 명령을 넣고 쿨다운을 소비한다. 없으면 명령도 쿨다운 소비도 없고 다음 스텝에 다시 시도한다. 장판은 생성 스텝부터 `durationSteps` 뒤 Lifecycle의 수명 만료(order 10)에서 회수한다. 위 문장은 `placement: nearestEnemy`(기본, 5.13.1)의 규칙이다. (9회차 수정, 사용자 결정 2026-11-05, SPEC F6 9회차 — 7회차 "`placement: player`도 타깃 없으면 재시도"(Q47 ③) 번복) `placement: player`는 대상이 필요 없으므로 `Targets.TryFindNearest`를 호출하지 않고, 쿨다운이 되면 적이 하나도 없어도 플레이어 위치로 `SpawnPlayerZone` 명령을 넣고 쿨다운을 소비한다. "타깃 있음"은 대상이 필요한 공격(W1·W4·E1, `placement: nearestEnemy` 장판)의 발사 조건이고(TAC-F2-2), 대상이 필요 없는 공격(궤도형 W2·E2의 궤도 원(TAC-F6-4), `placement: player` 장판)은 타깃과 무관하게 작동한다 (EM: 적 0기 + `placement: player`에서 쿨다운마다 장판 1개·`_nextFireStep` 갱신 / 적 0기 + `nearestEnemy`에서 장판 0개·`_nextFireStep` 불변).
- TAC-F6-6: W2·W3 지속 피해는 무기 인스턴스가 소유한 `ContactDamageTracker`(5.12)가 처리한다. Enter 시 허용 스텝이면 즉시 1회, 겹침이 이어지면 `hitIntervalSteps`((14회차) 코드 이름 `WeaponLevelDefinition.HitIntervalSteps`)마다 1회, Exit 뒤에도 허용 스텝까지 기록을 유지한다. 키는 대상 `EntityHandle`(세대 포함)다. 같은 무기의 장판 여러 개가 같은 적에 겹쳐도 그 무기의 기록 하나로 센다 (EM). (17회차, PM 판정 — 구현 보정) 장판·궤도 원이 디스폰되면 그 엔티티가 겹쳐 있던 적마다 트래커 `OnExit`을 재생한다(TAC-0-10, 5.12). 그래서 장판이 사라진 뒤에는 그 장판 몫의 겹침이 남지 않는다 (EM: `WeaponTests`의 `TACF6_6_ZoneDespawnEndsItsOverlapAlthoughNoExitIsEmitted`·`TACF6_6_OverlappingZonesOfOneWeaponShareOneCooldownRecord`).
- TAC-F6-7: 강화 값은 `levels[level-1]` 전체 파라미터 집합을 그대로 쓴다(절대값). 최대 단계 = `levels.Count`(기본 무기 5, 진화 무기 1).
- TAC-F6-8 (2회차 신규, A7): 무기 발사 결과물(W1·W4·E1 투사체, W3 장판, W2·E2 궤도 원)은 전부 WeaponTick에서 **명령으로** 적재되고 같은 스텝 Lifecycle(order 0)에서 생성된다. 생성 위치는 발사 스텝의 값이다. 그래서 W3의 첫 피해 스텝은 "발사 스텝 + 1"로 두 충돌 전략·두 틱 전략에서 같다. W2 궤도 원 수가 `orbCount`와 다르면(획득·강화·진화 직후) `OrbitWeapon`이 WeaponTick에서 모자란 만큼 `SpawnPlayerOrb`, 남는 만큼(인덱스 큰 것부터) `Despawn(Replaced)`를 넣는다 (EM + PM).
- TAC-F6-9 (2회차 신규, 3.0 I): W1·W4 투사체는 채널 0 Enter 1회에 피해를 주고 `Consumed` 표시 후 `Despawn` 명령을 넣는다. 같은 스텝에 같은 투사체의 다른 Enter는 `Consumed`라서 무시한다. 관통(`pierceCount > 0`)이면 "이미 맞힌 ID 목록"(세대 포함 `EntityHandle`)으로 재피해를 막고 `pierceCount + 1`회째 명중에서 소모된다 (EM).
- TAC-F6-10 (21회차 신규, SPEC F06 12회차 33행; IMP-FLOW 웨이브 6b): W2 또는 E2를 보유하는 동안 `OrbitRingPresenter`(5.17.2)가 그 슬롯의 링을 켜고 반지름이 `WeaponInstance.LevelDefinition.OrbitRadius`와 같다. W2를 강화하거나 E2로 진화하면 다음 프레임에 새 반지름이고, W2를 잃으면(개발자 로드아웃 0) 다음 프레임에 링이 꺼진다. `Rules.WeaponsEnabled == false` 중에도 링이 보이고, 개발자 모드 없이도 보인다. 링은 `SimEntity`·충돌 바디가 아니며 링이 있는 판과 없는 빌드의 같은 시드·입력 해시가 같다 (PM).

### F7. 조합(진화)

- TAC-F7-1: 자격 조건 = `weapon.Level == weapon.Definition.Levels.Count && passives.Owns(rule.passiveId) && !weapon.Definition.EvolvedOnly`((14회차) 코드 이름 `CombinationRule.PassiveId`, `WeaponDefinition.Levels`·`EvolvedOnly`는 일치). `TryFindFirstEligible()`은 무기 슬롯 순서로 훑어 첫 자격 규칙을 반환한다 (EM).

### F9. 오브젝트 풀링

- TAC-F9-1: 게임 코드는 `IPoolStrategy`만 참조하고, 그것도 `EntityLifecycle` 한 곳에서만 호출한다.
- TAC-F9-2: 구현 A(`CustomPoolStrategy`)는 템플릿별 비활성 스택(LIFO)이다. 비면 `Instantiate`로 확장하고 상한은 없다 [Q13]. 사전 생성 개수는 `PoolPrewarmCounts` 코드 상수다 [Q13, 측정 후 조정] (EM: 반환 후 재요청 시 같은 인스턴스).
- TAC-F9-3: 구현 B는 `Acquire`마다 `Instantiate`, `Release`마다 `SetActive(false)` 후 `Destroy`다 [실측 U22] (PM).
- TAC-F9-4: 구현 C는 템플릿별 `UnityEngine.Pool.ObjectPool<GameObject>`이고 `collectionCheck: true`, `maxSize: int.MaxValue`다 [실측 U21].

### F16. 타깃 탐색 전략

- TAC-F16-1: 세 구현 모두 `BuildIndex` 단계에서 받은 `MonsterSnapshotBuffer`의 위치로 거리를 계산하고, `TargetOrdering.IsBetter`(5a R6)로 고른다. 그래서 반환이 비트 단위로 같다 (EM: 무작위 배치 10,000건 + 동거리 배치 + 큰 몬스터 포함 배치에서 A=B 비교 / PM: A=B=C).
- TAC-F16-2: 공간 해시 셀 키 = `SpatialHash.CellOf(pos, cellSize)`(5a R14). 고리(ring) 탐색 종료 조건은 "고리 k를 끝냈고 `bestD2 ≤ (k·cellSize)²`" 또는 "점유 셀 범위를 벗어남"이다. 그 뒤 큰 몬스터 리스트를 전수 검사한다 (EM). (14회차 각주, 구현자 반박 수용 — 결과 동일성에 보수적) 첫 조건은 정확 산술에서는 맞지만 `FloorToInt(x / cellSize)`의 반올림으로 경계 근처 몬스터가 옆 셀에 배정될 수 있고 제곱거리에도 반올림이 있어, "같은 거리이면서 Id가 더 작은" 몬스터를 놓쳐 A와 비트가 갈릴 여지가 있다. 구현(`SpatialHashTargetProvider`)은 k > 0에서 하한 `bound = k·cellSize − 1e-5·(|px|+|py|+(k+1)·cellSize)`를 쓰고 `bound > 0 && bestD2 < bound²`(엄격 부등호)일 때만 멈춘다. 드물게 고리 1개를 더 보는 변형이라 TAC-F16-1 비트 동일성에 해롭지 않다. 두 번째 종료 조건은 그대로다. 고리 탐색은 질의점에서 점유 셀 범위까지의 첫 고리(`FirstOccupiedRing`)부터 시작해 빈 고리를 건너뛴다(원거리 질의 최적화). 해시된 몬스터가 0이면 고리 탐색 없이 큰 몬스터만 본다(5.7).
- TAC-F16-3 (2회차 재작성, A6): `Physics2DTargetProvider`가 켜져 있으면 BuildIndex order 5에서 `PhysicsBodySynchronizer.SyncMonstersForQuery()`가 모든 몬스터 바디의 `Rigidbody2D.position`을 스냅샷 위치로 직접 대입한다((10회차) 이전 회차의 `Physics2D.SyncTransforms()` 1회 호출은 불필요 — 실측 U32: Script 모드에서 `rb.position` 대입은 즉시 `OverlapCircle`에 반영된다). 그래서 질의 시점의 물리 위치 = 스냅샷 위치다. 질의는 `Physics2D.OverlapCircle(point, R, filter{Monster 레이어, useTriggers}, results)`를 반경 4부터 두 배씩 넓히되 상한은 "질의점에서 스냅샷 AABB의 가장 먼 꼭짓점까지 거리"다. 후보가 생기면 `R = √bestD2 + 1e-3`으로 한 번 더 질의하고, 최종 선택은 스냅샷 위치와 R6으로 한다(콜라이더 겹침 판정은 중심 거리 ≤ R인 몬스터를 모두 포함하는 상위 집합이다) [실측 U11·U32].
- TAC-F16-4: 공간 해시 셀 크기는 `SpatialHashSettings.CellSize`(기본 [기본값] 2.0) 코드 상수이며, 개발자 모드에서 다음 판부터 바꿀 수 있고 측정 헤더 `cellSize`에 기록된다. (13회차) 기본값 2.0의 단일 소유자는 Core `StrategySelection.DefaultSpatialHashCellSize`이며 `SpatialHashSettings.CellSize`는 그 상수를 참조한다(5.7·5.15).
- TAC-F16-5 (2회차 수정, 11회차 정정): 타깃 공급자는 판 진행 중에 `SwitchTargetProvider` 대기 명령으로 바꾼다. (11회차, 참조 방향) 명령은 `SwitchTargetProviderCommand`(5.7)로, App이 만든 새 공급자 인스턴스(`ITargetProvider`)와 요구사항 적용 콜백을 담는다(개발자 모드는 `IDevModeHost.RequestTargetProviderSwitch(kind)`를 부른다). 다음 스텝 `Begin`(order 0)에서 `PendingCommandQueue`가 `TargetProviderSlot.Replace(command.Provider)` 뒤 `command.ApplyRequirements()`만 호출한다. 콜백(App 구성)이 `MonsterSpatialIndex.Required`를 다시 계산하고 `PhysicsBodySynchronizer.ApplyRequirements(R19)`를 부른다(Physics2D로 바꾸면 활성 몬스터 콜라이더를 ID 순으로 켠다). `PendingCommandQueue`는 Strategies 형식을 참조하지 않는다. 나머지 3개 전략은 다음 판 `Reset`에서 적용한다(SPEC 3.0 B) (EM: 가짜 공급자·카운터 콜백으로 Begin에서 교체 1회·콜백 1회·순서 교체 → 콜백 / 코드 리뷰: Simulation 어셈블리에 `Survivor.Strategies` 참조 없음).
- TAC-F16-6 (2회차 신규, B, 3회차 수정): 공간 해시에서 빠지는 "큰 몬스터"는 `MonsterSizeRules.IsLarge(radius, isBoss)`(R25, `radius > GameRules.LargeMonsterRadiusThreshold ∥ behavior == boss`)로 정한다. 보스는 반지름과 무관하게 항상 큰 몬스터다(SPEC F16 "보스는 공간 해시에 들어가지 않는다"). JSON으로 반지름이 큰 일반 몬스터를 추가해도 같은 경로를 탄다 (EM).

### F17. Update 집중화

(15회차) 구현 확인됨(EM, 게이트 닫힘 중 무동작은 PM `FixedStepLoopTests`).

### F18. 충돌 판정

- TAC-F18-1: 채널 9개(5a R5)만 판정한다. 엔진판은 레이어 매트릭스(R30)로, 자체판은 채널 표로 같은 쌍만 본다 [실측 U12].
