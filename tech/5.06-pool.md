### 5.6 풀 전략과 템플릿 데코레이터 (Core 계약, IMP-POOL·IMP-COLLISION·IMP-LOOP 구현) (2회차 수정, A8)

```csharp
namespace Survivor.Core
{
    public enum PoolStrategyKind { InstantiateDestroy = 0, CustomPool = 1, UnityObjectPool = 2 }

    /// Supplies inactive-to-active GameObjects; never touches gameplay state.
    public interface IPoolStrategy
    {
        PoolStrategyKind Kind { get; }
        GameObject Acquire(GameObject template, Vector2 position);   // returned object is active at position
        void Release(GameObject instance);                           // throws InvalidOperationException on double release / foreign object
        void Prewarm(GameObject template, int count);                // no-op for InstantiateDestroy
        void ReleaseAll();                                           // run reset: every active instance released (B: destroyed)
        int ActiveCount { get; }
    }

    /// Hook that lets Strategies attach their components to entity templates without Simulation referencing Strategies.
    public interface IEntityTemplateDecorator
    {
        void Decorate(GameObject template, EntityCategory category);   // called once per template at bootstrap
    }
}
```

- 템플릿은 `PrefabCatalog`(Simulation, IMP-LOOP)가 부트스트랩에서 코드로 만든 비활성 `GameObject`다(카테고리별 8종). `PrefabCatalog`가 직접 붙이는 것은 `SpriteRenderer`와 카테고리별 `SimEntity` 파생 컴포넌트뿐이다. **(2회차) 나머지는 조립 루트가 주입한 데코레이터 목록이 붙인다**:
  - `PoolTemplateDecorator`(IMP-POOL): `PooledObject`(템플릿 참조와 활성 플래그).
  - `CollisionTemplateDecorator`(IMP-COLLISION): 비활성 `CircleCollider2D`(isTrigger) + `Rigidbody2D`(Kinematic, `simulated = false`) + `CollisionBodyLink`, 레이어 = R30.
  - `SelfTickTemplateDecorator`(IMP-LOOP): `Monster` → 비활성 `MonsterSelfTicker`, `PlayerProjectile`·`EnemyProjectile` → 비활성 `ProjectileSelfTicker`.
  데코레이터는 전략 선택과 무관하게 전부 적용된다(TAC-F9-7). 그래서 전략이 바뀌어도 템플릿을 다시 만들 필요가 없다.
- 레지스트리 항목에 프리팹 덮어쓰기가 있으면 그 프리팹을 복제한 뒤 같은 데코레이터를 적용한다(F11).
- `PoolPrewarmCounts`(Simulation 상수) [Q13]: Monster 450, PlayerProjectile 300, EnemyProjectile 100, PlayerOrb 16, PlayerZone 16, EnemyZone 8, Gem 600, Chest 16. 측정 후 조정한다.

#### 5.6.1 구현 확정 사실 (14회차, 웨이브 2a IMP-POOL, main d06b0bb)

코드(`Scripts/Strategies/Pool/*`)에서 읽어 옮긴 것이다. 설계 변경은 없다. 네임스페이스는 `Survivor.Strategies.Pool`이다.

```csharp
namespace Survivor.Strategies.Pool
{
    /// ★ (rev 14) Pool bookkeeping attached to every entity template.
    [DisallowMultipleComponent]
    public sealed class PooledObject : MonoBehaviour
    {
        public GameObject Template { get; internal set; }   // null on the template itself and before the first Acquire
        public bool IsActive { get; internal set; }         // true while acquired
        internal object Owner { get; set; }                 // strategy that last handed it out (foreign-release check)
        internal long AcquireSerial { get; set; }           // acquire order inside the owner (deterministic ReleaseAll)
    }

    public sealed class PoolTemplateDecorator : IEntityTemplateDecorator
    {
        public void Decorate(GameObject template, EntityCategory category);   // adds PooledObject once (idempotent); null -> ArgumentNullException
    }

    public sealed class CustomPoolStrategy : IPoolStrategy { public CustomPoolStrategy(); }            // A: per-template Stack (LIFO)
    public sealed class InstantiatePoolStrategy : IPoolStrategy { public InstantiatePoolStrategy(); }  // B: Instantiate / SetActive(false) + Destroy
    public sealed class UnityObjectPoolStrategy : IPoolStrategy { public UnityObjectPoolStrategy(); }  // C: per-template ObjectPool<GameObject>

    /// ★ (rev 14) Shared by the three strategies (composition, not a base class).
    internal sealed class PoolInstanceTracker
    {
        internal PoolInstanceTracker(object owner);
        internal int ActiveCount { get; }
        internal static void ValidateTemplate(GameObject template);
        internal static void ValidatePrewarm(GameObject template, int count);   // count < 0 -> ArgumentOutOfRangeException
        internal static GameObject CreateInstance(GameObject template);
        internal GameObject MarkAcquired(GameObject template, GameObject instance, Vector2 position);
        internal GameObject MarkReleased(GameObject instance);                   // returns the template
        internal List<GameObject> SnapshotActiveInAcquireOrder();
        internal static InvalidOperationException Fail(string message);          // logs "[HH:mm:ss.fff] [ERROR] [Pool] ..." and returns the exception
    }
}
```

- **공유 도우미 `PoolInstanceTracker`(internal)**: 템플릿 검증, 활성 집합, 반환 검증(중복·남의 객체)을 세 전략이 합성으로 공유한다. 공개 추상 기반 클래스는 공개 타입을 늘리고, internal 기반 클래스는 public 파생 클래스의 기반으로 쓸 수 없어(CS0060) 합성을 택했다.
- **`PooledObject.Template`**: 템플릿 자체에서는 null이고 첫 `Acquire` 때 채워진다. `Instantiate`는 비직렬화 값을 복사하지 않고, 자기 참조는 클론 자신으로 바뀌기 때문이다.
- **`PoolTemplateDecorator.Decorate`**: 여러 번 불러도 `PooledObject`는 1개다. `template == null`이면 `ArgumentNullException`. `category`는 결과에 영향을 주지 않는다.
- **템플릿 검증(`Acquire`·`Prewarm` 공통)**: null → `ArgumentNullException`. 활성 상태 템플릿, 또는 `PooledObject`가 없는 템플릿 → `InvalidOperationException`. 따라서 LOOP `PrefabCatalog`가 데코레이터를 적용하기 전에 풀을 부르면 즉시 예외다. `Prewarm`의 `count < 0`은 `ArgumentOutOfRangeException`이다(B도 같은 검증 뒤 아무것도 하지 않는다).
- **반환 검증(`Release`)**: `Release(null)` → `ArgumentNullException`. 파괴된 객체의 반환은 중복 반환으로 간주해 `InvalidOperationException`. `PooledObject`가 없거나 `Owner`가 이 전략이 아닌 객체(남의 객체) → `InvalidOperationException`. 이미 반환된 객체 → `InvalidOperationException`. **반환 규칙 위반(중복·남의 객체·파괴됨)만 `Debug.LogError`(`[HH:mm:ss.fff] [ERROR] [Pool] …`, 객체 이름과 `GetInstanceID()`)를 남긴 뒤 던지고, 인자 오류(null·음수 count·템플릿 검증)는 로그 없이 예외만 던진다.** U21 실측대로 `ObjectPool`의 `collectionCheck`는 남의 객체를 잡지 못하므로 Owner 검사가 필수다(6.2 U21).
- **`Acquire` 순서**: 위치를 먼저 대입하고 `SetActive(true)`한다(`OnEnable`이 이미 새 위치를 본다). 상태 리셋은 없다(TAC-F9-6, 색·스케일 유지 테스트로 확인).
- **C(`UnityObjectPoolStrategy`)**: 템플릿별 `ObjectPool<GameObject>`(`collectionCheck: true`, `maxSize: int.MaxValue`, `defaultCapacity: 10`, `actionOnDestroy: Object.Destroy`). `ObjectPool`에 사전 생성 API가 없어 `Prewarm`은 기존 비활성 + 새 count개를 `Get`한 뒤 역순으로 `Release`한다(기존 스택 순서 유지, 새 인스턴스는 아래). `ObjectPool.Release`가 던지는 예외는 로그 뒤 `InvalidOperationException`으로 감싼다(방어용 — 트래커가 먼저 막으므로 실제로는 도달하지 않는다).
- **`ReleaseAll`**: 세 전략 모두 `AcquireSerial` 순(획득 순서)으로 `Release`한다(`HashSet` 순서에 의존하지 않음). B는 그 결과로 전부 파괴된다(1프레임 뒤, U22).
- **프로파일러**: 세 전략 모두 `ProfilerMarkers.Pool.Auto()`로 `Acquire`·`Release`를 감싼다. `Prewarm`·`ReleaseAll` 자체는 감싸지 않는다(`ReleaseAll`은 안에서 부르는 `Release`마다 마커가 열린다).
- (14회차, 각주 — **PM 결정 대기**) 풀 전략 토글(TAC-F9-7, 다음 판 `Reset`) 때 옛 A·C 전략 객체가 보유한 비활성 인스턴스가 씬에 남는다. `IPoolStrategy`에 정리 수단이 없다. 후보 (a) `Dispose`/`Clear` 추가 (b) App이 옛 전략의 비활성 인스턴스 파괴 (c) 누적 허용 — 06 6.1 끝의 (14회차) 미결 설계 항목. 15회차에 반영 예정.
- (14회차, 각주) `collectionCheck: true`의 비용(반환마다 O(n) 탐색인지)은 미측정이다. F10 측정에서 C에 불리하게 작용할 수 있다(6.2 U21 "남은 미확인").
