- 이름 접두사는 쓰지 않는다. 네임스페이스와 asmdef로 충돌을 막는다. 다만 **클래스명은 프로젝트 전체에서 고유**해야 한다(Unity가 MonoBehaviour를 파일명으로 찾으므로, CODING_GUIDE §2.2).

#### 5c.2a 기능별 필수 기록 초안 의무 (2회차 신규, SPEC F14 4회차 매핑 표, 3회차 수정)

SPEC F14는 "기능별 필수 기록이 없으면 그 기능은 미완료"라고 정했고, 기록 시점은 "기능 브랜치 머지 커밋에 해당 devlog/README 변경이 포함된다"로 검증한다. 기록 파일(`README.md`, `docs/devlog.md`)의 소유자는 doc-writer·사용자이므로, 구현자는 **완료 보고에 초안을 담는다**. (3회차) **구현자의 기록 초안은 해당 기능 브랜치 머지 전에 소유자(doc-writer 또는 사용자)가 README/devlog에 반영해 같은 머지 커밋에 포함한다.** 반영되지 않은 채 머지하지 않는다. team-lead는 초안이 없거나, 머지 커밋에 해당 기록 변경이 없으면 그 구현 작업을 완료로 받지 않는다. 측정 결과(가설에 대한 결과·해석)는 사용자가 측정을 마친 시점의 별도 커밋으로 devlog에 추가한다(측정은 ~~웨이브 6~~ (20회차 번호 이동) ~~웨이브 7~~ (21회차 번호 이동) 웨이브 8 이후 사용자 수행이므로).

### 5c.3 계층 간 핵심 계약 요약 (구현자가 반드시 지킬 것)

1. (2회차 수정) 엔티티 생성·회수는 Lifecycle 단계에서 `EntityLifecycle.Spawn/Despawn`만 쓴다(R11). 다른 단계에서는 `SimulationCommand`를 넣는다. 풀·ID 할당기·물리 바디를 직접 부르지 않는다. (16회차, 명시적 예외 [기본값]) 플레이어는 풀 엔티티가 아니므로 `PlayerEntity`(IMP-PLAYER)가 몸·자석 바디를 직접 만들고 할당기에서 1:1·2:1을 받아 현재 `ICollisionStrategy`·`IPhysicsBodyRegistry`에 직접 등록·해제한다(판 리셋에서만, 5.12 `PlayerEntity`·TAC-F8-2).
2. (2회차 수정) `IUpdatable.Tick`은 자기 상태만 쓰고, 부작용은 `context.Commands.Enqueue`로 넘긴다. 생성 스텝에는 Tick이 오지 않는다(5.4).
3. 집합 순회·피해 적용은 `EntityHandle` 오름차순이다(R10). `Dictionary`/`HashSet`를 순서가 중요한 곳에서 순회하지 않는다.
4. 시간은 스텝 정수, 속도는 스텝당 값으로만 계산한다. 초 단위 상수가 코드에 나타나면 안 된다(R1·R3).
5. 난수는 `RngStreams.Get(stream)`만 쓴다. 스트림 배정: 스폰 종·각도 = Spawn, 소환 각도 = Summon, 상자 드랍 = Drop, 상자 효과 = Chest, 레벨업 = LevelUp.
6. 위치의 원본은 `SimEntity.Position`이다. `transform.position`은 `PresentationSync.LateUpdate`(실행 순서 −100)가 프레임당 1회 쓴다. 단 `Body.DrivesTransform == true`인 엔진 모드 바디는 쓰지 않는다 [실측 U10]. `Rigidbody2D`·`Collider2D`는 `PhysicsBodySynchronizer`만 만진다(5.9.1). (18회차, 웨이브 4c 결함 B — U10 확인) `DrivesTransform = Enabled && Link.Sink != null`이고 동기화기가 갱신한다(엔진판 `Register`·`Unregister`·`Clear`가 ★ internal `RefreshDrivesTransform`을 부름, 5.9). 종전에는 이 값이 항상 거짓이라 `PresentationSync`가 엔진 바디 `transform`을 썼고, 다음 `Simulate`가 그것을 텔레포트로 취급해 그 스텝의 `MovePosition`을 버렸다(엔진판이 한 스텝 늦음). 이 규칙의 준수자는 `PresentationSync`(LOOP)와 `PlayerPresenter`(App) 둘이다. `EntityPresenter`·`CameraFollow`·`BackgroundTiler`는 host 위치를 쓰지 않는다(자식 `"Visual"` 배율·카메라·배경만).
7. (2회차 수정) 오류 규약: 계약 위반(중복 반환, 같은 채널에 핸들러 두 번 등록, 같은 순서값의 단계 핸들러, Lifecycle 밖 생성, 스텝 밖 `CloseAfterCurrentStep` 등)은 `InvalidOperationException`을 던진다. 데이터 오류는 던지지 않고 `DataValidationReport`에 넣는다. 런타임의 예상 가능한 실패(타깃 없음 등)는 `bool Try...` 패턴으로 처리한다. 예외를 잡는 곳은 드라이버 3개 각각 한 곳이고, 잡으면 `[HH:mm:ss.fff] [ERROR] [Loop] phase=<단계> step=<n> <예외형>: <메시지>`((15회차 정정) 이 형식과 #8의 Area를 합친 것 — 구현 `LoopLog.PhaseError`, PM 테스트가 정규식으로 단언. 14회차까지는 `[시각] [ERROR] phase=<단계> step=<n> <메시지>`)를 남긴 뒤 `SimulationClock.AbortStep()`(그 스텝 중단, 게이트 `Error`로 닫힘)을 부르고, FLOW가 결과 화면이 아니라 오류 표시로 간다(CODING_GUIDE §4·§5). (15회차, **[기본값]**으로 명문화) 객체별 틱(F17 A)의 셀프 티커 `FixedUpdate` 안 예외는 드라이버가 잡지 못해 `AbortStep`이 일어나지 않는다(Unity 로그만 남고 스텝은 계속된다). `IUpdatable.Tick`의 예외는 계약 위반이며 중앙 틱 모드 결정론 테스트에서 드러난다. 처리 변경 없음.
8. 로그 형식: `[HH:mm:ss.fff] [LEVEL] [Area] message` (Area = Data/Loop/Pool/Collision/Flow/Dev). 판 시작·종료·레벨업·진화·핫 리로드·전략 변경·측정 시작/종료는 성공해도 한 줄을 남긴다(§5). 스텝마다 남기는 로그는 금지한다(측정 오염). (14회차) Core에 공용 포매터는 없고, 영역별 internal 도우미가 이 형식을 지킨다(웨이브 2a: Data `DataLog`, Pool `PoolInstanceTracker.Fail`). 타임스탬프 `DateTime.Now`는 로그 전용이며 결정론 금지 목록(TAC-0-2)의 예외다. ~~(공용 포매터로 통합할지는 PM이 LOOP 전에 검토한다 — 14회차는 정하지 않는다.)~~ (15회차) PM 확정: 영역별 internal 도우미 유지(Data `DataLog`, Pool `PoolInstanceTracker.Fail`, Loop `LoopLog`; 뒤 웨이브도 같은 방식). (15회차, 기준선 — 웨이브 2b에서 확인, 뒤 웨이브 구현자 전원) EditMode 테스트 asmdef는 Editor 전용 플랫폼이라 **그 안에 정의한 `SimEntity` 파생 테스트 더블은 `AddComponent`할 수 없다**(오류 "Can't add script behaviour … because it is an editor script"). 런타임 어셈블리(Simulation·Strategies)의 컴포넌트(셀프 티커, `KeyboardInputSource`)는 EditMode에서도 `AddComponent`되고, `Instantiate`도 EditMode에서 된다. 실물 풀의 `Clear`는 `Object.Destroy`를 쓰므로 EditMode에 맞지 않는다. 그래서 엔티티가 필요한 테스트(생명주기·수명·레지스트리·카탈로그·Despawn 핸들러)는 PlayMode `[Test]`로 둔다(TAC-0-8·0-9·0-10의 "생명주기 부분은 PM").
