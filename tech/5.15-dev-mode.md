### 5.15 개발자 모드 주입 경계와 측정 (Dev, IMP-DEV)

게임 쪽에 미리 있어야 하는 주입 지점(이 지점들은 개발자 모드가 꺼져 있어도 존재하는 "값"이다):

```csharp
namespace Survivor.Core
{
    /// Runtime-tunable values read by gameplay; defaults equal normal play. Dev mode only mutates these.
    public sealed class SimulationRules
    {
        public int MonsterCap = GameRules.MonsterCapDefault;          // 400; dev may set int.MaxValue
        public float DespawnDistance;                                 // from spawnTable.json; dev overrides via R26
        public bool DespawnDistanceOverridden;                        // (rev 2) hot reload keeps the override
        public bool PlayerTakesDamage = true;
        public bool WeaponsEnabled = true;
        public bool LevelUpEnabled = true;
        public long StopAtStep = long.MaxValue;
        public bool RecordBestTime = true;                            // (rev 2) dev attach sets false (SPEC F8)
        public bool AutoPauseOnFocusLoss = true;                      // (rev 2) measurement sets false (SPEC F8·F19)
        public float ChestDropChance = GameRules.ChestDropChance;     // (rev 3) 0.02; measurement presets set 0 (SPEC F10)
    }

    public interface ISpawnPolicy   // normal: TableSpawnPolicy (IMP-MONSTER); dev: DevSpawnPolicy
    {
        /// Fills spawn requests for this step; MonsterSpawner applies cap and placement.
        void CollectSpawns(in StepContext context, int liveMonsterCount, DeterministicRng spawnRng, List<string> monsterIdsOut);
        bool BossSpawnDue(long step);
    }

    public readonly struct StrategySelection
    {
        public readonly PoolStrategyKind Pool; public readonly TargetProviderKind Target;
        public readonly TickStrategyKind Tick; public readonly CollisionStrategyKind Collision;
        public readonly CollisionDetectionMode2D EngineDetectionMode;   // Discrete by default
        public readonly float SpatialHashCellSize;                      // (rev 2) recorded as cellSize
        public const float DefaultSpatialHashCellSize = 2f;             // (rev 13) single owner of the 2.0 default; SpatialHashSettings.CellSize references it (TAC-F16-4)
        public StrategySelection(                                       // (rev 13)
            PoolStrategyKind pool,
            TargetProviderKind target,
            TickStrategyKind tick,
            CollisionStrategyKind collision,
            CollisionDetectionMode2D engineDetectionMode = CollisionDetectionMode2D.Discrete,
            float spatialHashCellSize = DefaultSpatialHashCellSize);
        public static StrategySelection ShippingDefault { get; }        // CustomPool, SpatialHash, CentralTick, SelfSquaredDistance
        public static StrategySelection Baseline { get; }               // InstantiateDestroy, BruteForce, PerObjectFixedUpdate, EngineCollider2D
    }
}

(14회차) 반영 확인됨(main d06b0bb, `public const`).
- (3회차) `InputOverride`·`SpawnPolicyOverride`는 값을 바꿔도 진행 중인 판에는 적용되지 않고 다음 `Reset`(판 시작)에서 1회 바인딩된다(TAC-F8-2 ④). 그래서 개발자 모드가 꺼진 플레이에서는 스텝마다 오버라이드 null 검사가 돌지 않는다(SPEC F19 "비활성 상태에서는 분기 없음"). (17회차, 웨이브 3 구현 확정) 바인딩 메서드: `MonsterSpawner.Bind(SpawnPolicyOverride ?? new TableSpawnPolicy(dataRegistry))`, `PlayerMovement.SetInputSource(InputOverride ?? keyboard)`(5.12·5.12.1, 순서는 5.14 `RunSession` 각주).

`PendingCommandQueue`(Simulation, Begin order 0) 명령 종류: `SetLoadout`, `SetHealth`, `AddXp`, `LevelUpNow`(다음 레벨까지 경험치 추가), `SpawnMonstersNow`(SimulationCommand로 변환), `SpawnBossNow`, `SpawnChestNow`, `SwapData`, `SwitchTargetProvider`((11회차) 내용은 5.7 `SwitchTargetProviderCommand` — App이 공급자와 요구사항 콜백을 담아 넣는다), `SetDespawnDistance`. (11회차) `SpawnBossNow`는 `MonsterSpawner`의 "이번 판 보스 생성됨" 플래그(5.12.1)가 이미 서 있으면 거부하고(명령은 소비, 보스 생성 명령을 넣지 않음), 오버레이에 "보스는 판당 1기"를 표시한다. 판정은 `PendingCommandQueue`가 Begin에서 ★ `MonsterSpawner.BossSpawnedThisRun`(읽기 전용, 11회차 PM 승인, 5.12.1)을 읽어 한다. 개발자 명령 결과를 돌려주는 경로나 `IDevModeHost`의 알림 수단은 기존에 없으므로, 오버레이 표시는 시간 점프 거부(TAC-F19-3)와 같은 방식으로 `DevController`가 명령을 넣기 전에 ★ `IDevModeHost.BossSpawnedThisRun`(App `GameBootstrap`이 `MonsterSpawner.BossSpawnedThisRun`을 그대로 돌려줌, Dev → App → Simulation)을 읽어 참이면 "보스는 판당 1기"를 표시한다(그 경우 명령을 넣지 않는다. 넣더라도 `PendingCommandQueue`가 다시 거부한다).

(15회차, 웨이브 2b 구현 확정 — main b9f8ea5, `Scripts/Simulation/Loop/PendingCommandQueue.cs`·`PendingCommand.cs`·`PendingCommandKind.cs`) 큐와 명령 페이로드의 구현 시그니처(★ = 구현이 정한 것):

```csharp
namespace Survivor.Simulation
{
    /// ★ (rev 15) Kind of a between-steps command (this order = the list above).
    public enum PendingCommandKind
    { SetLoadout = 0, SetHealth = 1, AddXp = 2, LevelUpNow = 3, SpawnMonstersNow = 4, SpawnBossNow = 5,
      SpawnChestNow = 6, SwapData = 7, SwitchTargetProvider = 8, SetDespawnDistance = 9,
      SetSpawnsEnabled = 10 }   // ★ (rev 21, wave 6a IMP-MONSTER line-level) owner kind -> MonsterSpawner.HandleSetSpawnsEnabled (5.12.1)
    //   ★ (rev 22, wave 7 IMP-PLAYER line-level) + SetPassiveLoadout = 11 — owner kind -> PlayerProgressionApplier.HandleSetPassiveLoadout (5.14)

    /// ★ (rev 15) One between-steps command; build it with the static factories (fields used depend on Kind).
    public readonly struct PendingCommand
    {
        public readonly PendingCommandKind Kind;
        public readonly string DefinitionId;      // SpawnMonstersNow, SpawnBossNow
        public readonly int Count;                // monster count (SpawnMonstersNow) or XP amount (AddXp)
        public readonly Vector2 Position;         // SpawnMonstersNow, SpawnBossNow, SpawnChestNow
        public readonly float Radius;             // SpawnMonstersNow ring radius
        public readonly bool IgnoreCap;           // SpawnMonstersNow
        public readonly float Value;              // health (SetHealth) or D (SetDespawnDistance)
        public readonly object Payload;           // SetLoadout loadout, defined by the handler's owner (PLAYER); opaque to the queue
        public readonly GameData Data;            // SwapData
        public readonly DataValidationReport Report; // SwapData
        public readonly SwitchTargetProviderCommand TargetSwitch; // SwitchTargetProvider (5.7)
        public static PendingCommand SetLoadout(object loadout);
        public static PendingCommand SetHealth(float health);
        public static PendingCommand AddXp(int xp);
        public static PendingCommand LevelUpNow();
        public static PendingCommand SpawnMonstersNow(string definitionId, int count, Vector2 position, float radius, bool ignoreCap); // count <= 0 -> ArgumentOutOfRangeException
        public static PendingCommand SpawnBossNow(string definitionId, Vector2 position);
        public static PendingCommand SpawnChestNow(Vector2 position);
        public static PendingCommand SwapData(GameData data, DataValidationReport report);   // report null -> ArgumentNullException
        public static PendingCommand SwitchTargetProvider(in SwitchTargetProviderCommand command); // no provider -> ArgumentException
        public static PendingCommand SetDespawnDistance(float distance);  // not positive or infinite -> ArgumentOutOfRangeException
        public static PendingCommand SetSpawnsEnabled(bool enabled);      // ★ (rev 21) Count = enabled ? 1 : 0 (no new field)
        public static PendingCommand SetPassiveLoadout(object loadout);   // ★ (rev 22) Payload = IReadOnlyList<PassiveLoadoutEntry> (PLAYER's format)
    }

    /// Begin order 0: applies the commands queued outside the step in queue order (TAC-0-1).
    public sealed class PendingCommandQueue : IStepPhaseHandler
    {
        public PendingCommandQueue(TargetProviderSlot targets, GameDataRegistry data, SimulationRules rules); // ★ (rev 15)
        public Func<bool> BossSpawnedThisRun { get; set; }   // ★ (rev 15) composition root wires MonsterSpawner.BossSpawnedThisRun; null = "not spawned"
        public int PendingCount { get; }                     // ★ (rev 15)
        public static bool IsOwnerHandled(PendingCommandKind kind);   // ★ (rev 15) true for SetLoadout, SetHealth, AddXp, LevelUpNow
                                                                      //   (rev 21) + SetSpawnsEnabled; KindCount = SetSpawnsEnabled + 1
                                                                      //   (rev 22) + SetPassiveLoadout; KindCount = SetPassiveLoadout + 1
        public void RegisterHandler(PendingCommandKind kind, Action<PendingCommand, StepContext> handler); // ★ (rev 15)
        //   owner kinds only: built-in kind -> ArgumentException, second handler -> InvalidOperationException, null -> ArgumentNullException
        public void Enqueue(in PendingCommand command);      // ★ (rev 15) owner kind without a handler -> InvalidOperationException at enqueue time
        public void Enqueue(in SwitchTargetProviderCommand command);  // (rev 11, 5.7) = Enqueue(PendingCommand.SwitchTargetProvider(command))
        public void Clear();                                 // ★ (rev 15) run reset (TAC-F8-2 ④): drops queued commands, handlers stay
    }
}
```

- **소유자 종류**(`IsOwnerHandled` = `SetLoadout`·`SetHealth`·`AddXp`·`LevelUpNow`)는 ~~PLAYER·FLOW가 `RegisterHandler`로 핸들러를 등록한다~~ → (16회차 정정, 배선 규칙 통일) **조립 루트(App, IMP-FLOW 웨이브 4)가 `RegisterHandler`로 등록한다.** 소유자(PLAYER·FLOW)는 핸들러가 부를 메서드만 공개하고 등록 코드를 갖지 않는다(5c.3 #9 메모). 핸들러가 `StepContext`를 받는 이유는 `SetLoadout`이 `context.Step`을 첫 보유 규약(TAC-F2-2, 5.14)에 써야 하기 때문이다. 핸들러 본문의 대상은 5.14 소유 그대로다: `SetLoadout` → `PlayerProgressionApplier.SetLoadout`(PLAYER, `Payload`를 자기 형식으로 해석), `SetHealth` → `PlayerProgressionApplier.SetHealth`(PLAYER), `AddXp` → `ExperienceSystem.AddXp(Count)`(FLOW), `LevelUpNow` → `ExperienceSystem`(FLOW), (21회차) `SetSpawnsEnabled` → ★ `MonsterSpawner.HandleSetSpawnsEnabled`(MONSTER, 등록 1줄은 조립 루트 `GameBootstrap.cs:318` 뒤 — 웨이브 6a IMP-MONSTER 줄 단위, 5.12.1·5c.2), (22회차) `SetPassiveLoadout` → ★ `PlayerProgressionApplier.HandleSetPassiveLoadout`(PLAYER, 등록 1줄은 `GameBootstrap.cs:320` 뒤 — 웨이브 7 IMP-PLAYER 줄 단위, 5.14 22회차·5c.2). (16회차 **[기본값]**) `LevelUpNow`에는 새 API가 없다: 핸들러가 `exp.AddXp(XpCurve.RequiredForNext(exp.Level, curve) − exp.Xp)`(`curve` = `GameDataRegistry.Current`의 `PlayerStatsDefinition.XpCurve`; Data의 실제 시그니처는 `XpCurve.RequiredForNext(int level, XpCurveDefinition def)`)를 부르고, 같은 스텝 Lifecycle order 90의 `StepOutcomeGate`가 `TryBeginLevelUp`으로 레벨업을 연다.
- **내장 종류**는 큐가 직접 처리한다: `SpawnMonstersNow` → `SimulationCommand(SpawnMonsters, Source = None)`, `SpawnBossNow` → `SimulationCommand(SpawnMonsters, count 1, ignoreCap: true, 반지름 0)`(`BossSpawnedThisRun()`이 참이면 Info 로그 "SpawnBossNow refused …" 뒤 소비), `SpawnChestNow` → `SimulationCommand(SpawnChest)`, `SwapData` → `GameDataRegistry.TrySwap(Data, Report)`(거부되면 Warning 로그, 현재 데이터 유지), `SwitchTargetProvider` → `TargetProviderSlot.Replace` → `ApplyRequirements()`(5.7), `SetDespawnDistance` → `Rules.DespawnDistance = Value`, `Rules.DespawnDistanceOverridden = true`. Begin에서 적용 중에 들어온 명령은 다음 Begin으로 넘어간다.
- (15회차, PM **[기본값]**) `SwapData`는 D(`SimulationRules.DespawnDistance`)를 건드리지 않는다. `SimulationRules.DespawnDistanceOverridden`이 거짓이면 **D의 소비자(MONSTER `DespawnSystem`, 5.12.1)가 참조할 때마다 `GameDataRegistry.Current`의 스폰 테이블 D(`SpawnTable.DespawnDistance`)를 읽는다** — 5c.3 #10 "스폰 테이블은 참조할 때마다 `Current`를 읽는다"의 적용이며 새 규칙이 아니다. 참이면 `SetDespawnDistance`가 쓴 `Rules.DespawnDistance`를 쓴다.

#### 5.15.1 배속 (2회차, A2)

`DevController.SetTimeScale(x)`는 `Mathf.Clamp(x, 0.25f, 3f)`를 `Time.timeScale`에 쓴다. (10회차, D9 변경, 실측 U23) 이어서 `Time.maximumDeltaTime = StepMath.MaxCatchUpSteps * StepMath.StepSeconds / Time.timeScale`(= 0.05 / timeScale)로 갱신해 스케일 후 프레임당 최대 3스텝을 유지한다(5.3 배속). 1x로 되돌릴 때도 같은 함수를 거쳐 0.05로 돌아간다(판 진행 중에는 `Time.timeScale`을 이 함수 밖에서 쓰지 않는다). (11회차) 판 시작마다 `timeScale = 1`, `maximumDeltaTime = 0.05`로 초기화한다. 배속은 판 사이에 유지하지 않는다(측정 판이 이전 판의 배속을 물려받지 않게). ~~이 초기화는 판 시작 경로의 App 코드가 `RunSession.Reset(in RunStrategies)` 직후, `Open` 전에 한다(TAC-F8-2의 App 조율 단계, 개발자 모드 유무와 무관).~~ (19회차 정정, PM [기본값] — DECISIONS 9절) App은 하지 않는다(코드에 없고 추가하지 않는다). **Dev가** `IDevModeHost.RunEnded` 처리와 자기 `StartNewRun` 호출 경로에서 `Time.timeScale = 1`, `Time.maximumDeltaTime = StepMath.MaxCatchUpSteps * StepMath.StepSeconds`로 되돌린다. 배속을 바꾸는 것은 개발자 모드뿐이므로 개발자 모드가 없으면 초기화도 필요 없다. 실제 배속 = 최근 1초(비스케일) 동안의 `SimulationFrameCounter.LastFrameSteps` 합 / 60((19회차) Dev는 ★ `IDevModeHost.LastFrameSteps`로 읽는다). ((15회차 정정, 코드대로 명문화 — Dev 구현 전이라 설계 변경이 아니라 읽을 값의 정정) 14회차까지는 `StepsThisFrame` 합이라 적었으나, 플레이어 루프에서 `FixedUpdate`가 `Update`보다 먼저 돌고 `SimulationFrameCounter.Update`(order −10000)가 그 값을 0으로 되돌리므로 `Update`·`LateUpdate`·코루틴에서 읽으면 항상 0이다. 되돌리기 직전 값이 ★ `LastFrameSteps`다, 5.3.) 측정 중에는 1로 고정되고 변경 시 세션이 무효가 된다.

#### 5.15.2 측정 세션 절차 (2회차 재작성, A9, 3회차 수정)

1. 사용자가 오버레이에서 프리셋(A0의 N, A1~A6, B1~B8, C1~C2)과 `durationSteps`를 고르고 "측정 시작"을 누른다.
2. `MeasurementGuard.Check`: 시각화 하나라도 켜짐 / 충돌 로그 옵션 켜짐 / `timeScale != 1` / 한 스텝 진행 모드 / (3회차) 프리셋에 고정 무기 구성이 없거나 프리셋의 `ChestDropChance != 0` → 거부, 원인을 오버레이에 표시(SPEC F10·F19 4회차 배제 조건). (21회차, SPEC F19 73행·Q50 ⑪⑯) 카메라 줌은 거부 조건이 **아니다**. **5b 계약**: 가드를 통과한 직후, 3번의 오버레이 숨김보다 먼저 `DevController.ResetZoom()`(orthographic size 9)을 부른다 — 측정 판은 항상 9로 시작한다.
3. 통과하면: 오버레이 숨김 → 환경 적용(vSync 0, targetFrameRate −1, runInBackground true, AutoPauseOnFocusLoss false) → `NextRunSelection = preset`, `NextRunCollisionDecorator = null` → 규칙 설정(고정 시드, LevelUpEnabled false, AutoPath, PlayerTakesDamage false, (3회차) `ChestDropChance = 0`, D = R26(N), N > 400이면 상한 해제) → (3회차) `InputOverride = AutoPathInputSource`, `SpawnPolicyOverride = DevSpawnPolicy`(스폰 중단 + 즉시 N기 + N 유지)를 **판 시작 전에** 설정 → `StartNewRun()`(이 `Reset`에서 두 오버라이드가 바인딩된다) → 0스텝 Begin에 `SetLoadout(프리셋 무기 구성)`.
4. 워밍업·종료: TAC-F19-7. (3회차) 측정 중 상자 드랍은 0%이고, 레벨업 비활성과 함께 무기 구성이 측정 내내 프리셋 그대로 고정된다. 세션 중 무기 구성이 바뀌는 경로(개발자 `SetLoadout`·`SpawnChestNow`)가 실행되면 무효로 처리한다. (17회차) 후보 신호: `PlayerProgressionApplier.ChangeCount`(PLAYER — 무기·패시브가 바뀔 때마다 1 증가, 0스텝 `SetLoadout` 직후 값과 비교하면 이후 변경을 감지한다)(Dev 사용 여부는 IMP-DEV가 정함).
5. 종료 시 CSV 기록(5.15.3) → 환경 복원 → 오버레이 다시 표시.
6. 무효 조건(세션 중 F1, 시각화·배속·로그 변경, (3회차) 무기 구성 변경, (8회차, SPEC F10·F19 8회차) 판 시작 `Open` 이후 게이트가 `Paused`·`RunReset`·`Error`로 닫힘 — `DevModeRoot.Update`가 `clock.CloseSequence`·`CloseReason`으로 감지): 오버레이에 "측정 무효: <원인>"을 표시한다. (8회차 정정) "기록하지 않음"을 고쳐, 무효 세션도 측정 파일(5.15.3)을 쓰고 헤더 `valid = false`, `invalidReason = <원인>`을 남긴다. `summary.csv`에는 추가하지 않는다. 일시정지 중에도 프레임이 돌아 FPS·GC 집계가 오염되기 때문이다. (11회차) 무효가 되는 순간 세션을 **즉시** 끝내고(`StopAtStep`까지 계속 돌지 않는다) 5번 절차를 그대로 수행한다: 측정 파일 기록(`valid = false`, `invalidReason`) → 환경 복원(vSync·targetFrameRate·`runInBackground`·`AutoPauseOnFocusLoss`) → 오버레이 다시 표시.

#### 5.15.3 측정 파일과 열 (2회차 재작성, A1)

측정 1회 = `persistentDataPath/measurements/measurement_<yyyyMMddTHHmmssZ>.csv` 하나. 형식(R28):
- **헤더 블록**: 1열 `key`, 2열 `value`인 행들. 끝에 빈 행 1개.
- **본문 블록**: 열 이름 행 1개 + 값 행 1개.
- 별도로 `measurements/summary.csv`에 헤더 키와 본문 열을 한 행으로 이어 붙여 추가한다(16회 표 작업용, 파일이 없을 때만 BOM과 열 이름 행을 쓴다). (11회차) 같은 `label`이 여러 번 쌓이면 devlog 집계는 그 라벨의 **마지막 유효 행**을 쓴다.
- 프레임 원자료는 `measurements/frames_<timestamp>.csv`(`frame,unscaledDtMs,steps,gcBytes,memUsedMB,liveMonsters,activeGems,<marker>_ms...`). (19회차) 원천: `steps` = ★ `IDevModeHost.LastFrameSteps`, `liveMonsters` = ★ `IDevModeHost.LiveMonsterCount`(`MonsterRegistry.Count` — 전체 생존 몬스터 수, 보스 포함 [기본값]), `activeGems` = ★ `IDevModeHost.ActiveGemCount`(`PickupRegistry.ActiveGemCount`). 본문 `monsterCount*`·`activeGems_*`도 같은 원천이다.

**로드아웃 0~5** (`TrySetLoadout`, 5.12 "로드아웃"의 코드 사실을 받는다)
- `TryPlan` 규칙 **[기본값]**(거부 문자열은 영어, 그대로 커맨드 로그에 남는다):
  1. 요청 항목마다 ID가 비어 있지 않고 `data`에 정의돼 있어야 한다(아니면 `"Unknown weapon '<id>'."`). 진화 전용(`EvolvedOnly`) ID는 거부(`"<id> is an evolved weapon; evolution is the only way to get it."`) — 진화 무기는 이 설정으로 만들거나 지울 수 없다(Q50 ⑱). 단계는 0..`Levels.Count`(아니면 `"<id> has levels 0..<n>."`), 같은 ID 두 번은 거부.
  2. `consumedByEvolution`에 든 ID(진화로 소모된 원본 — 진화 무기는 이 설정으로 지울 수 없으므로 "그 진화 무기를 보유 중"과 같다)를 1 이상으로 요청하면 거부(`"<id> was evolved; set it to 0."`).
  3. 슬롯 배치: 현재 슬롯을 0번부터 보며 — 빈 슬롯은 빈칸, 진화 무기는 **그 슬롯·그 단계 그대로**, 기본 무기는 요청에서 1 이상이면 **그 슬롯 유지**(단계만 요청값), 0이거나 요청에 없으면 빈칸(제거 — 요청에 없는 기본 무기는 미보유, 기존 "empty id = no weapon" 오버레이 의미와 같음). 이어서 요청 순서대로, 아직 놓이지 않은 1 이상 항목을 **빈 슬롯 중 가장 앞 번호**에 넣는다(Q50 ⑱ — 진화 순서는 그 슬롯 번호 기준, F07).

  5. 현재 슬롯의 진화 무기가 `data`에 없으면(핫 리로드로 삭제) 거부(`"<id> is not in the current data."`) — `SetLoadout`이 그 슬롯을 정의 조회하다 예외를 내지 않게.

- 기록 지점: `Done`·`Refuse`를 `Done(string command, string message)`·`Refuse(string command, string message)`로 바꿔(Dev 내부, private) 모든 사용자 조작 경로가 한 줄씩 남긴다 — `SetTimeScale`처럼 `LastMessage`에 직접 쓰는 곳(113행)도 `Done`을 거친다. 시스템 동작(`OnRunEnded`의 `ResetTimeScale`, `Poll`)은 기록하지 않는다. `LastMessage`는 지금처럼 메시지 본문을 유지한다.
- **상자 결과 병합**: ★ `IDevModeHost.ChestResults`(5.15 블록)를 읽는 private `PullChestResults()`를 ① `Poll()` 맨 앞(리셋 감지보다 먼저) ② `Done`/`Refuse`가 줄을 쓰기 직전에 부른다. `_lastChestSequence`보다 큰 `Sequence`만 오래된 것부터 줄로 옮기고 마지막 값을 기억한다(중복 방지 키 = `ChestResult.Sequence`, 판을 넘어도 줄지 않음). ②가 있으므로 같은 스텝이면 명령 줄이 먼저, 상자 줄이 뒤다(명령은 스텝 N 적용 전에 `Clock.Step = N`으로 기록되고, 스텝 N의 상자 결과는 그 뒤에야 생긴다). ①이 매 프레임 돌므로 판 리셋(`ResetForRun`의 `Clear`) 전에 지난 판 결과가 모두 옮겨진다 — 오버레이가 닫혀 있어도 정수 비교 1회의 비용이다(SPEC F19 74행 "기록은 표시 비용 규칙과 충돌하지 않음").
- 상자 줄 **[기본값]**: `"#<run> <step> Chest: <text>"`, `<text>` = 강화 `"<displayName> Lv <from>→<to>"`(SPEC 예 "Chest: 투사체 Lv 3→4", `→` U+2192), 진화 `"<displayName> (evolved)"`, 회복 `"Heal +<amount F1>"`. `displayName` = `Data.Current.TryGetWeapon(TargetId)`의 `DisplayName`, 없으면 `TargetId`. `<step>` = `ChestResult.Step`.
  - (22회차, 웨이브 7 IMP-DEV) ★ `ChestEffect.PassiveUpgraded`(5.14 22회차) 줄은 무기 강화와 **같은 문구** `"<displayName> Lv <from>→<to>"`이고, `displayName`만 `Data.Current.TryGetPassive(TargetId)`의 `DisplayName`(없으면 `TargetId`)이다. 코드 사실: `DevController.ChestText`(`DevController.cs:660~678`)는 `Healed`가 아니면 `TryGetWeapon`으로만 이름을 찾고 `Evolved`가 아니면 강화 문구를 쓴다 — 그대로 두면 패시브 줄은 문구는 맞지만 이름이 ID(`"P1 Lv 1→2"`)로 나온다. 그래서 이름 조회를 `Kind == PassiveUpgraded ? TryGetPassive : TryGetWeapon`으로 나누는 한 군데만 고친다.
- 표시: `DevOverlay` 164~166행을 `CommandLog`의 최신 줄부터 `Count`줄 그리기로 바꾼다. 새 판에 비우지 않고(세션 = `DevController` 수명), 파일로 내보내지 않는다. 로그 기록·표시는 시뮬레이션 상태를 쓰지 않는다.
  - (22회차 수정, 웨이브 7 IMP-DEV, SPEC F19 13회차 74행, DECISIONS 9절 6항 2026-11-11 보강) **커맨드 로그는 별도 콘솔 창에 그린다.** 코드 사실(6b 머지본): `DevOverlay.DrawWindow`가 메인 창(`_window = new Rect(10, 10, 460, 680)`, `GUILayout.Window(0x5D3F, …)`, `DevOverlay.cs:34·148`) 안 현황 패널 아래에 로그 `Count`줄을 높이 제한 없이 그리고(165~169행) 그 아래 탭·스크롤뷰(171~184행)를 밀어낸다. 바꿀 것:

    3. **오버레이의 일부(SPEC 74행 13회차)**: 콘솔 창은 `DevOverlay.OnGUI` 안에서만 그리므로 `DevOverlay.enabled == false`(F1 숨김·측정 자동 숨김)이면 함께 그려지지 않고, `_consoleOpen`은 컴포넌트 필드라 다시 열면 그대로다. 측정 중에 콘솔 창을 열려면 오버레이를 먼저 열어야 하므로 기존 "측정 중 오버레이 열림 → 세션 무효"(5.15.2) 판정에 그대로 걸린다 — 새 무효 조건 코드가 필요 없다. 닫혀 있으면 `DrawConsoleWindow`가 불리지 않아 표시 비용이 없고, 기록(`DevController`의 `Done`/`Refuse`·`PullChestResults`)은 `DevOverlay`와 무관하게 계속된다.
    4. 기록·줄 형식·세션 유지·`DevCommandLog`는 **불변**이다. 테스트 훅 [기본값]: ★ `internal bool ConsoleOpen { get; set; }`(=`_consoleOpen`, Dev 어셈블리 internal — `Tests.Dev`가 이미 `DevController.ChestText` 등 internal을 쓴다). TAC-F19-21.
