#### 5.17.1 HUD 보유 패널 (20회차 신설, SPEC F8 11회차 5·12~17행, Q49 ③④⑤⑧, DECISIONS 7절 "HUD에 보유 무기·패시브 레벨 표시")

현재 코드(main `986987a`): `HudView`(`UI/HudView.cs`)는 시간·레벨·체력·경험치 네 줄이고 `Refresh(long step, int level, float hp, float maxHp, int xp, int requiredXp)`(65행)가 값이 바뀐 줄만 다시 쓴다. 호출은 `GameFlowController.RefreshHud`(`GameFlowController.cs:357~364`) 하나이며, `StartRun`(107행)과 `Update`(HUD가 보일 때 매 프레임, 183~186행)가 부른다. 줄은 `UiFactory.CreateCornerText`(왼쪽 위 기준)로 만든다. UI 어셈블리는 Core·Data·Simulation을 참조한다(5c.1, `Survivor.UI.asmdef`).

- **패널 내용**(SPEC F8 12~14행): 보유 무기를 슬롯 순서로 한 줄씩 `"<displayName> Lv <n>"`, 진화 무기는 `"<displayName> (진화)"`(단계 없음), 그 아래 보유 패시브를 슬롯 순서로 `"<displayName> Lv <n>"`, 마지막 줄 `"몬스터 체력 ×" + value.ToString("F1", CultureInfo.InvariantCulture)`. 빈 슬롯은 줄이 없다. 무기·패시브가 하나도 없어도 배율 줄은 남는다(숨기지 않음, Q49 ⑧). 줄 구분은 `\n` 하나. 레벨 숫자는 `level.ToString(CultureInfo.InvariantCulture)`.
  - 표시 이름 = **인스턴스의 정의**(`WeaponInstance.Definition.DisplayName`, `PassiveInstance.Definition.DisplayName`) — 핫 리로드 뒤에도 보유 인스턴스는 로드 당시 정의를 쓰는 규약(5c.3 #10·5.14)과 같다. `displayName`은 바인더가 필수·비어 있지 않음으로 검사하므로(`WeaponsBinder.cs:35`·`PassivesBinder.cs:24`) 대체 문자열이 필요 없다.
  - 진화 판별 = `WeaponInstance.Definition.EvolvedOnly`(진화 결과 무기는 `evolvedOnly: true`만 될 수 있다, 5.13.3 검증·5.13.1). 조합 규칙을 다시 훑지 않는다.
  - 배율 값 = R31 `GameDataRegistry.Current.SpawnTable.HpMultiplierAt(Clock.Step)` — `Clock.Step`은 HUD 시간 줄과 같은 값(완료 스텝 수 = 다음에 돌 스텝 번호, R2)이라 그 스텝에 스폰될 몬스터의 배율과 같다. `Current` 또는 `SpawnTable`이 null이면 **[기본값]** 1.0.
- ★ **`HudLoadoutFormatter`** (static, `Survivor.UI`, 파일 `Scripts/UI/HudLoadoutFormatter.cs`) **[기본값]**: 위 문자열 규칙의 유일한 소유자다. UI에 두는 이유 — 한국어 표시 문구는 표시 계층의 것이고 UI가 Simulation을 이미 참조하므로 새 참조가 필요 없다(Simulation에 두면 시뮬레이션 어셈블리가 화면 문구를 갖게 된다). 개발자 현황 패널(Dev)은 UI를 참조할 수 없고(5c.1 표) 레이블도 영어라 자기 포매터를 쓴다(5.15.4) — 두 포매터가 공유하는 것은 R31 값뿐이다. `Format`은 슬롯 목록의 null을 건너뛰며 인자 목록이 null이면 `ArgumentNullException`. `WeaponLine`·`PassiveLine`·`HpMultiplierLine`을 따로 공개하는 것은 EditMode 테스트가 정의 객체 없이 문자열 규칙을 검사하게 하려는 것이다.
- ★ **`HudView.RefreshLoadout(int loadoutVersion, IReadOnlyList<WeaponInstance> weapons, IReadOnlyList<PassiveInstance> passives, float hpMultiplier)`** — `Refresh`와 같은 "값이 바뀐 때만 텍스트를 다시 쓴다" 관례. 보여 준 `loadoutVersion`·`hpMultiplier`(정확한 `float` 비교 — 같은 함수가 같은 입력으로 낸 값이라 근사 비교가 필요 없다)를 기억하고 둘 중 하나라도 다르면 `HudLoadoutFormatter.Format`으로 다시 만든다. 그 밖의 프레임에는 문자열을 만들지 않는다(할당 억제). `Create`에서 이 텍스트를 만들 때 보여 준 값은 "없음"(`loadoutVersion = int.MinValue` 등)으로 두어 첫 호출이 반드시 다시 쓰게 한다.
- **갱신 시점 [기본값]** — 브리핑의 "런 시작 + 레벨업 적용 직후 + 배율은 매 `Refresh`" 대신 **더 단순한 쪽을 택한다: `GameFlowController.RefreshHud`가 매번 `_hud.RefreshLoadout(_host.Applier.ChangeCount, session.Weapons.Slots, session.Passives.Slots, multiplier)`를 부른다.** `PlayerProgressionApplier.ChangeCount`(PLAYER, 공개 읽기 전용 `int`, `PlayerProgressionApplier.cs:36`)는 무기·패시브가 바뀌는 모든 경로 — 판 시작 `ResetForRun`(55행), 레벨업 적용, 상자 강화·진화(131·273행), 개발자 `SetLoadout`(257행 등) — 에서 1씩 오르는 기존 값이다. 이유: ① 호출 지점을 `StartRun`·`OnOptionChosen`에 따로 심지 않아도 `RefreshHud` 하나로 끝난다(`StartRun`이 이미 `RefreshHud`를 부른다 — 판 시작 시 "시작 무기 Lv 1"이 첫 프레임에 나온다). ② **상자(F4)의 강화·진화는 레벨업이 아니라 스텝 안(Resolve order 0 채널 8)에서 일어난다** — 레벨업 직후만 갱신하면 상자 진화 뒤 패널이 다음 레벨업까지 낡는다. 개발자 `SetLoadout`·`LevelUpNow`도 같다. ③ 판정이 정수 비교 하나라 매 프레임 비용이 `Refresh`의 비교들과 같은 급이다. `ChangeCount`는 판을 넘어 계속 증가하므로 새 판에서도 반드시 값이 달라진다. SPEC F8 15행 "다음 프레임 안에"는 `RefreshHud`가 HUD가 보이는 매 `Update`에서 돌기 때문에 성립한다(레벨업 선택 적용은 `OnOptionChosen` 안이고, 그다음 `Update`에서 반영). 배율 줄은 같은 호출에서 매번 `HpMultiplierAt`을 다시 계산하고(구간 몇 개의 선형 탐색, 할당 없음) 값이 같으면 문자열을 만들지 않는다 — 구간이 바뀐 다음 프레임에 갱신된다(SPEC F8 14행).
  - IMP-FLOW 편집 범위: `GameFlowController.RefreshHud`에 배율 계산 1~3줄 + `RefreshLoadout` 호출 1줄. 새 필드·이벤트 없음. `_host.Applier`는 이미 `OnOptionChosen`이 쓰는 접근자다(262행).

#### 5.17.2 표시 배율·W2 궤도 표시 (21회차 신설, 웨이브 6b 구현, SPEC 00-common 3.0 C 12회차·F06 12회차 33행, Q50 ⑧, DECISIONS 7절 "표시 크기 > 히트박스, W2 궤도 원 궤도 표시")

현재 코드(origin/main a501bd8): 풀 엔티티 표시는 `EntityPresenter`(`App/EntityPresenter.cs`)가 자식 `"Visual"`의 `localScale`을 `DiameterOf(entity.Body.Radius)`(60행 `radius * 2f`)로 생성 때(165행)와 매 `LateUpdate`(187행) 맞춘다. 대상은 Lifecycle의 **모든** 활성 엔티티(몬스터·아군/적 투사체·젬·상자·`DamageZone`·`EnemyHazardZone`·`OrbitOrb`)다. 플레이어 원은 `PlayerPresenter.LateUpdate`(`App/PlayerPresenter.cs:48`, `Body.Radius * 2f`)가 그린다. 둘 다 IMP-FLOW 소유이고 시뮬레이션이 읽는 값은 쓰지 않는다(5c.3 #6). 궤도 반지름 표시 코드는 없다.

**표시 배율**
- ★ `GameRules.BodyVisualScale = 1.25f`(Core `GameRules.cs`, IMP-CORE 파일 — 웨이브 6b IMP-FLOW 줄 단위 수정권, R20 (21회차)). JSON에 두지 않는다(SPEC 3.0 C·D "규칙").
- **[기본값] 몸체형/영역형 구분 = `EntityCategory`(Core, 이미 존재) 값으로.** ★ `internal static float EntityPresenter.VisualScaleOf(EntityCategory category)`: `PlayerOrb`·`PlayerZone`·`EnemyZone` → `1f`(영역형: W2/E2 궤도 원, W3 장판, 적 장판), 나머지(`Monster`·`PlayerProjectile`·`EnemyProjectile`·`Gem`·`Chest`) → `GameRules.BodyVisualScale`. `SortingOrderOf(EntityCategory)`(42행)와 같은 꼴이다. 고르지 않은 대안: 타입 검사(`is OrbitOrb` 등 — App이 PLAYER·MONSTER 구체 타입 셋에 더 묶임, 새 영역형이 생기면 놓침), `SimEntity` 플래그 ★(Simulation·LOOP 수정, 시뮬레이션 객체에 표시 개념 유입). 카테고리 8종이 SPEC의 몸체형 6종·영역형 3종(궤도 원 = `PlayerOrb`)과 1:1로 대응하므로 추가 정보가 필요 없다.
- 수정 지점: 165·187행의 `DiameterOf(entity.Body.Radius)` → `DiameterOf(entity.Body.Radius) * VisualScaleOf(entity.Category)`. `DiameterOf`는 그대로 둔다(`EntityVisualTests.DiameterOf_IsTwiceTheRadius`가 그대로 통과). `PlayerPresenter` 48행 → `Body.Radius * 2f * GameRules.BodyVisualScale`(반지름 0일 때의 `1f`는 그대로, `using Survivor.Core;` 추가).
- 판정 반지름(`Body.Radius`, F11 데이터)·접촉 거리(R32)·`DevVisualizer`의 충돌 반경 원(판정 반지름, SPEC F19 50행·Q50 ⑲)은 바뀌지 않는다 — 세 번째 크기 없음. 상태 해시 불변(5.16).
- 기록(위반 아님): 보스 표시 반지름 1.5 × 1.25 = 1.875가 스폰 원과 화면 반대각의 여유 1.64(SPEC F3 37행, Q44)보다 크므로, 보스가 r=20에 등장하는 순간 표시 원의 가장자리가 화면 모서리에 걸쳐 보일 수 있다. SPEC은 "스폰 **지점**은 화면 밖"(중심)을 요구하고 판정 반지름 1.5 < 1.64라 기준은 지켜진다. 일반 몬스터(최대 0.5 × 1.25 = 0.625)는 해당 없음.

**W2·E2 궤도 표시**
- ★ **`OrbitRingPresenter : MonoBehaviour`**(App `Scripts/App/OrbitRingPresenter.cs`, IMP-FLOW, 새 파일) — `public void Initialize(WeaponInventory weapons)`(null → `ArgumentNullException`). `GameBootstrap.BuildPresentation`이 `PlayerPresenter` 줄(372행) 다음에 플레이어 host(`"Player"`)에 붙인다(1줄). 시뮬레이션 객체가 아니다(`SimEntity`·충돌 바디·명령 없음 — F18 판정 대상 아님).
- **[기본값] 구성**: `Initialize`가 슬롯 수(`GameRules.MaxWeaponSlots` = 4)만큼 자식 `"OrbitRing.<slot>"`에 `LineRenderer`(`loop = true`, `useWorldSpace = false`, `positionCount = 64`, `widthMultiplier = 0.05`, `sortingOrder = 7`(몬스터 5와 투사체·궤도 원 8 사이), 색 흰색 알파 0.35)를 만들어 꺼 둔다. 플레이어 host는 배율 1이고(`PlayerPresenter`는 자식에만 배율을 씀) 로컬 원점이 플레이어 위치라 링이 플레이어를 따라간다(host 위치는 `PlayerPresenter`·엔진 바디가 쓴다). 단위 원 64점은 `Initialize`에서 한 번 계산한다.

W2와 E2가 동시에 있으면 링 2개.
- **공격 끔 중에도 표시**: `Rules.WeaponsEnabled`를 보지 않는다(SPEC F06 33행·F19 66행). 개발자 모드와 무관하게 일반 플레이에서 항상 동작한다.
