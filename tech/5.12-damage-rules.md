### 5.12 피해·획득 규칙 구성요소 (Simulation, IMP-PLAYER/IMP-MONSTER)

```csharp
namespace Survivor.Simulation
{
    /// Attacker-side per-target cooldown for persistent hitters (W2/E2 orbs, W3 zones). One per weapon instance.
    public sealed class ContactDamageTracker
    {
        public ContactDamageTracker(int hitIntervalSteps);
        public void OnEnter(EntityId target, long step);   // overlapCount++ ; mark for immediate hit check
        public void OnExit(EntityId target);               // overlapCount-- ; keeps nextAllowed record
        /// Appends targets to hit this step in ascending Id order and advances their nextAllowed.
        public void CollectHits(long step, List<EntityId> hitsOut);
        public void Forget(EntityId target);               // Despawned subscriber (TAC-0-10)
        public void SetInterval(int hitIntervalSteps);     // level-up / P1 change. (rev 7, D14 confirmed) W2/E2: P1-applied interval; W3 zone: definition value, never P1-scaled.
                                                           // (rev 8) applies from the next computation only: existing nextAllowed records are not recomputed (TAC-F2-3)
        public void Clear();
    }

    /// Victim-side shared invulnerability for the player (body contact, M3 projectiles, M4 zones).
    public sealed class PlayerDamageReceiver : ICollisionEventHandler, IStepPhaseHandler   // Resolve order 20
    {
        // Enter/Exit for channels 3 and 5 maintain an overlap set; channel 4 Enter is a one-shot candidate (projectile consumed).
        // Resolve: if Rules.PlayerTakesDamage && step >= _invulnerableUntilStep && (pending one-shot || overlap set non-empty):
        //   damage = max over candidates, tie -> smaller EntityId; _invulnerableUntilStep = step + invulnerabilitySteps.
        // While invulnerable, channel-4 Enter consumes the projectile without damage (SPEC 3.0 I).
        // Despawned subscriber removes ids from the overlap set (no Exit on unregister).
        public long InvulnerableUntilStep { get; }
        public void Clear();
    }

    /// Resolve order 10: persistent weapon damage in weapon slot order, each tracker's hits in ascending target Id.
    /// (rev 8) When !Rules.WeaponsEnabled it does not call CollectHits (orb/zone damage stops; Enter/Exit bookkeeping continues) (TAC-F2-5).
    public sealed class WeaponDamageResolver : IStepPhaseHandler { }
}
```

- 일회성 접촉(W1·W4 투사체 → 몬스터, 젬, 상자): Enter 1회를 처리하고 `MarkConsumed` 후 `Despawn(Consumed)` 명령. 관통은 TAC-F6-9.
- 한 투사체가 같은 스텝에 몬스터 둘과 Enter하면 정렬 순서상 앞(작은 몬스터 ID)만 맞히고, 나머지 이벤트는 투사체가 `IsConsumed`라 무시한다(관통 없음 = 정확히 1회 피해, SPEC F18).
- 이미 hp ≤ 0인 몬스터에 대한 같은 스텝의 추가 피해는 무시한다(처치는 `KillPipeline`에서 1회).
- (7회차, D14 확정 2026-11-05) P1(공격 속도)은 `ContactDamageTracker`의 틱 간격 중 W2·E2 궤도 원에만 적용된다(W2의 유일한 간격). W3 장판 트래커의 간격은 정의값 `hitIntervalSteps` 그대로이며, W3에서 P1이 줄이는 것은 장판 생성 쿨다운뿐이다(TAC-F2-3, R13).
- (8회차, SPEC F2·F19 8회차) P1 변경은 `SetInterval` 뒤의 **다음 산정부터** 적용되고 기존 `nextAllowed`는 그대로다. `WeaponsEnabled == false`이면 궤도 원·장판의 피해 판정이 멈추고(`WeaponDamageResolver`가 `CollectHits`를 부르지 않음) 궤도 원 표시는 유지된다(TAC-F2-5).

#### 5.12.1 IMP-MONSTER 소유 클래스 설계 (7회차 신설)

5c.2 소유권 맵이 IMP-MONSTER에 준 클래스 중 설계 절이 없던 것을 모은다. **새 설계가 아니라** 02 TAC·5a·5c.3·5.04·5.10·5.15에 흩어진 계약을 한곳에 옮긴 것이다. 기존 문서에 없어 이 소절에서 정해야 문장이 완성된 곳은 **[기본값]**으로 표시했다. 어긋나면 원 출처(각 줄의 참조)가 우선한다. `MonsterCommandHandler`·`DropCommandHandler`는 5.04(명령 핸들러), `Monster`·`EnemyProjectile`은 5.08(`IUpdatable`)이 정의한다.

**`MonsterSpawner`** (`IStepPhaseHandler`)
- 책임: 일반 스폰과 보스 등장을 실행한다. 판 시작(`RunSession.Reset`)에 1회 바인딩된 `ISpawnPolicy`(일반 = `TableSpawnPolicy`, 개발자 = `SpawnPolicyOverride`)를 쓰고, 상한과 배치는 정책이 아니라 이 클래스가 적용한다.
- 입력: `ISpawnPolicy.CollectSpawns(context, liveMonsterCount, spawnRng, monsterIdsOut)`·`BossSpawnDue(step)`, `StepContext.PlayerPosition`, 활성 몬스터 수, `Rules.MonsterCap`(기본 400), Spawn 스트림, `GameRules.SpawnRadius`(20), 스폰 테이블의 `bossMonsterId`(`GameDataRegistry.Current`에서 매번 읽음).
- 출력: `EntityLifecycle.Spawn` 직접 호출(명령 아님). 목록을 앞에서부터 1기마다 `live < cap`을 검사하고, 통과하면 `SpawnGeometry.PointOnCircle(playerPos, SpawnRadius, rng.NextFloat01())`로 위치를 1회 뽑아 생성한다. 실패하면 그 스텝의 남은 항목을 버린다. **[기본값]** 버린 항목은 각도를 뽑지 않는다(Spawn 스트림을 소비하지 않는다). `BossSpawnDue`가 참인 스텝에는 일반 스폰을 끝내고 보스 1기를 상한과 무관하게 같은 원주(각도도 Spawn 스트림)에 생성한다. `bossMonsterId`가 무효면 보스를 만들지 않는다(소프트락, D6). (8회차, SPEC F3 8회차) `live`는 **보스를 제외한** 활성 몬스터 수이며 `CollectSpawns`의 `liveMonsterCount`에도 같은 값을 넘긴다(R20, TAC-F3-3). (8회차, SPEC F19 8회차) 보스는 판당 1기다: 보스 등장 조건은 `!_bossSpawnedThisRun && policy.BossSpawnDue(step)`(`TableSpawnPolicy`는 `step >= BossSpawnStep`, 아래)이고, 합치면 `step >= GameRules.BossSpawnStep && !bossSpawned`다. **[기본값]** 이 플래그는 `MonsterSpawner`의 판 단위 내부 상태로, 자기 보스 생성과 `MonsterCommandHandler`가 boss 행동 몬스터를 만들 때(개발자 `SpawnBossNow` 경로) 모두 세우고(같은 어셈블리 `internal`, 새 공개 멤버 없음), 판 리셋에서 지운다.
- 호출 단계: Lifecycle order 30(`SimulationCommandBuffer` 0 → `LifetimeSystem` 10 → `DespawnSystem` 20 뒤, `StepOutcomeGate` 90 앞). Lifecycle에서 `EntityLifecycle`을 직접 부르는 셋 중 하나다.
- 참조: TAC-F3-2·F3-3·F3-4·F3-6·F3-10·F8-10, R7·R10·R11·R20, D4·D6, 5c.3 #5·#9·#10, 5.04 메모, 5.15 `ISpawnPolicy`·`IDevModeHost.SpawnPolicyOverride`.

**`SpawnScheduler`**
- 책임: 구간 안 스텝 k의 스폰 수를 누적 변수 없이 계산한다. `SpawnsDueAtStep(rate, k) = ⌊(k+1)·rate/60⌋ − ⌊k·rate/60⌋`. 상태가 없으므로 몰아서 스폰할 수 없다.
- 입력: 구간의 `spawnsPerSecond`(rate), k = 현재 스텝 − 구간 시작 스텝(`startSeconds`를 R1로 환산한 값).
- 출력: 그 스텝의 스폰 수(`int`). 명령·이벤트 없음.
- 호출 단계: **[기본값]** `TableSpawnPolicy.CollectSpawns` 안에서만 호출한다(Lifecycle order 30의 `MonsterSpawner`를 거쳐). `ISpawnPolicy` 계약상 스폰 요청을 채우는 쪽이 정책이기 때문이다.
- 참조: TAC-F3-2·F3-3, R1, 5.13.4, 5c.5 "스폰 스케줄".

**`TableSpawnPolicy`** (`ISpawnPolicy`, 일반 플레이)
- 책임: 현재 스텝이 속한 스폰 테이블 구간(`startSeconds` 포함, `endSeconds` 미포함)을 찾아 `SpawnScheduler`의 수만큼 몬스터 종을 고른다. 종 선택은 구간 `entries`의 `weight`로 `WeightedSampler.PickIndex`(R9, 복원 추출)를 Spawn 스트림으로 뽑는다. 구간 밖 스텝(600초 이후 포함)은 0기다.
- 입력: `in StepContext`(스텝), `liveMonsterCount`, `spawnRng`(Spawn 스트림), 스폰 테이블(`GameDataRegistry.Current`, 참조할 때마다 읽음 — 핫 리로드 적용 시점은 5.11.1 표). **[기본값]** `liveMonsterCount`는 쓰지 않는다(상한은 `MonsterSpawner`가 적용한다).
- 출력: `monsterIdsOut`에 몬스터 ID를 추첨 순서대로 채운다. 명령 없음. `BossSpawnDue(step)`은 (8회차 정정, SPEC F19 8회차) `step >= GameRules.BossSpawnStep`(36000)이다 — 7회차의 `==` [기본값]을 대체한다. `>=`라 시간 점프로 36000을 건너뛰어도 등장하고, 재등장은 `MonsterSpawner`의 "이번 판 보스 생성됨" 플래그가 막는다(위).
- 호출 단계: Lifecycle order 30에서 `MonsterSpawner`가 호출한다. `SpawnPolicyOverride`가 null일 때 `Reset`에서 바인딩된다(매 스텝 null 검사 없음).
- 참조: TAC-F3-2·F3-6, R9, 5c.3 #5·#10, 5.13.4, 5.15 `ISpawnPolicy`·0절 3회차 #3, TAC-F11-5.

**`DespawnSystem`** (`IStepPhaseHandler`)
- 책임: 플레이어에게서 너무 멀어진 일반 몬스터를 회수한다. 보스는 보지 않는다. 젬·상자도 보지 않는다(젬·상자에는 디스폰 경로가 없다).
- 입력: 활성 몬스터(`EntityId` 오름차순), `StepContext.PlayerPosition`, 디스폰 거리 D(스폰 테이블 `despawnDistance`, 기본 45, 개발자 덮어쓰기는 R26).
- 출력: `SpawnGeometry.IsBeyondDespawn(pos, playerPos, D)`(R18, 엄격 초과)가 참이면 `EntityLifecycle.Despawn(id, DespawnReason.OutOfRange)`를 직접 호출한다(명령 아님) → `Despawned` 이벤트. `KillPipeline`을 거치지 않으므로 드랍·처치 수가 없다.
- 호출 단계: Lifecycle order 20. Lifecycle에서 `EntityLifecycle`을 직접 부르는 셋 중 하나다.
- 참조: TAC-F3-5·F4-8, R10·R11·R18·R24·R26, 5c.3 #9, 5.04 메모, 5.10 `Despawned`.

**`KillPipeline`** (`IStepPhaseHandler`)
- 책임: 그 스텝의 처치를 한 번에 확정한다. 이번 스텝 hp ≤ 0이 된 몬스터를 `EntityId` 오름차순으로 처리하고, 처치 수 증가의 유일한 위치다(R24).
- 입력: 이번 스텝 Resolve order 0(채널 0 투사체 명중)과 order 10(`WeaponDamageResolver` 지속 피해)에서 hp ≤ 0이 된 몬스터, `PlayerStats.pickups.gemXpValue`, Drop 스트림, `Rules.ChestDropChance`(기본 0.02, 측정 중 0). 5.10에서 `EntityLifecycle.Despawned` 구독자로 적혀 있다(구독 목적은 5.10에 없어 여기서 정하지 않는다).
- 출력: 일반 몬스터 처치마다 처치 수 +1, 처치 위치에 `SpawnGem` 명령 1개, 상자 판정 `rng(Drop).Chance(Rules.ChestDropChance)` 정확히 1회(확률이 0이어도 뽑음) → 참이면 `SpawnChest` 명령, `Despawn(Killed)` 명령. 보스 처치는 드랍·상자 판정 없이 `BossKilledThisStep = true`를 세우고 처치 수에는 포함된다(R24 "보스·소환체 포함"). **[기본값]** 보스에도 `Despawn(Killed)` 명령을 넣는다(R24가 처치를 `Killed` 회수로 정의하므로).
- 호출 단계: Resolve order 30(`PlayerDamageReceiver` 20 뒤). 명령은 같은 스텝 Lifecycle order 0에서 `DropCommandHandler`·`EntityDespawnCommandHandler`가 처리한다. `BossKilledThisStep`(TAC-F4-1)은 같은 스텝 Lifecycle order 90의 `StepOutcomeGate`가 클리어 판정에 읽는다(사망 > 클리어 > 레벨업 — TAC-F4-1·TAC-F5-4 1단계·TAC-F8-8, 5.03 게이트 규칙).
- 참조: TAC-F4-1·F4-2·F4-7·F5-8·F8-8, R10·R24, 5c.3 #5·#9, 5.04 메모(핸들러 배정), 5.10 `Despawned`, 6.1 C 목록 ⑤.

**`PickupSystem`** (`IStepPhaseHandler`, `ICollisionEventHandler` 채널 6~8)
- 책임: 젬 끌림 이동과 젬·상자 획득을 처리한다. 젬 판정은 채널 두 개다(자석 Enter = 끌림 시작, 몸통 Enter = 획득, D16).
- 입력: `CollisionEventRouter`가 `CollisionEvent.CompareTo` 순서로 넘기는 채널 6(`PlayerMagnetVsGem`)·7(`PlayerBodyVsGem`)·8(상자) Enter, `StepContext.PlayerPosition`, `pickups.gemAttractSpeed`(스텝당 값), Chest 스트림. Exit은 무시한다(끌림은 되돌리지 않는다).
- 출력: 채널 6 → 젬을 끌림 상태로 표시. 채널 7 → `ExperienceSystem.AddXp(gemXpValue)` + 젬 `MarkConsumed` 후 `Despawn(Consumed)` 명령. 채널 8 → `ChestEffectResolver.Resolve(rng(Chest), context)`(진화·강화·회복은 `PlayerProgressionApplier`가 적용) + 상자 `Despawn(Consumed)` 명령. WeaponTick에서는 끌림 상태 젬을 `gemAttractSpeed`로 플레이어 쪽으로 옮긴다.
- 호출 단계: WeaponTick order 10(젬 끌림 이동, `WeaponInventory` 0 뒤), Resolve order 0(라우터 디스패치 안의 채널 6·7·8). 상자 회복이 order 0이라 order 20 플레이어 피해보다 먼저다. (8회차, SPEC F4 8회차) 같은 스텝의 상자 여러 개는 이벤트 순서대로 하나씩 `Resolve`하며, 앞 상자의 진화 결과가 뒤 상자의 자격 판정에 반영된다(TAC-F4-4).
- 참조: TAC-F4-3·F4-4·F4-6·F4-8, D16·D23, 5c.3 #5·#9, 5.00 `ICollisionEventHandler`·`IStepPhaseHandler` 표, 5.12 일회성 접촉 규칙(위), 5.14 `ExperienceSystem.AddXp` 주석·`ChestEffectResolver`.
