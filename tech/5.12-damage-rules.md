### 5.12 피해·획득 규칙 구성요소 (Simulation, IMP-PLAYER/IMP-MONSTER)

```csharp
namespace Survivor.Core
{
    /// ★ (rev 16, DECISIONS 4 2026-11-07) An entity that can take weapon damage. Implemented by Monster (IMP-MONSTER);
    /// consumed by PlayerHitHandler (channel 0) and WeaponDamageResolver (IMP-PLAYER). file: Scripts/Core/IDamageable.cs (IMP-CORE)
    public interface IDamageable
    {
        /// False once health reached 0 (stays false until the entity is despawned and reused).
        bool IsAlive { get; }

        /// Subtracts amount from health at step. A call while !IsAlive is ignored (the implementation's job: extra damage to a
        /// monster already at hp <= 0 in the same step is dropped, the kill is confirmed once by KillPipeline).
        /// amount must be finite and >= 0, else ArgumentOutOfRangeException.
        void ApplyDamage(float amount, long step);
    }

    /// ★ (rev 16, DECISIONS 4 2026-11-07) An entity that damages the player on contact. Implemented by Monster (definition
    /// ContactDamage), EnemyProjectile (Damage), EnemyHazardZone (zone damage) (IMP-MONSTER); consumed by PlayerDamageReceiver
    /// (channels 3, 4, 5, IMP-PLAYER). file: Scripts/Core/IContactDamageSource.cs (IMP-CORE)
    public interface IContactDamageSource
    {
        /// Damage dealt to the player by one hit (>= 0).
        float ContactDamage { get; }
    }
}

namespace Survivor.Simulation
{
    /// Attacker-side per-target cooldown for persistent hitters (W2/E2 orbs, W3 zones). One per weapon instance.
    public sealed class ContactDamageTracker
    {
        public ContactDamageTracker(int hitIntervalSteps);
        public void OnEnter(EntityHandle target, long step);   // overlapCount++ ; mark for immediate hit check
        public void OnExit(EntityHandle target);               // overlapCount-- ; keeps nextAllowed record
        /// Appends targets to hit this step in ascending Id order and advances their nextAllowed.
        public void CollectHits(long step, List<EntityHandle> hitsOut);
        public void Forget(EntityHandle target);               // Despawned subscriber (TAC-0-10)
                                                               // (rev 17) victim side only; the attacker side (orb/zone despawn) is OnExit replay, below
        public void SetInterval(int hitIntervalSteps);     // level-up / P1 change. (rev 7, D14 confirmed) W2/E2: P1-applied interval; W3 zone: definition value, never P1-scaled.
                                                           // (rev 8) applies from the next computation only: existing nextAllowed records are not recomputed (TAC-F2-3)
        public void Clear();
        public int IntervalSteps { get; }                                    // ★ (rev 17) current hit interval
        public int TrackedCount { get; }                                     // ★ (rev 17) targets with an overlap or a pending cooldown record
        public bool TryGetNextAllowed(EntityHandle target, out long nextAllowedStep); // ★ (rev 17) record lookup (tests, diagnostics)
        //   (rev 17, code) CollectHits drops an expired record whose overlapCount is 0 (same as no record; bounds memory)
    }

    /// Victim-side shared invulnerability for the player (body contact, M3 projectiles, M4 zones).
    public sealed class PlayerDamageReceiver : ICollisionEventHandler, IStepPhaseHandler   // Resolve order 20
    {
        // Enter/Exit for channels 3 and 5 maintain an overlap set; channel 4 Enter is a one-shot candidate (projectile consumed).
        // Resolve: if Rules.PlayerTakesDamage && step >= _invulnerableUntilStep && (pending one-shot || overlap set non-empty):
        //   damage = max over candidates, tie -> smaller EntityHandle; _invulnerableUntilStep = step + invulnerabilitySteps (rev 14: PlayerStatsDefinition.InvulnerabilitySteps).
        // While invulnerable, channel-4 Enter consumes the projectile without damage (SPEC 3.0 I).
        // Despawned subscriber removes ids from the overlap set (no Exit on unregister).
        public long InvulnerableUntilStep { get; }
        public void Clear();
        // ★ (rev 16) constructor takes Func<EntityHandle, IContactDamageSource> contactSources (other arguments: implementer's choice);
        //   the damage of a candidate = contactSources(id).ContactDamage
        public PlayerDamageReceiver(PlayerHealth health, Func<GameData> currentData,
                                    Func<EntityHandle, IContactDamageSource> contactSources, EntityLifecycle lifecycle); // ★ (rev 17) subscribes lifecycle.Despawned
        public int OverlapCount { get; }   // ★ (rev 17) contact sources overlapping now (channels 3 and 5)
        //   (rev 17, PM: defined behaviour) a candidate with ContactDamage 0 is still "the maximum applied once": the 0 damage is applied
        //   and invulnerability starts. No monster in the current data has 0 contact damage.
        //   (rev 17, code) channel 4 marks the projectile consumed and enqueues Despawn(Consumed) even while invulnerable; one-shot
        //   candidates are cleared at the end of every Resolve
    }

    /// Resolve order 10: persistent weapon damage in weapon slot order, each tracker's hits in ascending target Id.
    /// (rev 8) When !Rules.WeaponsEnabled it does not call CollectHits (orb/zone damage stops; Enter/Exit bookkeeping continues) (TAC-F2-5).
    public sealed class WeaponDamageResolver : IStepPhaseHandler { }
    // ★ (rev 16) WeaponDamageResolver and PlayerHitHandler (channel 0) constructors take Func<EntityHandle, IDamageable> damageables
    //   and call damageables(id)?.ApplyDamage(damage, context.Step)
    //   ★ (rev 17, code) WeaponDamageResolver(WeaponInventory weapons, Func<EntityHandle, IDamageable> damageables);
    //   PlayerHitHandler(EntityLifecycle lifecycle, WeaponInventory weapons, Func<EntityHandle, IDamageable> damageables) — channels 0, 1, 2;
    //   channel 1/2 Enter/Exit go to the owning instance's tracker and the orb/zone's own overlap list; events of an orb/zone whose
    //   weapon is no longer in its slot are ignored
}
```

|---|---|---|---|
| ★ `IDamageable` | `Monster` | `PlayerHitHandler`(채널 0 투사체 명중), `WeaponDamageResolver`(지속 피해) | `Func<EntityHandle, IDamageable>` |

- (16회차) **[기본값] 엔티티 조회 경로**: 소비자는 `CollisionEvent.A/B`(또는 트래커의 대상 핸들)에서 엔티티를 생성자로 받은 조회 델리게이트로 얻는다. App(조립 루트)이 `id => lifecycle.TryGet(id, out SimEntity e) ? e as IDamageable : null`(접촉 피해원도 같은 꼴)로 채운다. 근거: PLAYER의 EditMode 테스트가 `SimEntity` 파생 더블 없이 인터페이스 더블만으로 돌아야 하고(5c.5 EditMode 제약), LOOP 드라이버의 `Func<ITickStrategy>`·`Func<Vector2>`와 `PickupSystem` 델리게이트와 같은 관례다. **[기본값] 조회 실패**(null — 이미 회수됐거나 인터페이스를 구현하지 않은 엔티티)는 그 이벤트·대상을 무시하고 로그를 남기지 않는다. 어느 채널에 어느 레이어가 오는지는 `CollisionChannelTable`이 보장한다.
- (16회차) 피해량 타입은 `float`이다. 데이터 정의(`MonsterDefinition.ContactDamage`·`MaxHealth`, `EnemyProjectileDefinition.Damage`, `WeaponLevelDefinition.Damage`)가 모두 `float`이기 때문이다. `KillPipeline`이 "이번 스텝 hp ≤ 0이 된 몬스터"를 고르는 방법(예: `Monster`가 사망 스텝을 기억)은 MONSTER 내부이고 인터페이스에 넣지 않는다. (17회차, 구현 확정) `Monster.DiedAtStep`(살아 있으면 −1)과 `KillConfirmed`다(5.12.1).
- (17회차, PM 판정 — 구현 보정, 설계 변경 아님) **겹침 정리는 양쪽에서 한다.** ① 피격자(몬스터) 디스폰 → `ContactDamageTracker.Forget`(TAC-0-10, 기존). ② **가해자(장판·궤도 원) 디스폰 → 자기 겹침 목록을 Exit으로 재생.** 두 충돌 전략 모두 `Unregister`에 Exit을 내지 않으므로(TAC-F18-5) 이것이 없으면 장판·궤도 원이 사라진 뒤에도 트래커의 겹침 수가 남아 그 적이 계속 맞는다. 구현: `OrbitOrb`·`DamageZone`이 지금 겹친 몬스터 목록(internal `Overlaps`)을 갖고, `PlayerHitHandler`가 채널 1·2 Enter/Exit 때 이 목록과 트래커를 함께 갱신한다. 그 엔티티가 회수되면 `WeaponInventory`의 `Despawned` 처리기가 소유 인스턴스에서 자식을 떼고 목록의 각 ID에 `owner.Tracker.OnExit(id)`를 부른 뒤 목록을 비운다(`WeaponInventory.ReleaseChild`). 같은 처리기는 회수된 것이 몬스터면 모든 무기의 `Tracker.Forget(id)`와 살아 있는 자식들의 목록에서 그 ID 제거를 한다. EM: `WeaponTests`의 `TACF6_6_ZoneDespawnEndsItsOverlapAlthoughNoExitIsEmitted`·`TACF6_6_OverlappingZonesOfOneWeaponShareOneCooldownRecord`. SPEC 3.0 I("실제 전이만")의 의도를 지키는 쪽이다.
- (16회차, PM **[기본값]**) **플레이어 등록 경로.** 플레이어는 풀 엔티티가 아니다(`EntityCategory` 8종에 없어 `PrefabCatalog` 템플릿도 `EntityLifecycle.Spawn<T>` 경로도 없다). IMP-PLAYER의 `PlayerEntity`가 몸 바디(`CollisionLayer.PlayerBody`, 반지름 `PlayerStatsDefinition.Radius`)와 자석 바디(`CollisionLayer.PlayerMagnet`, 반지름 `PlayerStatsDefinition.PickupRadius`에 P3 적용)를 **직접 만들고**, `EntityHandleAllocator`에서 ID를 몸 → 자석 순으로 받아(1:1 → 2:1, 5.01) 현재 `ICollisionStrategy.Register`·`IPhysicsBodyRegistry.Register`에 직접 등록한다(5c.3 #1의 명시적 예외). 두 바디의 `Host`는 ~~PLAYER가 만든 `GameObject`~~ (17회차 정정, 코드) 조립 루트가 만들어 `PlayerEntity` 생성자의 `host`로 넘기는 `GameObject` 하나(두 바디 공유, 표현은 조립 루트 몫)이고, PLAYER는 `Rigidbody2D`·콜라이더를 붙이지 않는다(`PhysicsBodySynchronizer.Register`가 멱등 추가, 5.9.1). 위치의 원본은 `PlayerEntity.Position`이며 PlayerMove 단계(`PlayerMovement`, order 0)마다 PLAYER가 두 바디의 `Position`을 함께 갱신한다. 자석 반지름이 바뀌면(P3 레벨업) PLAYER가 `Radius`를 고친 뒤 등록할 때 받은 충돌 전략의 `NotifyRadiusChanged(magnetBody)`를 부른다. 드라이버의 `StepContext.PlayerPosition`은 조립 루트가 `SimulationDriverEarly.Initialize`의 `playerPosition`에 `() => player.Position`을 넣어 얻는다(5.3).
  - (17회차 각주, PM 판정 [기본값]) **반지름 변경 경로 두 곳.** ① 자석: ★ `PlayerEntity.RefreshMagnetRadius()`가 `pickupRadius × (1 + P3)`(R13)를 다시 계산해 달라졌을 때만 `MagnetBody.Radius`를 고치고 등록 때 받은 전략의 `NotifyRadiusChanged`를 부른다. `PlayerProgressionApplier`가 패시브 변경마다(레벨업·`ResetForRun`) 부른다. ② 궤도 원: 강화로 `orbRadius`가 바뀌면 다음 WeaponTick에 `OrbitWeapon`이 각 궤도 원의 `Body.Radius`를 고치고 `lifecycle.Collisions.NotifyRadiusChanged(orb.Body)`를 부른다. `orbCount`가 바뀌면 같은 WeaponTick에서 각 간격도 새 `orbCount` 기준 2π·i/n으로 즉시 바뀌고, 모자란 인덱스는 `SpawnPlayerOrb`, 남는 인덱스는 큰 것부터 `Despawn(Replaced)`(TAC-F6-8). 엔진판은 다음 동기화에서 콜라이더 반지름을 갱신한다(5.9 `NotifyRadiusChanged` 주석).

#### 5.12.1 IMP-MONSTER 소유 클래스 설계 (7회차 신설)

(17회차, 웨이브 3 구현 확정 — IMP-MONSTER main f902e53) 생성자와 구현자가 더한 공개 멤버(의미는 코드 주석). 데이터는 전부 `GameDataRegistry` **인스턴스**를 받아 `.Current`를 읽는다(5.11, 5c.3 #10).

**`MonsterSpawner`** (`IStepPhaseHandler`)
- 책임: 일반 스폰과 보스 등장을 실행한다. 판 시작(`RunSession.Reset(in RunStrategies)`)에 1회 바인딩된 `ISpawnPolicy`(일반 = `TableSpawnPolicy`, 개발자 = `SpawnPolicyOverride`)를 쓰고, 상한과 배치는 정책이 아니라 이 클래스가 적용한다.
- 입력: `ISpawnPolicy.CollectSpawns(context, liveMonsterCount, spawnRng, monsterIdsOut)`·`BossSpawnDue(step)`, `StepContext.PlayerPosition`, 활성 몬스터 수, `Rules.MonsterCap`(기본 400), Spawn 스트림, `GameRules.SpawnRadius`(20), 스폰 테이블의 `bossMonsterId`(`GameDataRegistry.Current`에서 매번 읽음; (14회차) 코드 이름 `SpawnTable.BossMonsterId`, 무효면 null).
- 출력: `EntityLifecycle.Spawn` 직접 호출(명령 아님). 목록을 앞에서부터 1기마다 `live < cap`을 검사하고, 통과하면 `SpawnGeometry.PointOnCircle(playerPos, SpawnRadius, rng.NextFloat01())`로 위치를 1회 뽑아 생성한다. 실패하면 그 스텝의 남은 항목을 버린다. **[기본값]** 버린 항목은 각도를 뽑지 않는다(Spawn 스트림을 소비하지 않는다). `BossSpawnDue`가 참인 스텝에는 일반 스폰을 끝내고 보스 1기를 상한과 무관하게 같은 원주(각도도 Spawn 스트림)에 생성한다. `bossMonsterId`가 무효면 보스를 만들지 않는다(소프트락, D6). (8회차, SPEC F3 8회차) `live`는 **보스를 제외한** 활성 몬스터 수이며 `CollectSpawns`의 `liveMonsterCount`에도 같은 값을 넘긴다(R20, TAC-F3-3). (8회차, SPEC F19 8회차) 보스는 판당 1기다: 보스 등장 조건은 `!_bossSpawnedThisRun && policy.BossSpawnDue(step)`(`TableSpawnPolicy`는 `step >= BossSpawnStep`, 아래)이고, 합치면 `step >= GameRules.BossSpawnStep && !bossSpawned`다. **[기본값]** 이 플래그는 `MonsterSpawner`의 판 단위 내부 상태로, 자기 보스 생성과 `MonsterCommandHandler`가 boss 행동 몬스터를 만들 때(개발자 `SpawnBossNow` 경로) 모두 세우고(쓰기는 같은 어셈블리 `internal`), 판 리셋에서 지운다. (11회차, PM 승인) 읽기는 ★ `public bool BossSpawnedThisRun { get; }`(읽기 전용, ~~이 클래스의 유일한 신규 공개 멤버~~ (17회차 정정) 11회차 시점의 유일한 신규 공개 멤버였다 — 웨이브 3 구현의 추가 공개 멤버는 아래 블록)로 연다. 이 값이 참이면 개발자 `SpawnBossNow`는 거부된다(판정은 `PendingCommandQueue`가 이 속성을 읽어 Begin에서, 명령은 소비, 5.15, TAC-F19-2).
- 호출 단계: Lifecycle order 30(`SimulationCommandBuffer` 0 → `LifetimeSystem` 10 → `DespawnSystem` 20 뒤, `StepOutcomeGate` 90 앞). Lifecycle에서 `EntityLifecycle`을 직접 부르는 셋 중 하나다.
- 참조: TAC-F3-2·F3-3·F3-4·F3-6·F3-10·F8-10, R7·R10·R11·R20, D4·D6, 5c.3 #5·#9·#10, 5.04 메모, 5.15 `ISpawnPolicy`·`IDevModeHost.SpawnPolicyOverride`.

**`SpawnScheduler`**
- 책임: 구간 안 스텝 k의 스폰 수를 누적 변수 없이 계산한다. `SpawnsDueAtStep(rate, k) = ⌊(k+1)·rate/60⌋ − ⌊k·rate/60⌋`. 상태가 없으므로 몰아서 스폰할 수 없다.

- 출력: 그 스텝의 스폰 수(`int`). 명령·이벤트 없음.
- 호출 단계: **[기본값]** `TableSpawnPolicy.CollectSpawns` 안에서만 호출한다(Lifecycle order 30의 `MonsterSpawner`를 거쳐). `ISpawnPolicy` 계약상 스폰 요청을 채우는 쪽이 정책이기 때문이다.

**`TableSpawnPolicy`** (`ISpawnPolicy`, 일반 플레이)

- 호출 단계: Lifecycle order 30에서 `MonsterSpawner`가 호출한다. `SpawnPolicyOverride`가 null일 때 `Reset`에서 바인딩된다(매 스텝 null 검사 없음).
- 참조: TAC-F3-2·F3-6, R9, 5c.3 #5·#10, 5.13.4, 5.15 `ISpawnPolicy`·0절 3회차 #3, TAC-F11-5.

**`Monster` 행동 (17회차, 웨이브 3 구현 확정 — `Monster.Tick`, 5.08 `IUpdatable`)**
- (17회차, PM 판정 [기본값]) **추적 "딱 맞춤"**: 추적 이동은 internal `StepMove.Toward(from, target, distance)`다 — 남은 거리의 제곱이 `distance²` 이하이면 목표 위치에 정확히 멈추고(넘어가 진동하지 않음, 결정적), 아니면 `from + delta·(distance / √|delta|²)`. 거리 0이면 제자리. M1·M2(Approach·Cooldown)·M3(사거리 밖)·M4 추적과 끌린 젬 이동(`PickupSystem`)이 같은 함수를 쓴다. 방향 단위 벡터는 `StepMove.UnitDirection`(겹치면 +x, `MoveMath.DirectionOrDefault` 관례).
- (17회차, PM 판정 [기본값]) **M2 경계 스텝**(TAC-F3-7): 트리거 조건(`dist² ≤ TriggerDistance²`)이 참인 스텝부터 Charge이고 그 스텝 이동부터 `ChargeSpeedPerStep`·고정 방향이다. `step >= PhaseEndStep`이면 Charge → Cooldown, Cooldown → Approach로 넘어가고, Approach로 넘어간 그 스텝에 바로 트리거 판정을 한다.
- M3: 사거리 안이면 멈추고 `step >= NextFireStep`일 때 `SpawnEnemyProjectile`(첫 발은 사거리에 든 첫 Tick). M4: 추적 + 패턴마다 독립 쿨다운, 쿨다운은 명령을 낸 스텝에 소비(TAC-F3-9). 모든 쿨다운의 초기값은 생성 스텝이라 첫 사용은 생성 스텝 + 1의 첫 Tick이다.
