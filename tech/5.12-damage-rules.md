### 5.12 피해·획득 규칙 구성요소 (Simulation, IMP-PLAYER/IMP-MONSTER)

```csharp
namespace Survivor.Core
{
    /// ★ (rev 16, DECISIONS 4 2026-11-07) An entity that can take weapon damage. Implemented by Monster (IMP-MONSTER);
    /// consumed by PlayerHitHandler (channel 0) and WeaponDamageResolver (IMP-PLAYER). file: Scripts/Core/IDamageable.cs (IMP-CORE)
    public interface IDamageable
    {
        /// False once health reached 0 (stays false until the entity is despawned and reused).
        bool IsAlive { get; }

        /// Subtracts amount from health at step. A call while !IsAlive is ignored (the implementation's job: extra damage to a
        /// monster already at hp <= 0 in the same step is dropped, the kill is confirmed once by KillPipeline).
        /// amount must be finite and >= 0, else ArgumentOutOfRangeException.
        void ApplyDamage(float amount, long step);
    }

    /// ★ (rev 16, DECISIONS 4 2026-11-07) An entity that damages the player on contact. Implemented by Monster (definition
    /// ContactDamage), EnemyProjectile (Damage), EnemyHazardZone (zone damage) (IMP-MONSTER); consumed by PlayerDamageReceiver
    /// (channels 3, 4, 5, IMP-PLAYER). file: Scripts/Core/IContactDamageSource.cs (IMP-CORE)
    public interface IContactDamageSource
    {
        /// Damage dealt to the player by one hit (>= 0).
        float ContactDamage { get; }
    }
}

namespace Survivor.Simulation
{
    /// Attacker-side per-target cooldown for persistent hitters (W2/E2 orbs, W3 zones). One per weapon instance.
    public sealed class ContactDamageTracker
    {
        public ContactDamageTracker(int hitIntervalSteps);
        public void OnEnter(EntityHandle target, long step);   // overlapCount++ ; mark for immediate hit check
        public void OnExit(EntityHandle target);               // overlapCount-- ; keeps nextAllowed record
        /// Appends targets to hit this step in ascending Id order and advances their nextAllowed.
        public void CollectHits(long step, List<EntityHandle> hitsOut);
        public void Forget(EntityHandle target);               // Despawned subscriber (TAC-0-10)
        public void SetInterval(int hitIntervalSteps);     // level-up / P1 change. (rev 7, D14 confirmed) W2/E2: P1-applied interval; W3 zone: definition value, never P1-scaled.
                                                           // (rev 8) applies from the next computation only: existing nextAllowed records are not recomputed (TAC-F2-3)
        public void Clear();
    }

    /// Victim-side shared invulnerability for the player (body contact, M3 projectiles, M4 zones).
    public sealed class PlayerDamageReceiver : ICollisionEventHandler, IStepPhaseHandler   // Resolve order 20
    {
        // Enter/Exit for channels 3 and 5 maintain an overlap set; channel 4 Enter is a one-shot candidate (projectile consumed).
        // Resolve: if Rules.PlayerTakesDamage && step >= _invulnerableUntilStep && (pending one-shot || overlap set non-empty):
        //   damage = max over candidates, tie -> smaller EntityHandle; _invulnerableUntilStep = step + invulnerabilitySteps (rev 14: PlayerStatsDefinition.InvulnerabilitySteps).
        // While invulnerable, channel-4 Enter consumes the projectile without damage (SPEC 3.0 I).
        // Despawned subscriber removes ids from the overlap set (no Exit on unregister).
        public long InvulnerableUntilStep { get; }
        public void Clear();
        // ★ (rev 16) constructor takes Func<EntityHandle, IContactDamageSource> contactSources (other arguments: implementer's choice);
        //   the damage of a candidate = contactSources(id).ContactDamage
    }

    /// Resolve order 10: persistent weapon damage in weapon slot order, each tracker's hits in ascending target Id.
    /// (rev 8) When !Rules.WeaponsEnabled it does not call CollectHits (orb/zone damage stops; Enter/Exit bookkeeping continues) (TAC-F2-5).
    public sealed class WeaponDamageResolver : IStepPhaseHandler { }
    // ★ (rev 16) WeaponDamageResolver and PlayerHitHandler (channel 0) constructors take Func<EntityHandle, IDamageable> damageables
    //   and call damageables(id)?.ApplyDamage(damage, context.Step)
}
```

- (16회차, DECISIONS 4절 2026-11-07) **PLAYER↔MONSTER 경계**: Simulation 안에서 IMP-PLAYER와 IMP-MONSTER는 서로의 구체 클래스를 참조하지 않는다. 피해 적용과 피해량 읽기는 위 Core 인터페이스 2개로, `PickupSystem`의 바깥 호출은 생성자 델리게이트로만 넘나든다(5.12.1, 5c.3 #13).

| 인터페이스 (Core) | 구현자 (IMP-MONSTER) | 소비자 (IMP-PLAYER) | 조회 델리게이트 (App이 주입) |
|---|---|---|---|
| ★ `IDamageable` | `Monster` | `PlayerHitHandler`(채널 0 투사체 명중), `WeaponDamageResolver`(지속 피해) | `Func<EntityHandle, IDamageable>` |
| ★ `IContactDamageSource` | `Monster`(정의 `ContactDamage`), `EnemyProjectile`(정의 `Damage`), `EnemyHazardZone`(장판 피해) | `PlayerDamageReceiver`(채널 3·4·5) | `Func<EntityHandle, IContactDamageSource>` |

- (16회차) **[기본값] 엔티티 조회 경로**: 소비자는 `CollisionEvent.A/B`(또는 트래커의 대상 핸들)에서 엔티티를 생성자로 받은 조회 델리게이트로 얻는다. App(조립 루트)이 `id => lifecycle.TryGet(id, out SimEntity e) ? e as IDamageable : null`(접촉 피해원도 같은 꼴)로 채운다. 근거: PLAYER의 EditMode 테스트가 `SimEntity` 파생 더블 없이 인터페이스 더블만으로 돌아야 하고(5c.5 EditMode 제약), LOOP 드라이버의 `Func<ITickStrategy>`·`Func<Vector2>`와 `PickupSystem` 델리게이트와 같은 관례다. **[기본값] 조회 실패**(null — 이미 회수됐거나 인터페이스를 구현하지 않은 엔티티)는 그 이벤트·대상을 무시하고 로그를 남기지 않는다. 어느 채널에 어느 레이어가 오는지는 `CollisionChannelTable`이 보장한다.
- (16회차) 피해량 타입은 `float`이다. 데이터 정의(`MonsterDefinition.ContactDamage`·`MaxHealth`, `EnemyProjectileDefinition.Damage`, `WeaponLevelDefinition.Damage`)가 모두 `float`이기 때문이다. `KillPipeline`이 "이번 스텝 hp ≤ 0이 된 몬스터"를 고르는 방법(예: `Monster`가 사망 스텝을 기억)은 MONSTER 내부이고 인터페이스에 넣지 않는다.
- (16회차, PM **[기본값]**) **플레이어 등록 경로.** 플레이어는 풀 엔티티가 아니다(`EntityCategory` 8종에 없어 `PrefabCatalog` 템플릿도 `EntityLifecycle.Spawn<T>` 경로도 없다). IMP-PLAYER의 `PlayerEntity`가 몸 바디(`CollisionLayer.PlayerBody`, 반지름 `PlayerStatsDefinition.Radius`)와 자석 바디(`CollisionLayer.PlayerMagnet`, 반지름 `PlayerStatsDefinition.PickupRadius`에 P3 적용)를 **직접 만들고**, `EntityHandleAllocator`에서 ID를 몸 → 자석 순으로 받아(1:1 → 2:1, 5.01) 현재 `ICollisionStrategy.Register`·`IPhysicsBodyRegistry.Register`에 직접 등록한다(5c.3 #1의 명시적 예외). 두 바디의 `Host`는 PLAYER가 만든 `GameObject`이고, PLAYER는 `Rigidbody2D`·콜라이더를 붙이지 않는다(`PhysicsBodySynchronizer.Register`가 멱등 추가, 5.9.1). 위치의 원본은 `PlayerEntity.Position`이며 PlayerMove 단계(`PlayerMovement`, order 0)마다 PLAYER가 두 바디의 `Position`을 함께 갱신한다. 자석 반지름이 바뀌면(P3 레벨업) PLAYER가 `Radius`를 고친 뒤 등록할 때 받은 충돌 전략의 `NotifyRadiusChanged(magnetBody)`를 부른다. 드라이버의 `StepContext.PlayerPosition`은 조립 루트가 `SimulationDriverEarly.Initialize`의 `playerPosition`에 `() => player.Position`을 넣어 얻는다(5.3).

```csharp
namespace Survivor.Simulation
{
    /// (rev 16) Run-registration contract of the player (IMP-PLAYER, Scripts/Simulation/Player/PlayerEntity.cs). Other members and the
    /// class shape are the implementer's; allocator, physics registry, stats source and host are injected by the composition root.
    public sealed class PlayerEntity   // (MonoBehaviour or not: implementer's choice)
    {
        public Vector2 Position { get; }             // authoritative; PlayerMove keeps Body/MagnetBody.Position equal to it
        public CollisionBody Body { get; }           // CollisionLayer.PlayerBody, Id 1:1 after RegisterForRun
        public CollisionBody MagnetBody { get; }     // CollisionLayer.PlayerMagnet, Id 2:1 after RegisterForRun

        /// ★ (rev 16) RunSession.Reset step ④, right after EntityHandleAllocator.Reset(): allocates body then magnet ids, places both
        /// bodies at position, registers them to collisions and the physics registry, and remembers collisions for NotifyRadiusChanged
        /// and UnregisterFromRun. Throws InvalidOperationException when already registered, ArgumentNullException for null collisions.
        public void RegisterForRun(ICollisionStrategy collisions, Vector2 position);

        /// ★ (rev 16) RunSession.Reset, before step ① (DespawnAll): unregisters both bodies from the remembered strategy and the physics
        /// registry. Ids are not freed (step ④ resets the allocator). No-op when not registered (first run).
        public void UnregisterFromRun();
    }
}
```

- (16회차 [기본값]) 현재 충돌 전략은 판마다 바뀌므로 `RunSession.Reset`이 `RegisterForRun`의 인자로 `next.Collision`을 넘긴다(`EntityLifecycle.Collisions`를 읽지 않는다 — `Reset` 안에서 교체 직후 값이 같지만 인자 쪽이 의존이 하나 적다). 해제를 ① 앞에 두는 이유: `IPhysicsBodyRegistry`에는 `Clear`가 없어 ②의 `ICollisionStrategy.Clear()`만으로는 물리 레지스트리 쪽 등록이 남는다.

- 일회성 접촉(W1·W4 투사체 → 몬스터, 젬, 상자): Enter 1회를 처리하고 `MarkConsumed` 후 `Despawn(Consumed)` 명령. 관통은 TAC-F6-9.
- 한 투사체가 같은 스텝에 몬스터 둘과 Enter하면 정렬 순서상 앞(작은 몬스터 ID)만 맞히고, 나머지 이벤트는 투사체가 `IsConsumed`라 무시한다(관통 없음 = 정확히 1회 피해, SPEC F18).
- 이미 hp ≤ 0인 몬스터에 대한 같은 스텝의 추가 피해는 무시한다(처치는 `KillPipeline`에서 1회).
- (7회차, D14 확정 2026-11-05) P1(공격 속도)은 `ContactDamageTracker`의 틱 간격 중 W2·E2 궤도 원에만 적용된다(W2의 유일한 간격). W3 장판 트래커의 간격은 정의값 `hitIntervalSteps`((14회차) 코드 이름 `WeaponLevelDefinition.HitIntervalSteps`) 그대로이며, W3에서 P1이 줄이는 것은 장판 생성 쿨다운뿐이다(TAC-F2-3, R13).
- (8회차, SPEC F2·F19 8회차) P1 변경은 `SetInterval` 뒤의 **다음 산정부터** 적용되고 기존 `nextAllowed`는 그대로다. `WeaponsEnabled == false`이면 궤도 원·장판의 피해 판정이 멈추고(`WeaponDamageResolver`가 `CollectHits`를 부르지 않음) 궤도 원 표시는 유지된다(TAC-F2-5).

#### 5.12.1 IMP-MONSTER 소유 클래스 설계 (7회차 신설)

5c.2 소유권 맵이 IMP-MONSTER에 준 클래스 중 설계 절이 없던 것을 모은다. **새 설계가 아니라** 02 TAC·5a·5c.3·5.04·5.10·5.15에 흩어진 계약을 한곳에 옮긴 것이다. 기존 문서에 없어 이 소절에서 정해야 문장이 완성된 곳은 **[기본값]**으로 표시했다. 어긋나면 원 출처(각 줄의 참조)가 우선한다. `MonsterCommandHandler`·`DropCommandHandler`는 5.04(명령 핸들러), `Monster`·`EnemyProjectile`은 5.08(`IUpdatable`)이 정의한다.

**`MonsterSpawner`** (`IStepPhaseHandler`)
- 책임: 일반 스폰과 보스 등장을 실행한다. 판 시작(`RunSession.Reset(in RunStrategies)`)에 1회 바인딩된 `ISpawnPolicy`(일반 = `TableSpawnPolicy`, 개발자 = `SpawnPolicyOverride`)를 쓰고, 상한과 배치는 정책이 아니라 이 클래스가 적용한다.
- 입력: `ISpawnPolicy.CollectSpawns(context, liveMonsterCount, spawnRng, monsterIdsOut)`·`BossSpawnDue(step)`, `StepContext.PlayerPosition`, 활성 몬스터 수, `Rules.MonsterCap`(기본 400), Spawn 스트림, `GameRules.SpawnRadius`(20), 스폰 테이블의 `bossMonsterId`(`GameDataRegistry.Current`에서 매번 읽음; (14회차) 코드 이름 `SpawnTable.BossMonsterId`, 무효면 null).
- 출력: `EntityLifecycle.Spawn` 직접 호출(명령 아님). 목록을 앞에서부터 1기마다 `live < cap`을 검사하고, 통과하면 `SpawnGeometry.PointOnCircle(playerPos, SpawnRadius, rng.NextFloat01())`로 위치를 1회 뽑아 생성한다. 실패하면 그 스텝의 남은 항목을 버린다. **[기본값]** 버린 항목은 각도를 뽑지 않는다(Spawn 스트림을 소비하지 않는다). `BossSpawnDue`가 참인 스텝에는 일반 스폰을 끝내고 보스 1기를 상한과 무관하게 같은 원주(각도도 Spawn 스트림)에 생성한다. `bossMonsterId`가 무효면 보스를 만들지 않는다(소프트락, D6). (8회차, SPEC F3 8회차) `live`는 **보스를 제외한** 활성 몬스터 수이며 `CollectSpawns`의 `liveMonsterCount`에도 같은 값을 넘긴다(R20, TAC-F3-3). (8회차, SPEC F19 8회차) 보스는 판당 1기다: 보스 등장 조건은 `!_bossSpawnedThisRun && policy.BossSpawnDue(step)`(`TableSpawnPolicy`는 `step >= BossSpawnStep`, 아래)이고, 합치면 `step >= GameRules.BossSpawnStep && !bossSpawned`다. **[기본값]** 이 플래그는 `MonsterSpawner`의 판 단위 내부 상태로, 자기 보스 생성과 `MonsterCommandHandler`가 boss 행동 몬스터를 만들 때(개발자 `SpawnBossNow` 경로) 모두 세우고(쓰기는 같은 어셈블리 `internal`), 판 리셋에서 지운다. (11회차, PM 승인) 읽기는 ★ `public bool BossSpawnedThisRun { get; }`(읽기 전용, 이 클래스의 유일한 신규 공개 멤버)로 연다. 이 값이 참이면 개발자 `SpawnBossNow`는 거부된다(판정은 `PendingCommandQueue`가 이 속성을 읽어 Begin에서, 명령은 소비, 5.15, TAC-F19-2).
- 호출 단계: Lifecycle order 30(`SimulationCommandBuffer` 0 → `LifetimeSystem` 10 → `DespawnSystem` 20 뒤, `StepOutcomeGate` 90 앞). Lifecycle에서 `EntityLifecycle`을 직접 부르는 셋 중 하나다.
- 참조: TAC-F3-2·F3-3·F3-4·F3-6·F3-10·F8-10, R7·R10·R11·R20, D4·D6, 5c.3 #5·#9·#10, 5.04 메모, 5.15 `ISpawnPolicy`·`IDevModeHost.SpawnPolicyOverride`.

**`SpawnScheduler`**
- 책임: 구간 안 스텝 k의 스폰 수를 누적 변수 없이 계산한다. `SpawnsDueAtStep(rate, k) = ⌊(k+1)·rate/60⌋ − ⌊k·rate/60⌋`. 상태가 없으므로 몰아서 스폰할 수 없다.
- 입력: 구간의 `spawnsPerSecond`(rate), k = 현재 스텝 − 구간 시작 스텝(`startSeconds`를 R1로 환산한 값). (14회차) 코드 이름 `SpawnSegmentDefinition.SpawnsPerSecond`·`StartStep`·`EndStep`.
- 출력: 그 스텝의 스폰 수(`int`). 명령·이벤트 없음.
- 호출 단계: **[기본값]** `TableSpawnPolicy.CollectSpawns` 안에서만 호출한다(Lifecycle order 30의 `MonsterSpawner`를 거쳐). `ISpawnPolicy` 계약상 스폰 요청을 채우는 쪽이 정책이기 때문이다.
- 참조: TAC-F3-2·F3-3, R1, 5.13.4, 5c.5 "스폰 스케줄".

**`TableSpawnPolicy`** (`ISpawnPolicy`, 일반 플레이)
- 책임: 현재 스텝이 속한 스폰 테이블 구간(`startSeconds` 포함, `endSeconds` 미포함)을 찾아 `SpawnScheduler`의 수만큼 몬스터 종을 고른다. 종 선택은 구간 `entries`의 `weight`로 `WeightedSampler.PickIndex`(R9, 복원 추출)를 Spawn 스트림으로 뽑는다. 구간 밖 스텝(600초 이후 포함)은 0기다.
- 입력: `in StepContext`(스텝), `liveMonsterCount`, `spawnRng`(Spawn 스트림), 스폰 테이블(`GameDataRegistry.Current`, 참조할 때마다 읽음 — 핫 리로드 적용 시점은 5.11.1 표). **[기본값]** `liveMonsterCount`는 쓰지 않는다(상한은 `MonsterSpawner`가 적용한다).
- 출력: `monsterIdsOut`에 몬스터 ID를 추첨 순서대로 채운다. 명령 없음. `BossSpawnDue(step)`은 (8회차 정정, SPEC F19 8회차) `step >= GameRules.BossSpawnStep`(36000)이다 — 7회차의 `==` [기본값]을 대체한다. `>=`라 시간 점프로 36000을 건너뛰어도 등장하고, 재등장은 `MonsterSpawner`의 "이번 판 보스 생성됨" 플래그가 막는다(위).
- 호출 단계: Lifecycle order 30에서 `MonsterSpawner`가 호출한다. `SpawnPolicyOverride`가 null일 때 `Reset`에서 바인딩된다(매 스텝 null 검사 없음).
- 참조: TAC-F3-2·F3-6, R9, 5c.3 #5·#10, 5.13.4, 5.15 `ISpawnPolicy`·0절 3회차 #3, TAC-F11-5.

**`DespawnSystem`** (`IStepPhaseHandler`)
- 책임: 플레이어에게서 너무 멀어진 일반 몬스터를 회수한다. 보스는 보지 않는다. 젬·상자도 보지 않는다(젬·상자에는 디스폰 경로가 없다).
- 입력: 활성 몬스터(`EntityHandle` 오름차순), `StepContext.PlayerPosition`, 디스폰 거리 D(스폰 테이블 `despawnDistance`((14회차) 코드 이름 `SpawnTable.DespawnDistance`), 기본 45, 개발자 덮어쓰기는 R26). (15회차, PM **[기본값]**) D는 `SimulationRules.DespawnDistanceOverridden`이 거짓이면 **참조할 때마다** `GameDataRegistry.Current`의 `SpawnTable.DespawnDistance`를 읽고, 참이면 개발자 `SetDespawnDistance`가 쓴 `Rules.DespawnDistance`를 쓴다. `SwapData`는 D를 건드리지 않으므로 핫 리로드 뒤 새 D는 이 경로로 반영된다(5c.3 #10의 적용, 새 규칙 아님, 5.11.1·5.15).

- 책임: 젬 끌림 이동과 젬·상자 획득을 처리한다. 젬 판정은 채널 두 개다(자석 Enter = 끌림 시작, 몸통 Enter = 획득, D16).
