- (2회차) `MovingObjectSpec.Layer`는 Core의 `CollisionLayer`를 그대로 쓴다. 1회차의 별칭 `CollisionLayerTag`는 C#에서 파일을 넘어 공유되는 형식 별칭을 만들 수 없어 없앴다.
- 파서(2회차, D17 확정): Newtonsoft `JToken.Parse`(`JsonLoadSettings { LineInfoHandling = Load, DuplicatePropertyNameHandling = Error }`)로 트리만 만들고, 바인딩은 리플렉션 없이 손으로 쓴다(필수·알 수 없는 키·타입을 직접 판정). 패키지는 웨이브 0에서 사용자가 추가한다(승인 게이트). 읽기는 TAC-F11-6.
  - (14회차, [기본값] 교체 명문화) 구현(`JsonTreeReader`, internal)은 `JToken.Parse` 대신 `JsonTextReader`(`DateParseHandling = None`, `FloatParseHandling = Double`) + `JToken.ReadFrom(reader, settings)`를 쓰고, 루트 값 뒤의 후행 내용(주석 제외)은 직접 거부한다(파일 단위 실패). `JsonLoadSettings`의 `LineInfoHandling = Load`·`DuplicatePropertyNameHandling = Error`는 같고, `CommentHandling = Ignore`가 더 있다. 이유: `JToken.Parse`는 날짜꼴 문자열을 날짜로 바꾼다. 선두 BOM(U+FEFF)은 파싱 전에 떼어 낸다. 패키지는 (14회차) 2026-11-06 `Packages/manifest.json` 직접 의존으로 추가됐다(U25 확인됨).
- 파일 단위 정책: 필수 4종(weapons, monsters, spawnTable, playerStats)이 없거나 전체 파싱에 실패하면 Blocking이다. 선택 3종은 Warning이고 폴백한다. 정의 단위 오류는 그 정의만 건너뛰고 Warning이다. 플레이어 기본 스탯은 정의 단위 오류도 Blocking이다(SPEC F11).
  - (14회차, 구현이 정한 엄격성 규칙 — PM 판정: [기본값]으로 명문화, 설계 변경 아님) 파일 단위: (1) `schemaVersion`이 없거나 정수 1이 아니면 파일 전체 실패다(필수 4종이면 Blocking, 선택 3종이면 Warning + 폴백). 루트가 객체가 아니거나 정의 배열(`weapons` 등)이 없을 때도 같다. (2) 스폰 테이블 최상위 오류(`despawnDistance` ≤ `GameRules.SpawnRadius`(20), `segments` 누락 또는 빈 배열 등)는 Blocking이고 스폰 테이블 없음으로 취급한다(플레이 불가 4기준의 "스폰 테이블 없음"도 함께 기록됨). (3) 레벨업 풀 최상위 오류는 Warning이고 `UniformFallback`으로 대체한다.
  - (14회차, 같은 판정) 정의 단위: (4) 정수 필드에 실수(2.0 포함)는 타입 오류다. (5) `bossMonsterId` 누락·무효(형식 오류, 없는 ID, boss 행동이 아님)는 Warning이고 `SpawnTableDefinition.BossMonsterId`는 null이다(D6 그대로). (6) 보스 소환(`summon`) 패턴의 `monsterId`가 무효(없는 ID 또는 보스)면 **그 보스 정의 전체**를 건너뛴다(Warning). (7) `targetId`가 없거나 형식 오류인 레벨업 규칙은 바인딩(5.11.0 ③)에서, 존재하지 않는 무기·패시브를 가리키는 규칙은 참조 검증(5.11.0 ④)에서 그 규칙만 건너뛴다(둘 다 Warning). (8) 유효 항목이 0개인 스폰 구간은 건너뛴다(Warning). 구간 `endSeconds`가 600을 넘으면 600으로 자르고 Warning, 앞 구간과 겹치면 그 구간을 건너뛴다(Warning). (9) 조합 규칙이 같은 `weaponId`를 두 번 쓰면 뒤 규칙을 건너뛴다(Warning). 알 수 없는 키는 Warning만 남기고 정의를 무효로 만들지 않는다.
  - (14회차, 같은 판정) 터널링(⑥ 단계): 1단 실패 객체마다 Warning 1건 + 그 객체가 2단에서 지목한 쌍마다 Warning 1건이다. 2단은 1단 실패 객체에 대해서만 돈다. 검사 목록에 상자·플레이어 자석은 없고, 장판(W3 `zone`, 보스 `hazardZone`)은 속도 0으로 들어 있다. 플레이어는 P2 최대 단계, 궤도 원은 `|ω|·R + 플레이어 최대 속도`(D1·D2), 젬은 `gemAttractSpeed`·`gemRadius`, M2는 몸통 이동과 돌진(`charge`) 두 항목이다.
- 플레이 불가 4기준: 사용 가능한 무기 0개, 스폰 가능한 몬스터 0종(스폰 테이블이 참조하는 유효 몬스터 기준), 플레이어 기본 스탯 없음, 스폰 테이블 없음. `startingWeaponId`가 유효하지 않으면 플레이어 기본 스탯 오류(Blocking)로 본다 [기본값, D7]. (14회차) `startingWeaponId`가 진화 전용 무기여도 같은 Blocking이다. `PlayabilityChecker.Check`가 실패한 기준마다 Blocking 1건을 넣으므로 `IsPlayable`("Blocking 0건")은 "Blocking 없음 + 4기준 충족"과 동치다.

#### 5.11.0 최초 로드 (4회차 신규)

- **호출 주체**: 부팅 시 최초 로드는 `GameBootstrap.Awake`(App, **IMP-FLOW 소유**, 5c.2)가 한 번 한다. 순서는 `SimulationSettingsApplier.Apply()` → `PhysicsSettingsApplier.Apply()` → `DisplaySetup.Apply()` → `GameDataLoader.LoadAll(Application.streamingAssetsPath)`(**IMP-DATA 소유**) → `GameDataRegistry.Initialize(data, report)` → `report.IsPlayable`이면 `FlowState.Title`, 아니면 `FlowState.DataError`로 F11 시작 차단 화면(TAC-F8-4, `LastReport.BlockingIssues` 표시)이다. `DataError` 상태에서는 `Current`가 null이고 판을 시작할 수 없다. 개발자 모드의 `DevModeEntry`(AfterSceneLoad)는 이 뒤에 붙는다(U40).
- **검증 묶음 호출 순서 (고정)**: `LoadAll`/`LoadFromTexts` 내부에서 항상 ① 파일별 읽기(UTF-8, U+FFFD 경고) → ② `JsonTreeReader`(Newtonsoft 파싱, 파일 단위 실패 판정) → ③ `Binders/*`(필드 바인딩·정의 단위 검증·ID 중복·초→스텝 환산, 7종 고정 순서: PlayerStats, Weapons, Passives, Monsters, SpawnTable, Combinations, LevelUpPool — 참조되는 쪽 먼저) → ④ 파일 간 참조 검증(조합·스폰 테이블·`startingWeaponId`·보스 소환 `monsterId`·(14회차) 레벨업 규칙 `targetId`) → ⑤ `PlayabilityChecker`(플레이 불가 4기준) → ⑥ `TunnelingInvariantValidator.Validate`(경고만) 순이다. 핫 리로드도 같은 `LoadAll`을 쓰므로 같은 순서를 탄다. (14회차) 구현 확인됨: `GameDataLoader`가 이 순서 그대로다(④ 안의 순서는 `startingWeaponId` → 보스 소환 → 스폰 테이블 → 조합 → 레벨업 규칙). 끝에 요약 한 줄(파일 수·정의 수·경고·차단 건수)을 `[Data]` INFO(플레이 가능) 또는 WARN(불가)으로 남긴다.

#### 5.11.1 핫 리로드 적용 시점 (2회차 신규, Q43 확장)

교체는 `SwapData` 대기 명령으로 다음 스텝 `Begin`에서 일어난다. 그 뒤 각 데이터의 적용 시점:

| 데이터 | 새 정의가 적용되는 때 | 유지되는 것 |
|---|---|---|
| 무기 | 다음 레벨업 선택지 생성, 다음 새 무기 획득 | 보유 무기 인스턴스는 생성 때 받은 정의 유지. (8회차, SPEC F19 8회차) 단계 수(5단계 여부)·강화 가능 판정(R22)·강화 후보도 인스턴스의 정의 기준이고, 새 파일에서 삭제된 무기의 보유 인스턴스도 유지된다(5.14) |
| 몬스터 | 다음 스폰 | 활성 몬스터는 기존 정의 유지 |
| 스폰 테이블 | 다음 스텝의 스폰 계산부터(`MonsterSpawner`가 매 스텝 `Current.SpawnTable`을 읽는다). `despawnDistance`도 다음 스텝부터(개발자가 D를 덮어쓴 경우는 덮어쓴 값 유지). (15회차 [기본값]) `SwapData`는 D를 건드리지 않고, `SimulationRules.DespawnDistanceOverridden`이 거짓이면 `DespawnSystem`이 참조할 때마다 `Current`의 D를 읽는다(5.12.1·5.15) | 이미 스폰된 몬스터 |
| 패시브 | 다음 선택지 생성 | 보유 패시브의 정의. (8회차) 단계 수·강화 후보도 그 정의 기준, 삭제된 패시브의 보유 인스턴스도 유지 |
| 조합 규칙 | 다음 진화 판정(상자 획득) | - |
| 레벨업 풀 | 다음 선택지 생성 | 열려 있는 회차의 선택지 3개 |
| 플레이어 기본 스탯 | 다음 참조부터: `moveSpeed`·`pickupRadius`(자석 반지름 갱신)·`invulnerabilitySeconds`·`radius`(바디 반지름 갱신, `NotifyRadiusChanged`)·`xpCurve`(다음 레벨업 판정)·`pickups`(다음 젬·상자 생성) | **현재 체력과 최대 체력**(PM 방향), 현재 레벨·경험치. `startingWeaponId`는 다음 판부터 |

- 열거형(`Definitions/DefinitionEnums.cs`): `WeaponBehavior { Projectile, Homing, Orbit, Zone }`, `ZonePlacement { NearestEnemy, Player }`, `MonsterBehavior { Chaser, Charger, Ranged, Boss }`, `BossPatternKind { HazardZone, Summon }`, `PassiveStat { AttackSpeed, MoveSpeed, PickupRadius }`. `DataFileKind`·`IssueSeverity`는 `DataEnums.cs`.
- 명명 규칙(TAC-F11-3 확인됨): 원본 초 값은 `*Seconds`(속도·각속도는 파일 단위 이름 그대로 `MoveSpeed`·`AngularSpeedDegPerSec` 등), R1·R3 환산값은 `*Steps`/`*PerStep`. 소비자는 환산값만 읽는다.
- 정의 객체의 setter는 `internal`이므로 다른 어셈블리(소비자·테스트)는 정의를 직접 만들 수 없고 `GameDataLoader.LoadFromTexts`로만 만든다(5c.5). `GameData` 생성자도 internal이다.
- `GameData`의 ID 조회(`TryGetWeapon` 등)는 서수 비교(대소문자 구분)이고 null ID는 false다. `Combinations`·`Passives`는 파일 없음·오류 시 빈 목록, `SpawnTable`·`PlayerStats`는 무효 시 null이다.
