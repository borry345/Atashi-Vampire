### F18. 충돌 판정 전략 교체

**요구사항**: 모든 피격·접촉·획득 판정을 `ICollisionStrategy` 인터페이스 뒤로 분리하고 두 방식을 교체할 수 있게 한다. 판정은 고정 스텝에서 수행한다.

- 구현 A: `Collider2D` 기반 (Unity 물리, CCD 끔 `Discrete`)
- 구현 B: 자체 제곱거리 판정 (원-원)

**교체 범위: 다섯 판정 전부**. 근거: W2 궤도·W3 장판은 몬스터와 충돌하므로 이를 `Collider2D`에 맡기려면 몬스터 400마리가 전부 `Collider2D`를 유지·갱신해야 한다. 궤도 개수가 적은 것은 무관하다. 그러면 객체당 유지 비용 400개 분량과 `Physics2D` 시뮬레이션이 그대로 남아 비교가 무의미해진다.

1. 내 투사체 ↔ 몬스터
2. 경험치 젬 ↔ 플레이어
3. 플레이어 ↔ 몬스터
4. W2 궤도 ↔ 몬스터
5. W3 장판 ↔ 몬스터

여기에 **M3 적 투사체 ↔ 플레이어, 상자 획득, M4 보스 장판 ↔ 플레이어**도 같은 인터페이스를 통해 판정한다. 무기 모양을 원으로 정의했으므로(F6) 모든 판정이 원-원이며 판정 함수가 하나다. 몬스터의 `Collider2D`는 **구현 A(`Collider2D` 전략)와 `Physics2D` 쿼리 전략(F16 구현 C)을 쓸 때만 켜는 토글 구조**다. 전략 전환은 **다음 판 시작 시** 적용된다(3.0 B).

**인터페이스 규약**: 두 방식의 성격이 반대다(엔진은 콜백 기반 수동, 자체는 폴링 기반 능동). **폴링 쪽으로 통일**한다. `ICollisionStrategy.CollectEvents()`는 **이번 스텝의 Enter(새로 겹친 스텝)·Exit(겹침이 끝난 스텝) 이벤트 목록**을 **(채널, ID) 순으로 정렬**해 반환한다. 이벤트 종류는 이 두 가지뿐이다. 엔진 구현은 `OnTriggerEnter2D`/`OnTriggerExit2D` 콜백에서 이벤트를 큐에 모아두고 스텝 끝에 목록으로 반환한다. 이렇게 하면 **피해 적용 로직이 전략과 무관하게 하나로 유지**된다(피해 적용은 3.0 I). 반환 목록은 (채널, ID) 순으로 정렬해 두 전략 모두 결정론을 확보한다. 결정론은 "자체 판정을 고를 이유"가 아니라 두 전략 모두가 갖춰야 할 공통 요건이다. 이벤트 비교 키는 **(스텝 번호, 종류, 채널, 객체 ID 쌍)** 이며, 채널은 판정 종류(위 1~5와 추가 3종)를 구분한다(TECH_SPEC D8).

**수용 기준**

*판정 규칙*
- 주어진 같은 배치에서 두 구현이 다섯 판정(및 추가 3종)의 "충돌 여부"를 같게 판정해야 한다 (원 근사 반지름이 동일한 조건 내). 판정 경계(정확히 접촉하는 거리)의 처리는 하나로 고정한다.
- 주어진 구현 B에서 두 객체 중심 간 제곱거리가 (반지름 합)² 이하이면 충돌, 초과면 비충돌로 판정되어야 하며, 제곱근 연산 없이 제곱 비교만으로 판정해야 한다.
- 주어진 구현 B에서 후보는 F16의 공간 해시로 추려야 한다. 전체 쌍을 전수 비교하지 않아야 한다. 보스(M4)는 공간 해시에 없으므로 별도 리스트에서 전수 검사해 판정에 포함해야 한다.
- (5회차 수정) 주어진 구현 B에서 경험치 젬과 몬스터에는 `Collider2D`가 없거나 비활성이어야 한다 (W2 궤도·W3 장판 포함 모든 판정이 자체 처리되므로). **단, 타깃 탐색 구현 C(`Physics2D` 쿼리)를 함께 쓰는 조합에서는 몬스터 `Collider2D`가 질의 전용으로 켜지며 충돌 판정에는 쓰이지 않는다. 젬은 항상 없거나 비활성이다.** (TECH D27)
- 주어진 구현 B에서 W2 궤도(작은 원 여러 개)와 W3 장판(원형 영역)은 원-원 판정으로 몬스터와 판정되어야 한다.
- 주어진 관통 없는 투사체(W1)가 한 번 명중하면 두 구현 모두 정확히 1회 피해만 주어야 한다.
- 주어진 같은 시드·입력 시퀀스에서 두 구현이 스텝 단위로 같은 피격·처치 결과를 내야 한다 (고정 스텝 덕분에 프레임레이트에 무관).
- (4회차 수정) 주어진 구현을 런타임 토글 또는 빌드 설정으로 전환할 수 있어야 한다. 런타임 토글의 효과는 **다음 판 시작 시 적용**된다(3.0 B).
- 주어진 호출자는 `ICollisionStrategy`에만 의존해야 하며, 반환된 이벤트 목록을 소비하는 피해 적용 로직이 전략별로 중복되지 않고 하나여야 한다.
- (5회차 수정) 주어진 엔진 구현이 모아둔 Enter/Exit 이벤트는 **(채널, ID) 순**으로 정렬되어 반환되어야 한다. 자체 판정(구현 B)도 같은 순서로 반환해야 한다.
- 주어진 두 구현에 대해 F10 항목을 동일 조건에서 측정한 결과가 기록되어야 한다 (F10 묶음 A).
- (4회차 신규) 주어진 `CollectEvents()`는 **Enter와 Exit 두 종류**의 이벤트만 반환해야 한다. Enter는 이번 스텝에 새로 겹친 쌍, Exit는 이번 스텝에 겹침이 끝난 쌍이며, 겹침이 지속되는 스텝에는 이벤트가 나오지 않아야 한다(두 전략 모두).
- (4회차 신규) 주어진 자체 판정(구현 B)은 폴링 결과를 이전 스텝과 비교해 Enter/Exit를 만들고, 엔진 구현(구현 A)은 `OnTriggerEnter2D`/`OnTriggerExit2D` 콜백을 큐에 모아 반환해야 한다. 두 구현이 같은 스텝에 같은 Enter/Exit를 내야 한다.
- (4회차 신규) 주어진 이벤트 목록의 각 항목은 (스텝 번호, 종류, 채널, 객체 ID 쌍)을 담아야 하며, 객체 ID는 3.0 H의 "인덱스 + 세대" 형식이어야 한다.

*터널링 방지: 객체별 불변식 (JSON 로드 시 검증, 런타임 보정 아님)*

고정 스텝이므로 터널링은 속도 데이터만의 함수다. 두 객체 a, b가 한 스텝에 서로 통과하지 않을 조건은 `(v_a + v_b)/60 ≤ r_a + r_b`이고, 이는 `(v_a/60 - r_a) + (v_b/60 - r_b) ≤ 0`으로 객체별 항으로 분리된다. 따라서 **모든 객체가 각자 `v_x/60 ≤ r_x`를 만족하면 모든 쌍이 자동으로 안전하다.** 불변식의 의미는 "어떤 객체도 한 스텝에 자기 반지름보다 멀리 이동하지 않는다"이다.

- 주어진 JSON 로드 시 **1단(O(N))**: 모든 이동 객체에 대해 `v_x/60 ≤ r_x`를 검사해야 한다. 전부 통과하면 모든 쌍이 안전하므로 검증을 끝내야 한다.
- 주어진 1단을 통과하지 못한 객체가 있으면 **2단**: 그 객체만 실제 충돌 상대와 쌍별로 `(v_a+v_b)/60 ≤ r_a+r_b`를 검사하고, 경고는 **어느 쌍이 위험한지 지목**해야 한다.
- 검사 대상 이동 객체에는 W1·W4 투사체, 몬스터(돌진 속도 포함), M3 적 투사체, **W2 궤도(플레이어 주변을 회전하므로 선속도가 있다)** 가 포함되어야 한다. **W3 장판은 정지해 있지만 식에 포함**시켜 자동 확인해야 한다 (손으로 "괜찮을 것"이라 판단하면 나중에 장판 크기를 조정했을 때 조용히 깨진다).
- 주어진 위반이 있어도 **경고만 하고 시작을 차단하지 않아야 한다** (StreamingAssets 편집 허용 취지, F11).
- 이 구조를 택한 이유: 쌍별 전수 검사는 O(N×M)이라 데이터가 늘수록 커지고 "코드 수정 없이 JSON만으로 추가"라는 F11의 핵심 주장과 구조가 어긋난다. 객체별 불변식은 O(N)이고 새 데이터를 추가할 때 그것만 검사하면 된다. (대안 기록은 F14.)

*동등성 검증 테스트 3종*
- (4회차 수정) **E1**: 주어진 같은 시드·같은 입력에서 자체 판정(구현 B)과 엔진판(`Collider2D`, CCD 끔 `Discrete`)이 **동일한 충돌 이벤트 집합**을 생성해야 한다. 비교 대상 이벤트는 위 Enter/Exit 이벤트이며, 비교 키는 **(스텝 번호, 종류, 채널, 객체 ID 쌍)** 이다. 충돌 이벤트 로그는 F19로 기록·내보낸다.
- (4회차 수정) **E2**: 주어진 기본 데이터 범위에서 엔진판 `Discrete`와 엔진판 `Continuous`(CCD 켬)가 **동일한 충돌 이벤트 집합**(같은 비교 키)을 생성해야 한다. 이것이 "CCD 유무와 무관하게 결과가 같다"는 주장의 직접 검증이다.
- **E3**: 주어진 기본 JSON의 모든 이동 객체가 위 불변식을 만족해야 한다. 게임을 돌리지 않고 데이터만 읽어 확인하는 정적 검증이다.
- E1 + E2의 추이성으로 "자체 판정 ↔ 엔진판 Continuous"까지 덮인다.
- **비교 실험에서는 양쪽 모두 CCD를 끈 상태(`Discrete`)로 맞춘다.** Unity 2D의 CCD는 `Rigidbody2D`의 Collision Detection을 `Continuous`로 명시해야 켜지며 기본값은 `Discrete`로 이해하고 있다. 이 기본값은 구현 단계에서 실측 확인이 필요하다 (Q39).
