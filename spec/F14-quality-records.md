### F14. 품질 관리 기록 **[사용자 수행]**

**수용 기준**
- (사용자 수행) 트러블슈팅은 `docs/devlog.md` 단일 파일에 기록되어야 한다.
- (사용자 수행) 각 트러블슈팅 항목은 "문제 → 원인 → 해결 → 배운 점" 4단 구조를 모두 갖추어야 한다. 한 단계라도 비어 있으면 완료 항목으로 세지 않는다.
- (사용자 수행) 트러블슈팅은 6건 이상이어야 한다.
- (사용자 수행) 측정 기록은 F10의 구성(A0 기준선 탐색, A 전략 비교 6회, B 스케일링 곡선 8회, C 엔진 대안 2회)과 상호작용 해석을 모두 포함해야 한다 (F10 연계).
- (사용자 수행) 다이어그램은 2개여야 한다 (F12 연계).
- (4회차 수정) (사용자 수행) `docs/devlog.md`에 **"검토했으나 채택하지 않은 대안"** 전용 섹션이 있어야 한다. 각 항목은 대안 이름 / 검토한 이유 / 채택하지 않은 근거를 담아야 한다. 최소 다음 **네 건**을 포함한다.
  - **sweep and prune**: Box2D·Bullet의 broadphase 기법이지만, 이 프로젝트의 질의가 국소 이웃 열거이지 전역 구간 집계가 아니고, 공간 해시가 O(1) 삽입·질의인 데 비해 로그 인자가 추가 비용이며, 이 규모에서는 캐시 지역성이 복잡도보다 지배적이라고 판단해 채택하지 않았다.
  - **터널링 쌍별 검사**: 모든 (객체, 상대) 쌍을 검사하는 방식은 O(N×M)이라 데이터가 늘수록 커지고 "코드 수정 없이 JSON만으로 추가"라는 F11의 주장과 구조가 어긋나, 객체별 불변식(O(N))으로 교체했다.
  - **ScriptableObject (JSON 대신)**: 에디터에서 프리팹·스프라이트를 직접 참조로 물릴 수 있어 "코드 수정 없이 추가"를 깔끔히 만족하지만, 빌드 후 편집이 불가능해 "빌드된 게임에서 데이터 파일만 편집해 추가"라는 시연을 할 수 없어 JSON(`StreamingAssets`)을 택했다. 대가로 파서·에셋 키 레지스트리·스키마 검증을 직접 만든다.
  - **Development Build 전용 개발자 모드**: 스크립팅 심볼로 컴파일을 분리하면 코드 자체가 없어 "꺼져 있으면 동일 동작"을 가장 강하게 충족하지만, 배포 빌드 하나로 플레이·측정·JSON 핫 리로드 시연을 모두 할 수 없어 릴리스 빌드에도 포함하고 `--dev` 인자로 활성화하는 쪽을 택했다. 대가로 동일 동작은 코드 부재가 아니라 측정(F19의 인자 없는 릴리스 빌드 vs `SURVIVOR_NO_DEV` 빌드 비교)으로 보인다.
  이 섹션이 "트레이드오프를 알고 선택했다"를 문서로 증명한다.
- (사용자 수행) 버그는 GitHub Issues로 트래킹하고, 트러블슈팅 기록(`devlog.md`)과는 분리한다. 버그 이슈가 해결된 뒤 배울 점이 있으면 `devlog.md`에 옮겨 적는다.
- (사용자 수행) 테스터 2~3명(지인, SSAFY 동기)에게서 받은 피드백이 `devlog.md`에 기록되어야 한다.
- (4회차 수정) (사용자 수행) 기록은 개발 중 그때그때 남겨야 하며 마지막에 몰아쓰기하지 않는다. 이는 **기능 브랜치 머지 커밋에 해당 devlog/README 변경이 포함된다**로 검증한다(머지 커밋에 기능별 필수 기록 변경이 없으면 위반).
- (사용자 수행) 커밋 이력은 정리된 상태여야 한다. 규칙은 Conventional Commits를 느슨하게 적용한다: `feat:` `fix:` `perf:` `refactor:` `docs:` `test:` 접두사만 지키고, 1커밋 = 1관심사로 한다. 엄격한 scope·본문 형식은 강제하지 않는다.
- (사용자 수행) 브랜치는 `main` + 기능별 feature 브랜치를 쓰며, 머지 후 feature 브랜치를 삭제한다.
- (4회차 신규) (사용자 수행) 주어진 **기능별 필수 기록 매핑 표**(아래)의 기록이 각 기능마다 존재해야 한다.
- (4회차 신규) 주어진 기능의 필수 기록이 없으면 **그 기능은 미완료**다. 이것이 기능 **완료 판정 조건**이며, team-lead는 tester의 판정과 함께 해당 기능의 필수 기록 존재를 확인한 뒤에 완료로 처리한다(PRD 공통 성공 조건 "기록이 없으면 해당 기능은 완료로 보지 않는다"의 검증 수단).
