# SPEC: 뱀서라이크 1차 MVP

> 기준 문서: `PRD.md` (동결된 스냅샷, 수정하지 않음). 이 문서가 현재 범위의 유일한 기준이다. PRD의 기능 ID F1~F15는 이름과 번호를 그대로 이어받았고, F16~F19는 SPEC 단계에서 추가했다. 목표/비목표는 PRD를 따르며 여기서 재진술하지 않는다. 4회차 개정은 3회차 이후 확정된 결정(RUN_LOG 2026-10-16)을 반영하고, PRD에서 빠졌던 요구(측정 항목 "메모리", 기능별 필수 기록)를 복원하며, 측정 설계의 구멍과 세 문서가 놓친 규칙을 메웠다. 이번 개정(5회차)은 2차 독립 검토 결과를 반영한 소폭 개정이다 — 측정 시작 가드 규칙의 모순 해소, 개발자 모드 오버헤드 비교의 판정 가능화, 충돌 정렬 키·측정 조건·ID 세대 범위의 명확화. 6회차 개정은 F6 무기 절의 표기 보강(W4 소멸 규칙 명시)과 W2 궤도 원 생애 규정(RUN_LOG 2026-10-21)이다. 수정한 기존 수용 기준에는 "(4회차 수정)", "(5회차 수정)" 또는 "(6회차 보강)", 새로 붙인 수용 기준에는 "(4회차 신규)", "(5회차 신규)" 또는 "(6회차 신규)"를 표시했다.

## 1. 개요 (Overview)

Unity 6000.3.26f1(Unity 6.3 LTS), Universal 2D(URP) 템플릿, C#으로 만드는 뱀서라이크 1차 MVP다. 화면은 창 모드, 16:9 고정이며, 시작 시 모니터 작업 영역에 들어가는 가장 큰 16:9 해상도(1920x1080 → 1600x900 → 1280x720)를 자동으로 고른다. 카메라는 orthographic size 9(월드 단위)라 보이는 범위는 해상도와 무관하고, UI는 Canvas Scaler로 스케일한다. 플레이어는 WASD/방향키로 **경계 없는 무한 평면**을 이동하고(맵 크기라는 개념이 없고 배경은 반복 배경이다), W1 투사체를 보유한 채 시작하며 무기는 자동으로 공격한다. 몬스터를 처치해 얻은 경험치 젬으로 레벨업하며, 항상 3칸으로 표시되는 선택지 중 하나를 골라 성장한다. 진화는 조건을 갖춘 상태에서 상자를 획득할 때 일어난다. 10분을 생존하고 최종 보스를 처치하면 클리어, 사망하면 게임 오버다. 결과물은 Windows 10/11 64비트 실행파일(GitHub Releases 배포)이다. 아트는 Unity 기본 Sprite와 색상으로 만든 도형을 쓰고 사운드는 제외한다.

게임 상태를 바꾸는 모든 로직(이동, 충돌 판정, 스폰, 디스폰, 투사체 수명 등)은 **1/60초 고정 타임스텝**(`FixedUpdate`)에서 실행하고, 렌더링과 입력 수집만 매 프레임(`Update`)에서 한다. 그래서 동작이 프레임레이트와 무관하다. 모든 시뮬레이션 객체는 "인덱스 + 세대" 형식의 ID를 가지며, 타이브레이크·쿨다운 기록·충돌 로그가 모두 이 ID를 쓴다.

이 프로젝트의 핵심 축은 게임 규모가 아니라 기록의 깊이다. 그래서 오브젝트 풀링(F9), 타깃 탐색(F16), Update 집중화(F17), 충돌 판정(F18)을 모두 전략 인터페이스로 분리해 교체 가능하게 만든다. 실제 게임 씬 위에서 켜는 **개발자 모드(F19)** 는 릴리스 빌드에도 포함되며 커맨드라인 인자 `--dev`로 활성화한다. 이 모드로 측정·디버그하며, 총 16회 측정(전략 비교 6 + 스케일링 곡선 8 + 엔진 대안 2, 그 앞에 기준선 탐색 A0)을 **6개 항목**(평균 FPS, 1% low, 프레임당 GC 할당, 동시 몬스터 수 한계, 시스템 ms, 메모리)으로 기록해 단독 기여와 상호작용을 확인한다(F10). 무기·몬스터·조합 규칙·스폰 테이블·패시브·레벨업 선택지 풀·플레이어 기본 스탯 7종은 JSON 데이터로 관리한다(F11). 이 과정을 README와 `docs/devlog.md`에 남기며, 기능별 필수 기록이 없으면 그 기능은 완료로 보지 않는다(F14).

**4회차 변경 요약**: 3회차 이후 RUN_LOG(2026-10-16)에서 확정된 결정을 반영했다 — 개발자 모드는 릴리스 빌드에도 포함하고 `--dev`로 활성화하며 비활성 상태에서는 시작 시 인자 확인 1회 외에 분기·감시가 없다(Q40), 충돌 이벤트는 Enter/Exit 두 종류이고 비교 키에 채널이 들어간다(Q41), 피해 적용은 일회성 접촉 / 공격자 측 쌍별 쿨다운 / 플레이어 공통 무적 세 갈래이며 모두 스텝 번호로 센다, 객체 ID는 인덱스+세대 형식이다, JSON 파서는 Newtonsoft이다, 젬·상자는 디스폰하지 않되 활성 젬 수를 기록한다, 창은 자동 선택한 16:9 해상도의 창 모드이고 카메라 orthographic size는 9이다. 또한 PRD가 요구했으나 빠졌던 측정 항목 "메모리"를 복원해 측정 항목을 6개로 늘리고, F14에 기능별 필수 기록 매핑 표와 "기록이 없으면 미완료"라는 완료 판정 조건을 신설했다. 측정 설계는 항목 4를 A0 스윕 전용으로 한정하고, N에 따른 디스폰 거리 공식, 무적·고정 무기 구성·스폰 중단+N 유지 조건, 측정 환경 고정, 워밍업 300스텝 제외, 측정 중 배제 조건, 배속 상한 3x, 스텝당 ms 정의를 보강했다. 마지막으로 세 문서가 놓친 규칙(사망>클리어>레벨업 우선순위, 포커스 상실 자동 일시정지, 개발자 모드 판의 최고 기록 미저장, 카메라 즉시 스냅, JSON 인코딩, 테스터 배포 요건 등)을 PM 기본값으로 채웠다. 미확정 사항은 Q1·Q38·Q39만 미확정으로 남기고 나머지는 "기본값 채택"으로 표시했으며, 신규로 Q45(측정 목표치 확정 시점)를 등록하고 작은 공백 모음 Q46은 PM 기본값으로 확정해 본문에 반영했다.

**5회차 변경 요약**: 2차 독립 검토 결과를 반영했다. ① F18의 "몬스터 Collider2D 없음/비활성" 기준에 타깃 탐색 구현 C(`Physics2D` 쿼리) 조합의 예외를 추가했다(TECH D27). ② 측정 시작 버튼이 오버레이 안에 있어 "오버레이가 켜져 있으면 측정 시작 불가" 규칙이 자기모순이었으므로, "시작을 누르면 나머지 조건을 검사하고 통과 시 오버레이를 자동으로 숨기며, 측정 중 오버레이를 다시 열면 그 세션은 무효"로 바꿨다(F10·F19). ③ 개발자 모드 오버헤드 비교를 세 상태가 섞여 판정 불가였던 것에서 "인자 없는 릴리스 빌드 vs `SURVIVOR_NO_DEV` 빌드"의 3분 플레이 3회 Profiler 비교로 다시 썼고, 비교용 빌드는 배포하지 않는다고 F13에 명시했다. ④ 충돌 이벤트 정렬을 "(채널, ID) 순"으로, ⑤ 측정 필수 조건에 "상자 드랍 0%와 무기 구성 프리셋 고정"을, ⑥ 객체 ID 세대 유일성을 "한 판 안에서"로(판 재시작 시 세대 1로 복귀, TECH D26), ⑦ F16의 존재하지 않는 Q21 참조를 바로잡았다.

F19를 F10과 분리한 이유: F10은 사용자가 Profiler로 재서 기록하는 사용자 수행 항목이고, 개발자 모드는 구현해야 하는 코드다. 한 기능에 두면 구현 대상과 사용자 수행 대상이 섞인다.

## 3. 기능별 요구사항 및 수용 기준 (Functional Requirements & Acceptance Criteria)

### 3.0 공통 규칙

**A. F11과 F3·F5·F6·F7의 역할 경계 (파일 소유권 기준)**
- **F11이 소유한다**: JSON 스키마 정의, JSON 파서/로더, 에셋 키 레지스트리(문자열 키 → 실제 프리팹/스프라이트), 스키마 검증과 오류 처리. 데이터 파일 자체의 형식 규칙도 F11 소유다.
- **F3(몬스터)·F5(레벨업 선택지)·F6(무기)·F7(조합)은 소비자다**: 이들은 F11이 로드한 정의 객체를 읽어 행동 로직을 구현한다. 파싱·검증·키 해석 코드를 자체적으로 갖지 않는다.
- 따라서 "JSON에서 읽는다 / 필드가 누락되면 거부한다 / 키를 에셋으로 해석한다"에 대한 수용 기준은 F11에만 있다. 소비자 기능의 수용 기준은 "정의된 값대로 동작한다"만 다룬다.
- JSON 관리 대상은 7종이다: 무기 정의, 몬스터 정의, 조합 규칙, 스폰 테이블, 패시브 정의, 레벨업 선택지 풀, 플레이어 기본 스탯. 패시브를 코드에 박으면 조합(F7)이 반쯤 하드코딩되어 F11의 핵심 주장이 약해지기 때문에 포함한다.

**B. 전략 교체 4건 공통 패턴 (F9, F16, F17, F18)**
- 각 전략은 인터페이스로 분리하고, 게임 코드는 인터페이스에만 의존한다.
- 각 전략은 런타임 토글 또는 빌드 설정 중 하나 이상으로 전환할 수 있어야 한다 (측정용). 4건은 서로 독립적으로 전환할 수 있어야 한다 (F10의 단독 기여 측정 전제).
- 전략을 바꿔도 게임 규칙상의 결과(피해 적용, 처치, 드랍 등)는 같아야 한다. 성능 특성만 달라진다.
- **(4회차 신규) 전략 전환의 적용 시점**: **타깃 탐색(F16)만 즉시 전환**하고, 풀링(F9)·Update 집중화(F17)·충돌 판정(F18) 전략은 **다음 판 시작 시 적용**한다.
- 전/후 측정은 F10이 소유한다. 각 기능의 기록 의무는 F10 기준으로 판정한다.
- 개발자 도구(F19)가 전략을 바꾸는 방식도 같은 구조(인터페이스 주입)를 따른다.

**C. 에셋 (스트레치 항목)**
- 1차 MVP의 필수 에셋은 Unity 기본 Sprite + 색상 도형이다.
- 완성 후 무료 에셋으로 교체하는 것은 **선택(스트레치) 항목**이며 필수 수용 기준이 아니다. 교체하지 않아도 어떤 기능도 미완료가 되지 않는다. 교체하는 경우에만 출처와 라이선스를 `README.md` 또는 `docs/`에 기록한다.

**D. 수치 밸런싱**
- 피해량, 체력, 이동속도, 경험치 곡선, 쿨다운 등 구체 수치는 이 문서에서 정하지 않는다. 구현·밸런싱 단계에서 조정하며, JSON 데이터로 노출해 코드 수정 없이 바꿀 수 있어야 한다 (Q1 참조).
- 이 문서에서 확정한 수치(스텝 1/60초, catch-up 3스텝, 스폰 반경 20, 디스폰 거리 45, 동시 400기 상한, 상자 확률, 카메라 orthographic size 9, 개발자 모드 배속 상한 3x, 측정 워밍업 300스텝 등)는 밸런싱 대상이 아니라 규칙이다.

**E. 일정**
- 마감 없음, 주당 10~20시간, 총 추정 140~160시간(주당 15시간 기준 9~11주)은 추정치이며 수용 기준이 아니다.

**F. 고정 타임스텝 (전역 아키텍처 규칙)**

게임 상태를 바꾸는 로직은 `FixedUpdate`(고정 간격)에서 실행하고, 렌더링과 입력 수집만 `Update`(매 프레임)에서 한다. 이유: 가변 `Time.deltaTime`을 쓰면 프레임레이트에 따라 한 프레임의 이동 거리가 달라져 투사체가 적을 통과하는 터널링, 적분 오차, 비결정론이 생긴다. 고정 스텝은 각 스텝의 dt가 항상 같아서 동작이 프레임레이트와 무관해진다. 이 규칙은 F1, F2, F3, F4, F6, F9, F16, F17, F18, F19의 수용 기준 전제다.

**스텝 간격은 1/60초**(Unity 기본 0.02초 대신)다. 근거: F10의 목표 FPS 기준(55/60)과 같은 단위라 측정 표를 환산 없이 읽을 수 있다.

수용 기준
- 주어진 이동, 충돌 판정, 스폰, 디스폰, 쿨다운, 투사체 수명, 몬스터 AI 등 게임 상태를 바꾸는 로직은 `FixedUpdate` 경로에서만 실행되어야 한다. `Update`에서는 렌더링 갱신과 입력 수집만 수행해야 한다. 로직 코드에서 가변 `Time.deltaTime`을 사용하지 않아야 한다.
- 주어진 스텝 간격(dt)은 실행 중 항상 1/60초로 고정되어야 한다.
- 주어진 `Update`에서 수집한 입력은 다음 스텝에서 소비되어야 하며, 한 프레임 안의 키 누름/뗌 이벤트(ESC, 1/2/3 선택 등)가 스텝 사이에서 유실되거나 중복 소비되지 않아야 한다.
- 주어진 동일한 입력 시퀀스(스텝 단위)와 동일한 난수 시드로 프레임레이트만 다르게(예: 30/60/144 FPS 제한) 같은 스텝 수만큼 실행하면, 플레이어 위치, 몬스터 수와 위치, 경험치, 투사체 상태가 서로 일치해야 한다.
- 주어진 난수 시드를 고정할 수 있어야 한다 (재현·측정용).
- **catch-up 상한 3스텝**: 주어진 한 프레임에서 밀린 스텝을 따라잡을 때 실행하는 스텝 수는 3을 넘지 않아야 한다(= 한 프레임당 최대 게임 시간 50ms, Unity의 `Time.maximumDeltaTime`을 0.05로 설정). 상한에 걸리면 못 따라간 시간을 버리고 **게임 시간이 실제 시간보다 느리게 흐르는 것(슬로모션)을 의도적으로 허용**한다. 근거: 상한 1이면 상시 슬로모션이 되고, 5 이상이면 무거운 프레임에서 스텝을 더 돌려 오히려 더 느려지는 악순환(death spiral)이 생긴다. 측정 대상이 "한 스텝에 몇 ms 걸리나"이므로 슬로모션은 측정에 영향이 없고 재현성에는 도움이 된다.
- 주어진 일시정지 또는 레벨업 선택 중에는 로직 스텝이 실행되지 않아야 한다.
- 주어진 게임 시간(경과 시간, 스폰 구간, 보스 등장 시각)은 실제 시간이 아니라 실행된 스텝 수 × 1/60초로 계산되어야 한다. 슬로모션 상황에서도 게임 시간 기준 규칙(스폰 표, 10분 보스)이 그대로 적용되어야 한다.
- **[스트레치]** 렌더 보간(스텝 사이 위치 보간)은 1차 범위에서 제외한다. 이유: 보간 비용이 F10 측정 수치를 오염시키므로 측정이 끝난 뒤에 넣어야 한다. 도입하더라도 측정 완료 후이며 필수 수용 기준이 아니다.

**G. 무한 평면과 좌표 (전역 규칙)**
- 맵에 경계가 없다. 플레이어 좌표에 제한을 두지 않으며 "맵 크기"라는 개념이 없다. 배경은 반복 배경(격자선·점 패턴 타일링 또는 UV 오프셋)이다.
- 좌표는 float를 쓴다. 10분 플레이에서 플레이어가 이동할 수 있는 최대 범위는 약 3,000유닛이라 float 정밀도로 안전하다.
- 무한 평면이므로 **디스폰 거리가 적 분포의 유일한 경계**다 (F3).
- 공간 분할(F16)은 무한 좌표를 해싱하는 **공간 해시**여야 한다. 고정 크기 배열 격자는 쓸 수 없다.

**H. (4회차 신규) 객체 ID**

충돌 판정과 타깃 탐색에 참여하는 모든 시뮬레이션 객체(몬스터, 투사체, 장판, 젬, 상자 등)의 ID는 **"인덱스 + 세대"** 형식이다. **디스폰(풀 반납 시점)마다 세대가 증가**한다. 이유: 풀링은 인덱스를 재사용하므로 인덱스만 ID로 쓰면 이미 사라진 객체의 쿨다운 기록이나 "이미 맞힌 ID 목록"이 같은 인덱스를 물려받은 새 객체에 잘못 적용된다. **세대 유일성은 한 판 안에서만 보장된다.** 판을 다시 시작하면 세대가 1로 돌아간다(TECH_SPEC D26). 타이브레이크(F16), 쿨다운 기록(3.0 I), 충돌 로그(F19)는 모두 이 ID를 쓴다.

수용 기준
- (5회차 수정) 주어진 한 판 안에서 풀 반납(처치 또는 디스폰) 뒤 같은 인덱스가 다시 쓰이면, 새 객체의 ID는 이전 객체의 ID와 달라야 한다(세대가 더 커야 한다). 판을 다시 시작하면 세대가 1로 돌아가는 것은 허용되며, 이전 판의 ID 기록(쿨다운, 맞힌 ID 목록)은 새 판으로 이월되지 않아야 한다.
- (4회차 신규) 주어진 ID 발급과 세대 증가 규칙은 풀 구현 A/B/C 어느 것을 쓰든 같아야 한다.
- (4회차 신규) 주어진 타이브레이크, 쿨다운 기록, 충돌 이벤트 로그는 모두 이 "인덱스 + 세대" ID를 사용해야 한다.

**I. (4회차 신규) 충돌 이벤트와 피해 적용 규칙**

충돌 판정 전략(F18)은 **Enter(새로 겹친 스텝)와 Exit(겹침이 끝난 스텝) 두 종류의 이벤트만** 보고한다. "누가 겹쳐 있는가, 언제 피해를 주는가"는 게임 로직이 전담하며, 이 로직은 전략과 무관하게 하나다. 피해 적용은 세 갈래다.

1. **일회성 접촉** — W1·W4 투사체, 경험치 젬, 상자: Enter 1회에 처리하고 객체를 회수한다. 관통 투사체는 "이미 맞힌 ID 목록"을 가진다.
2. **무기 → 적 지속 피해** — W2 궤도, W3 장판: **공격자 측 쌍별 쿨다운**. 무기 인스턴스가 대상별 "다음 허용 스텝"을 기록한다. Enter 때 허용 상태면 즉시 1회, 겹침이 지속되는 동안 허용 스텝마다 1회 적용한다. Exit 뒤에도 허용 스텝까지 기록을 유지한다(경계를 들락거리는 재진입으로 쿨다운을 우회하는 것을 막는다). 틱 간격은 무기 JSON 필드(초 단위)이며 로드 시 스텝으로 환산한다.
3. **적 → 플레이어** — 몸통 접촉, M3 투사체, M4 장판: **플레이어 공통 무적 시간**. 피격 후 일정 스텝 동안 모든 피해를 면제한다(플레이어 기본 스탯 JSON 필드). 쌍별로 하면 적 400기가 겹칠 때 즉사하기 때문이다. 무적 중 M3 투사체는 피해 없이 소모된다. 몸통 접촉 적이 여럿이면 그 스텝에 최대 피해 1회만 적용하며, 피해가 같으면 ID가 작은 쪽을 택한다.

쿨다운과 무적은 실수 시간이 아니라 **스텝 번호**로 센다(결정론).

세 갈래 각각의 구체 수용 기준은 F3(적→플레이어), F4(일회성 젬·상자), F6(무기 투사체·궤도·장판), F11(JSON 필드)에 있고, 여기에는 공통 기준만 둔다.

수용 기준
- (4회차 신규) 주어진 쿨다운과 무적은 실수 시간(`Time.time` 등)이 아니라 스텝 번호로 계산되어야 하며, 프레임레이트(30/60/144 FPS)와 무관하게 같은 스텝에 같은 피해가 적용되어야 한다.
- (4회차 신규) 주어진 충돌 판정 전략(F18 A/B)을 바꿔도 피해 적용 결과(누가 언제 얼마를 받았는지)가 같아야 하며, 피해 적용 로직은 전략별로 중복되지 않아야 한다.
