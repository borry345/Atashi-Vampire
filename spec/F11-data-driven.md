### F11. 데이터 기반 설계 (스키마·로더·레지스트리 소유자)

**요구사항**: 7종(무기 정의, 몬스터 정의, 조합 규칙, 스폰 테이블, 패시브 정의, 레벨업 선택지 풀, 플레이어 기본 스탯)을 JSON(ScriptableObject 아님)으로 관리한다. JSON 파일은 `StreamingAssets`에 둔다. 빌드 폴더에 원본 파일이 그대로 복사되므로 빌드 후에도 편집할 수 있다. JSON은 프리팹·스프라이트를 직접 참조할 수 없으므로 문자열 키로 간접 참조하며, 키를 실제 에셋으로 해석하는 레지스트리를 둔다. 이 기능은 JSON 파서/로더, 에셋 키 레지스트리, 스키마 검증을 포함한다. F3·F5·F6·F7은 이 결과를 소비한다. **JSON 파서는 Newtonsoft(`com.unity.nuget.newtonsoft-json`)** 를 쓰고, 필드 바인딩과 검증은 직접 구현한다. JSON 파일은 UTF-8이어야 한다.

**"코드 수정 없이 추가 가능"의 경계**: **기존 행동 타입의 파라미터·조합으로 구성되는 것까지**다. 예를 들어 "체력 300, 속도 2, 직선 추적형" 몬스터 추가는 JSON만으로 가능하다. "플레이어를 포위하는 AI"나 "벽에 튕기는 투사체" 같은 **새 행동 타입은 코드 추가가 필요**하며 범위 밖이다.

**파일 종류별 필수/선택 구분**: 필수 4종(무기 / 몬스터 / 스폰 테이블 / 플레이어 기본 스탯), 선택 3종(조합 규칙 / 패시브 정의 / 레벨업 선택지 풀 가중치).

**수용 기준**

*핵심 기준*
- **주어진 빌드된 게임(Windows 실행파일)에서 코드 재컴파일 없이 `StreamingAssets`의 JSON만 편집해 새 무기·몬스터를 추가하고 게임을 다시 실행하면, 그 무기·몬스터가 게임에서 사용 가능해야 한다. 이는 시연으로 증명 가능해야 한다.** (단, 기존 행동 타입 조합인 경우. 새 에셋 키가 레지스트리에 없으면 아래 규칙대로 기본 도형으로 대체된다.)
- 주어진 새 무기 JSON 정의를 추가하고 코드를 수정하지 않으면, 그 무기가 선택지 풀과 게임에서 사용 가능해야 한다 (기존 행동 타입 W1~W4 범주의 조합인 경우).
- 주어진 새 몬스터 JSON 정의를 추가하고 코드를 수정하지 않으면, 그 몬스터가 스폰 테이블에서 참조되어 게임에 등장해야 한다 (기존 행동 타입 M1~M3 범주 조합인 경우).
- 주어진 스폰 테이블, 조합 규칙, 패시브 정의, 레벨업 선택지 풀, 플레이어 기본 스탯도 JSON 편집만으로 바뀌어야 한다.
- 주어진 "새 행동 타입"은 범위 밖이며, 이 경계가 README에 문서화되어야 한다 (F12 연계).

*로더*
- 주어진 JSON 7종이 게임 시작 시 파싱되어 타입이 있는 정의 객체로 메모리에 적재되어야 한다. (개발자 모드의 핫 리로드는 예외, F19.)
- 주어진 JSON 파일은 `StreamingAssets`에서 읽어야 하며, 빌드(Windows 실행파일)에서도 에디터와 동일하게 로드되어야 한다 (에디터 전용 경로 의존 금지).
- 주어진 정상 JSON일 때 로드된 값이 파일의 값과 일치해야 한다 (필드 단위로).
- 주어진 JSON 문법 오류(깨진 JSON)일 때 게임이 크래시하지 않고, 어느 파일의 어느 부분이 문제인지 알 수 있는 경고/오류를 로그로 남겨야 한다.
- (4회차 신규) 주어진 JSON 파싱은 Newtonsoft(`com.unity.nuget.newtonsoft-json`)가 맡아야 하며, 필드 바인딩과 스키마 검증은 직접 작성한 코드가 맡아야 한다.
- (4회차 신규) 주어진 JSON 파일은 UTF-8이어야 한다. 읽은 텍스트에 디코딩 실패 문자(U+FFFD)가 있으면 "인코딩 오류 가능" 경고를 파일명과 함께 로그로 남겨야 한다(예: 한글 Windows 메모장의 CP949 저장 감지). 거부하거나 크래시하지 않아야 한다.

*정의 단위 스키마 검증과 실패 정책*
- 주어진 필수 필드 누락, 타입 오류, ID 중복, 참조 오류(존재하지 않는 무기/패시브/몬스터 ID 참조 등)가 있는 정의는 **해당 정의만 건너뛰고 경고 로그를 남기고** 게임은 시작해야 한다. 경고 로그에는 파일명, 정의 ID, 문제 필드(또는 참조)가 포함되어야 한다.
- 주어진 필수 필드 누락 정의의 경우 누락 필드명이 로그에 포함되어야 한다.
- 주어진 조합 규칙이 존재하지 않는 무기/패시브 ID를 참조하면 참조 오류로 감지되어야 한다. 스폰 테이블이 존재하지 않는 몬스터 ID를 참조해도 같다.
- 주어진 정의 ID가 중복되면 중복이 감지되어 경고 로그가 남아야 한다.
- 주어진 알 수 없는 키(스키마에 없는 필드)가 있으면 **무시하고 경고 로그**를 남겨야 한다. 거부하지 않아야 한다.
- 주어진 에셋 키가 레지스트리에 없으면 **기본 도형으로 대체하고 경고 로그**(키 이름 포함)를 남겨야 한다. 크래시하지 않아야 한다.

*파일 단위 실패 정책 (파일 전체 파싱 실패, 예: 중괄호 미닫힘. 정의 하나가 틀린 것과 층위가 다르다)*
- 주어진 **필수 4종** 중 하나라도 파일 전체 파싱에 실패하면 게임 **시작을 차단**해야 한다.
- (4회차 수정) 주어진 **선택 3종** 중 하나가 파일 전체 파싱에 실패하면 **경고 후 계속** 진행해야 한다. 조합 규칙이 없으면 진화만 안 되고(F7), 패시브 정의가 없으면 패시브가 선택지에서 빠지고(F5), 선택지 풀이 없으면 **회복을 포함한 모든 후보가 동일 가중치**로 폴백하되 회복은 체력 비율 가중을 유지해야 한다(F5).
- **"플레이 불가" 기준 4개**: ① 사용 가능한 무기 0개 ② 스폰 가능한 몬스터 0종 ③ 플레이어 기본 스탯 없음 ④ 스폰 테이블 없음. 검증 결과가 이 중 하나라도 해당하면 게임 시작을 차단해야 한다.
- 주어진 **플레이어 기본 스탯**은 단일 정의라 건너뛸 대상이 없으므로 오류면 시작을 **차단**해야 하며, 기본값으로 대체하지 않아야 한다. (기본값으로 때우면 밸런싱과 측정이 조용히 거짓이 되고, 그걸 모른 채 측정 결과를 포폴에 적게 된다.)
- 주어진 시작 차단 시 **콘솔 로그와 별개로 화면에 원인을 표시**해야 한다(어느 파일의 무엇이 문제인지). 사용자가 JSON을 직접 편집하므로 콘솔에만 로그가 남으면 그냥 고장난 것으로 보인다. 경고 후 계속 진행하는 경우는 콘솔 로그만으로 충분하다.
- 위 모든 경우에 로그가 반드시 남아야 한다. 어떤 경우도 조용히 무시하지 않아야 한다 (`CODING_GUIDE.md` §4와 일치).

*터널링 방지 검증 (로드 시 데이터 검증, 상세 규칙은 F18)*
- 주어진 JSON 로드 시 F18의 객체별 이동 불변식(`v_x/60 ≤ r_x`)이 검증되어야 한다. 위반은 경고만 하며 시작을 차단하지 않아야 한다 (StreamingAssets 편집 허용 취지 보존).

*에셋 키 레지스트리*
- 주어진 JSON의 에셋 키(문자열)가 레지스트리에 등록된 키이면 실제 프리팹/스프라이트로 해석되어야 한다.
- 주어진 새 에셋(도형 프리팹)을 레지스트리에 등록하고 JSON에서 그 키를 쓰면 코드 수정 없이 사용 가능해야 한다. 레지스트리에 키를 등록하는 방식(에디터 설정 등)은 코드 수정이 아닌 에디터/데이터 작업이어야 한다.
- 프리팹/스프라이트를 JSON에서 파일 경로나 GUID로 직접 참조하지 않는다. 문자열 키만 허용한다.

*소비자와의 경계*
- F3·F5·F6·F7 코드가 JSON 파싱, 검증, 에셋 키 해석을 직접 수행하지 않고 F11이 제공하는 정의 객체와 레지스트리만 사용해야 한다.
- 스키마(필드 목록, 필수/선택, 예시)가 `README.md` 또는 `docs/`에 문서화되어야 한다.

*(4회차 신규) 피해 틱·무적 필드와 출력 파일 형식*
- (4회차 신규) 주어진 무기 정의 스키마에는 W2/W3 피해 틱 간격 필드(초 단위)가 있어야 하며, 로드 시 스텝 수로 환산되어 로드된 정의 객체에 스텝 값으로 들어가야 한다(3.0 I).
- (4회차 수정) 주어진 플레이어 기본 스탯 스키마에는 공통 무적 시간 필드가 있어야 하며, **초 단위로 입력하고 로드 시 스텝으로 환산**해야 한다. 환산은 W2/W3 틱 간격과 같은 "초→스텝 환산" 공유 규칙을 써야 한다(Q46, 기본값 채택). 이 필드가 누락·오류이면 플레이어 기본 스탯 오류 정책(시작 차단)을 따라야 한다.
- (4회차 신규) 주어진 측정 CSV와 충돌 이벤트 로그 등 게임이 쓰는 CSV 파일은 UTF-8 BOM으로 저장되고 소수점은 InvariantCulture 형식(점)으로 쓰여야 한다.
