### F10. 성능 측정과 비교 기록

**요구사항**: F9, F16, F17, F18 네 건에 대해 측정값을 수치로 기록한다. 측정 항목은 **6개**로 고정한다. 측정은 F19 개발자 모드가 켜진 실제 게임 씬에서 수행한다.

| 번호 | 측정 항목 |
|---|---|
| 1 | 평균 FPS |
| 2 | 1% low(가장 느린 1% 프레임의 평균) 또는 최악 프레임 시간 |
| 3 | 프레임당 GC 할당 |
| 4 | 동시 몬스터 수 한계 (**A0 스윕에서만** 측정, N 고정 회차 A·B·C에서는 "해당 없음"으로 기록) |
| 5 | 해당 시스템의 ms (스텝당과 프레임당을 모두 기록하고, **스텝당을 주 지표**로 쓴다) |
| 6 | 메모리: 총 사용 메모리(Total Used Memory / Total Reserved Memory 계열 카운터). 측정 구간의 **평균과 최댓값**을 CSV에 두 열로 기록 |

**항목 2를 둔 근거**: 풀링의 본질은 GC로 인한 간헐적 스파이크 제거인데, 스파이크는 평균 FPS에 희석되어 잘 드러나지 않는다.

**항목 5의 근거와 정의**: 고정 스텝이라 한 프레임에 스텝이 1~3번 돌므로 같은 시스템의 비용이 두 기준으로 갈린다. 전략 비교는 스텝당으로 해야 공정하고(프레임당은 스텝 수가 섞여 들어가 알고리즘이 느린 건지 스텝이 많이 돈 건지 구분할 수 없다), 프레임 예산 판단은 프레임당으로 해야 한다. **스텝당 ms = 측정 세션 전체의 시스템 시간 합 / 전체 스텝 수**이며, 프레임별 비율의 평균이 아니다. 프레임당 ms도 같은 방식(세션 전체 합 / 전체 프레임 수)으로 구한다.

**항목 6의 근거**: PRD 축 2-1이 측정 수치로 "메모리"를 명시했다. 풀링은 GC 할당을 줄이는 대신 메모리를 미리 점유하므로 두 값을 함께 봐야 트레이드오프가 드러난다. 카운터 하나를 더 읽는 비용은 미미하다.

**"동시 몬스터 수 한계"의 정의**: 평균 FPS가 55 미만으로 떨어지는 시점의 동시 존재 수. (60은 수직동기·측정 노이즈에 걸리기 때문에 쓰지 않는다.) 이 값은 N을 올려가는 A0 스윕에서만 얻을 수 있으므로, N을 고정하는 A·B·C 회차에서는 정의상 측정할 수 없어 "해당 없음"으로 기록한다.

**끔/켬 정의**

| 전략 | 끔(기준선) | 켬(직접 구현) |
|---|---|---|
| 풀링 | `Instantiate`/`Destroy` | 자체 구현 풀 |
| 타깃 탐색 | 전수 순회 | 공간 분할(공간 해시) |
| Update | MonoBehaviour별 `FixedUpdate` | 중앙 틱 |
| 충돌 | `Collider2D` | 자체 제곱거리 |

**측정 설계**

| 묶음 | 구성 | 목적 |
|---|---|---|
| A0. 기준선 탐색 | 기준선(전부 끔)으로 적 수를 올려가며 평균 FPS 55 미만이 되는 지점 **N\*** 를 찾는다 | A·C의 측정 적 수 결정, 항목 4 측정 |
| A. 전략 비교 6회 @ N\* | 전부 끔 / 풀링만 켬 / 타깃 탐색만 켬 / Update만 켬 / 충돌만 켬 / 전부 켬 | 단독 기여와 상호작용 |
| B. 스케일링 곡선 8회 | 적 50/100/200/400 × {전수 순회, 공간 분할} | 곡선과 교차점 |
| C. 엔진 대안 2회 @ N\* | `UnityEngine.Pool.ObjectPool<T>`, `Physics2D` 쿼리 (각 회차에서 **나머지 세 전략은 기준선(전부 끔)** 으로 둔다) | 내 구현 vs 엔진 제공 |

- A의 6회차는 단독 기여 합과 비교해 **상호작용**을 확인한다. F16의 공간 분할을 F18이 후보 추림에 재사용하므로 두 전략은 독립이 아니다.
- **6회를 400기 고정에서 돌리지 않는다.** 400기는 게임플레이 상한일 뿐이며, 모든 전략이 그 지점에서 여유롭게 돌면 차이가 측정 노이즈에 묻힌다. N\*는 기준선이 버거워지기 시작하는 지점이라 차이가 가장 선명하다. 이 기준(평균 FPS 55 미만)은 측정 항목 4의 정의를 그대로 재사용한 것이라 임의 선택이 아니다.
- C를 A와 섞지 않는 이유: A는 "내 설계 변경의 효과", C는 "내 구현 vs 엔진 제공"이라 질문이 다르다. C에서 나머지 세 전략을 기준선으로 두는 이유도 같다 — 바꾼 변수가 하나여야 엔진 대안과 A의 단독 회차를 직접 비교할 수 있다.
- 총 측정 회차: A 6 + B 8 + C 2 = 16회 (A0은 N\* 탐색 절차). 개발자 모드 오버헤드 확인용 비교(F19, 인자 없는 릴리스 빌드 vs `SURVIVOR_NO_DEV` 빌드의 3분 플레이 3회 Profiler 비교)는 16회에 포함하지 않는 별도 1회다.

**N에 따른 디스폰 거리 D**: N ≤ 400이면 D = 45, N > 400이면 **D = 45·√(N/400)** (밀도 일정 — 면적이 반경² ∝ N이므로). A0·A·B·C 전 회차에 적용하고 측정 CSV에 사용한 D를 기록한다.

**측정 필수 조건** (전부 측정 CSV 헤더에 기록한다)
- 결정론 설정: 레벨업 비활성, 고정 시드, 플레이어 자동 경로(F19)
- 플레이어 무적
- 고정 무기 구성: W1~W4 각각의 단계를 명시하고 전 회차에서 동일하게 유지
- (5회차 신규) 측정 중 **상자 드랍 0%** (상자 효과로 무기 구성이 바뀌는 것을 막는다). **프리셋 무기 구성은 측정 내내 고정**한다.
- 스폰 중단 + 적 수 N 유지 모드 (죽으면 재스폰)
- 측정 환경 고정: 수직동기 끔, `Application.targetFrameRate` 무제한, 스크립팅 백엔드 Mono, 점진적 GC는 Unity 기본값 유지. 이 네 값과 PC 사양을 CSV 헤더에 기록한다.
- 워밍업: 적 수가 N에 도달한 뒤 **300스텝은 통계에서 제외**한다.
- (5회차 수정) 측정 시작 규칙과 배제 조건: 오버레이 안의 **측정 시작을 누르면** 나머지 조건(시각화 전부 끔, 충돌 이벤트 로그 끔, 배속 1x, 한 스텝 모드 아님)을 검사해 하나라도 어긋나면 **거부**하고, 통과하면 **오버레이를 자동으로 숨기고(렌더 비용 0) 시작**한다. 측정 중 오버레이를 다시 열면 **그 세션은 무효로 표시**된다.

**역할 구분**: 측정 훅과 F19 개발자 모드는 구현 대상이다. Profiler 연결, 측정 실행, 결과 기록은 **사용자 수행**이다.

**수용 기준**
- (4회차 수정) 주어진 A(6회), B(8회), C(2회) 구성 각각에 대해 측정 결과가 **6개 항목** 모두 `docs/devlog.md`(또는 측정 전용 섹션)와 측정 CSV에 수치로 기록되어야 한다. 항목 누락이 없어야 한다. 항목 5는 스텝당과 프레임당 값이 모두 있어야 하고, 항목 4는 A0에서만 값이 있으며 A·B·C에서는 "해당 없음"으로 기록되어야 한다.
- 주어진 A0 결과로 N\*와 그 도출 과정(어떤 적 수에서 평균 FPS가 55 미만이 되었는지)이 기록되어야 하고, A와 C는 같은 N\*에서 수행되어야 한다.
- (5회차 수정) 주어진 측정은 **F19 개발자 모드(실제 게임 씬)** 에서 수행되어야 한다. 측정 전용 씬이 아니므로 결정론 설정(레벨업 비활성, 고정 시드, 플레이어 자동 경로, 3.0 F)과 측정 필수 조건(무적, 고정 무기 구성, **상자 드랍 0%와 프리셋 무기 구성 고정**, 스폰 중단 + N 유지)이 모두 적용되어 있어야 하며 기록에 이 설정이 남아야 한다.
- 주어진 모든 측정에서 난수 시드와 적 배치 조건이 동일해야 하며, 기록에 시드 값이 남아야 한다.
- (5회차 수정) 주어진 측정 시작을 누르면 시각화 전부, 충돌 이벤트 로그, 배속(1x), 한 스텝 모드 조건이 검사되어 하나라도 어긋나면 측정이 시작되지 않아야 하고, 통과하면 오버레이가 자동으로 숨겨진 채 시작되어야 한다(측정 수치 오염 방지). 측정 중 오버레이를 다시 열면 그 세션이 무효로 표시되어야 한다.
- 주어진 측정은 **Development Build에 Profiler를 연결**해서 수행되어야 한다. 에디터 Profiler 값은 개발 중 빠른 확인용이며 공식 기록으로 인정하지 않는다.
- 주어진 모든 측정 기록에는 측정 PC 사양(CPU, GPU, RAM, OS)이 함께 적혀 있어야 한다.
- 주어진 측정 기록에는 측정 조건(빌드 종류, 전략 조합, 적 수, 디스폰 거리 D, 시드, 측정 시간 길이, 스텝 간격)이 적혀 있어야 한다. 재현 가능해야 한다.
- 주어진 A의 2~5회 단독 기여 개선 폭의 합계와 6회 실제 개선 폭의 비교가 기록되고, 차이(상호작용)에 대한 해석이 한 줄 이상 포함되어야 한다.
- **스케일링 곡선**: 주어진 B 측정은 적 수 50/100/200/400기 각각에서 전수 순회와 공간 분할 두 곡선으로 기록되어야 한다(표 또는 그래프). 곡선이 꺾이는지 여부가 관찰 결과로 서술되어야 한다.
- **교차점 기록**: 격자 유지 비용 때문에 적이 적은 구간에서는 전수 순회가 공간 분할보다 더 빠를 수 있다. 두 곡선의 교차 지점(또는 교차 구간, 교차하지 않으면 그 사실)이 기록되어야 한다. 전수 순회 전략은 **출하용이 아니라 대조군**이라는 점이 기록에 명시되어야 한다.
- (4회차 수정) 주어진 "동시 몬스터 수 한계"는 위 정의(평균 FPS 55 미만이 되는 시점의 동시 존재 수)로 **A0 스윕에서** 측정되고, 측정 방식이 기록에 명시되어야 한다.
- (4회차 수정) 주어진 적 수를 올릴 때 디스폰 거리 D도 위 공식(N ≤ 400이면 45, 초과면 `45·√(N/400)`)으로 함께 올려 밀도를 일정하게 유지해야 하며, 사용한 D가 기록되어야 한다 (F19).
- (4회차 수정) 주어진 측정 결과를 **CSV로 내보내는 기능**이 있어야 한다 (16회 측정의 표·그래프 작업 비용 절감, F19). CSV는 UTF-8 BOM, 소수점은 InvariantCulture 규칙을 따른다(F11).
- (4회차 수정) **목표치(합격선) 상태**: 목표 숫자는 지금 정하지 않는다. **숫자는 F19 완료 후 A0 기준선 측정 시점에 확정하고 그때 이 SPEC을 개정**한다(Q45). 현재 SPEC은 어떤 수용 기준에도 목표 수치를 포함하지 않는다.
- 주어진 각 전/후 비교에는 "무엇을 바꿨고, 수치가 어떻게 달랐고, 왜 그렇다고 판단하는가"의 해석이 한 줄 이상 포함되어야 한다.
- (4회차 신규) 주어진 스텝당 ms는 측정 세션 전체의 시스템 시간 합을 전체 스텝 수로 나눈 값으로 계산되어야 하며, 프레임별 비율의 평균으로 계산하지 않아야 한다.
- (4회차 신규) 주어진 측정 구성(CSV 헤더)에 무적 여부, 고정 무기 구성(W1~W4 단계), 스폰 중단 + N 유지 모드 여부, 수직동기·`targetFrameRate`·스크립팅 백엔드·점진적 GC 설정값, 적 수 N 도달 후 제외한 워밍업 스텝 수(300)가 모두 적혀 있어야 한다.
- (4회차 신규) 주어진 N 도달 후 300스텝은 통계 집계에서 제외되어야 한다.
- (4회차 신규) 주어진 C 묶음의 두 회차에서는 엔진 대안 하나만 켜고 나머지 세 전략은 기준선(전부 끔)이어야 한다.
- (4회차 신규) 주어진 측정 항목 6(메모리)은 총 사용 메모리(Total Used/Reserved Memory 계열 카운터) 값으로 각 회차에 기록되어야 하며, 측정 구간의 **평균과 최댓값**이 CSV의 두 열로 기록되어야 한다(Q46, 기본값 채택).
- (4회차 신규) 주어진 젬 수가 측정 CSV에 기록되어야 하고, 젬 부하가 비교를 가리는 것으로 드러나면 F4에 디스폰 규칙을 추가하는 판단이 devlog에 남아야 한다.
